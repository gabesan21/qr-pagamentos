# Spec - Storefront and customization

- **Project:** [[PROJECT|QR Pagamentos]]
- **Epoch/Phase:** [[roadmap/5-storefront-and-production|Phase 5.1-5.2]]
- **Status:** aprovada
- **Created:** 2026-07-21
- **Updated:** 2026-07-26 — task 9.2.2 adds the sessionless `/store/[slug]/pay` standalone-payment buyer experience, deliberately amending the redaction boundary with the `checkoutDataPolicy` member (the V1 `checkoutPolicy` precedent); the storefront custom-amount item gains the pay action. Earlier: 2026-07-26 — task 9.1.1 extends the public `/store/[slug]` projection with the redacted grouped catalog and the derived standalone-payments capability flag, deliberately amending the redaction boundary for the product-UUID cart reference and the resolved display currency code; task 9.1.2 rebuilds the sessionless `/store/[slug]` page as the branded grouped catalog with the slug-scoped versioned browser-local cart, further amending the boundary with the `standalonePaymentCurrencyCode` display label; task 9.2.1 gives the `standalonePayments` capability its first consumer (the sessionless standalone checkout) and pins the default-currency dispatch resolution with its opaque failure mode; task 9.1.3 adds the sessionless cart checkout command that turns a product-only browser cart into one owner-derived SINGLE_USE Commerce V2 link.

## What it covers

This spec defines the durable per-owner storefront contract: the persisted settings an owner controls, their validation and defaults, and the redaction boundary of the public storefront page. Checkout and order behavior stays in [[specs/checkout-and-order-lifecycle|Checkout and order lifecycle]].

## Requirements

- Every account owns exactly one storefront settings record, persisted on the account itself: a nullable public slug, a nullable display name per supported locale (`pt-BR` and `en`), a nullable brand accent color, an `enabled` flag, a nullable theme id, a nullable layout, a nullable logo media identifier, a standalone-payments flag, and a nullable default exchange currency code. The `enabled` flag defaults to disabled; no storefront is ever public until its owner opts in. The standalone-payments flag defaults to enabled, preserving payment-link behavior for every existing merchant.
- **Slug V1:** a storefront slug is lowercase ASCII, matches `^[a-z0-9](-?[a-z0-9])*$`, and is 1–63 characters. It is globally unique across all accounts; a collision on save is one opaque conflict outcome that never identifies the other owner or confirms that any particular slug is taken. Blank input clears the slug (null). Slugs appear only under the `/store/[slug]` path prefix, so no reserved-word list exists.
- **Display names V1:** each localized display name is nullable, NFC-normalized, trimmed, single-line, and at most 160 Unicode code points when present; blank input becomes null. Fallback rendering when a display name is absent belongs to the public page task, not to this settings contract.
- **Accent color V1:** the brand accent color is exactly one `#RRGGBB` hex value (uppercase persisted) or null; blank input becomes null.
- **Theme and layout V1:** the theme id is one of the closed six design-system themes (single source: the theme modifier contexts of `tokens/resolver.json`, re-exported read-only by `src/design-system/themes.ts` with a contract test pinning the two); the layout is `boxed` or `table`. Both are nullable; blank input clears them. Fallbacks are resolved at read/projection time, never stored: theme falls back to the design-system default (`pix-paper`), layout to `boxed`.
- **Default currency V1:** the store's default exchange currency is one uppercase `[A-Z]{3}` ISO 4217 code (format-validated at the service boundary, with a database `AAA`–`ZZZ` bounds check as defense-in-depth) or null; blank input clears it. Assigning a non-null code requires an active mapping in the dynamic registry defined in [[specs/catalog-and-payment-links|Catalog and payment links]]; a missing or inactive mapping fails the whole save with the same opaque failed outcome. A stored code survives later mapping deactivation for reads — only new assignments gate. No store or storefront surface may expose provider UUIDs, inactive codes, or a public currency-discovery surface.
- **Logo V1:** the settings record stores only the opaque 43-character media identifier of a `STOREFRONT_LOGO` object (no database foreign key; media rows are physically purged after grace). Replacement activates the new object through the canonical media boundary, saves the row, then orphans the previous object; a save failure compensates with a best-effort orphan of the just-activated object, so the worst case is a quota-counted unreferenced `ACTIVE` object, never a broken reference. Clearing saves null and orphans the old object.
- **Absent-versus-clear merge semantics:** every extended field (theme, layout, logo, standalone toggle, default currency) participates in a save only when the submitted form carries it; absent fields leave the stored values unchanged, while explicit blank input clears the nullable fields. This keeps legacy forms that submit only the original fields from silently wiping the extended settings. The settings workspace client reinforces this contract by omitting from the payload every extended field whose value still equals its prefilled one (observing the native `formdata` event, never intercepting the POST), so a save with an unchanged — possibly since-deactivated — stored currency succeeds without re-gating, while an emptied logo field still submits its explicit empty value to clear.
- **Settings workspace V1:** the merchant `/settings` route owns one sectioned bilingual storefront workspace (Identity, Appearance, Payments, Default currency) with a single native save. The Appearance section's live preview is a miniature storefront mock scoped by the additive `[data-theme-preview="<id>"]` token projection (byte-identical to the page-level theme block) plus the owner accent custom property; with no logo it renders only the official `BrandIdentity` merchant-fallback lockup, never a page-local mark. Logo upload is a separate origin-guarded `POST /storefront/logo` that stages a `STOREFRONT_LOGO` object through the media boundary and returns only empty `401`/`403` or opaque redirects — success carries the public-safe opaque identifier, failure carries no cause; the workspace previews the staged object through `/media/[identifier]` (owner-readable `STAGED`) and the settings save activates/orphans per Logo V1. Abandoned `STAGED` logos stay quota-counted until reconciliation, the accepted posture shared with 7.1.2. The default-currency select lists only the registry's active redacted `{ code, label }` choices plus a clear option; when no mapping is active it renders disabled with a bilingual explanation — a normal empty state, never an error and never the gating path.
- Enabling a storefront requires a valid slug already present in the same save; a save that requests enablement without a valid slug is rejected without mutation. Disabling never requires a slug and never clears the stored slug.
- The two toggles are independent: a disabled storefront keeps `/store/[slug]` unavailable while payment links and checkout stay reachable through the standalone-payments behavior. Task 9.2.1 gave the standalone toggle its first consumer: the sessionless standalone checkout (`POST /api/store/[slug]/checkout`, defined in [[specs/checkout-and-order-lifecycle|Checkout and order lifecycle]]) resolves the slug to an owner only when `storefront_enabled AND storefront_standalone_payments_enabled` hold, and the stored default currency code must resolve through the registry's active-pointer seam for dispatch — unknown/disabled slug, toggle off, null stored code, deactivated mapping, or inactive pair are one indistinguishable empty no-store `404`, with never a `BRL`/other-code fallback ("a stored code survives later deactivation" stays a reads-only rule and never applies to dispatch).
- Storefront settings change only through the authenticated owner's own re-authorized settings save, scoped to that owner and an `ACTIVE` account; no administrator, cross-owner, or public mutation path exists. Saves report only opaque changed/failed/conflict outcomes.
- **Public redaction boundary:** the sessionless `/store/[slug]` page may expose only the slug, the two display names, the accent color, the resolved theme id, the resolved layout, the logo media identifier (served or opaquely unavailable through the media read route), the owner's active products that have at least one active payment link (each linking to its checkout), the redacted public catalog delivered by task 9.1.1, and the derived `standalonePayments` capability boolean. The catalog groups the owner's active, non-archived products under their active categories (localized names only, deterministic closed ordering) with one uncategorized group sorted last — a product whose category is absent or inactive falls into it, and categories with no catalog products never appear. Each catalog product exposes exactly: an opaque `reference` (the canonical product UUID — unguessable, authority-free, and revalidated server-side by every later cart command; the deliberate 9.1.1 amendment reviewed at the critical 003 gate), the localized title and description, the exact-decimal price, the resolved display currency code (the product's stored code, else the store default, else null — display metadata only, surviving later registry deactivation like every stored code, and never a provider pair UUID or an inactive-code discovery surface), the opaque product image media identifier, and the `available` eligibility verdict (true for every member today because membership requires active ∧ non-archived; reserved so future eligibility rules can degrade a member instead of hiding it). The projection also exposes `standalonePaymentCurrencyCode` — the stored store-default code labelling the standalone custom-amount item and cart totals (the deliberate 9.1.2 boundary amendment: display metadata only, surviving later registry deactivation like every stored code, never a provider pair UUID or an inactive-code discovery surface). The projection also exposes `checkoutDataPolicy` — the owner's checkout data policy, exposed so the sessionless standalone-payment page (`/store/[slug]/pay`) renders the policy-exact customer form before any submit (the deliberate 9.2.2 boundary amendment: the same public-safe exposure V1 already ships as `checkoutPolicy` through the sessionless checkout presentation read; the server re-derives the policy from the locked owner row on every checkout command, so the member never grants authority). The projection never exposes either toggle's raw value beyond the enabled gate and the derived capability boolean, the owner identifier, username, email, credential state, provider data (including pair UUIDs), category UUIDs/state/versions/timestamps, product internal fields beyond the `reference` UUID and the media identifiers, or any other account data. Catalog reads stay bounded through deterministic ordering plus explicit `take` caps on categories and products.
- **Public page and browser cart V1 (9.1.2):** the sessionless `/store/[slug]` page scopes the resolved theme with `data-theme-preview` on `<main>` plus the validated `--storefront-accent` custom property, renders the logo through `/media/[identifier]` with a localized alt (the official merchant-fallback lockup while no logo exists), and renders the grouped redacted catalog as the single browsing surface in the owner's `boxed` or `table` layout — the V1 link-driven `products` list no longer renders on the page (the DTO member stays byte-frozen and `/pay/[identifier]` links remain reachable directly). A standalone custom-amount first item appears when `standalonePayments` is on, and that item alone makes a store non-empty. The cart is purely browser-local: key `qr-pagamentos:storefront-cart:v1:<slug>`, envelope `{ version: 1, items }`, product items `{ kind: "product", reference, quantity }` with an integer quantity bounded 1–9,999 (the V2 line bounds), and at most one `{ kind: "custom-amount", amount }` whose amount follows the canonical positive-decimal grammar (the product price class). Unknown versions or unparseable payloads discard silently; only references and quantities persist — never prices or totals. Every hydration reconciles the stored cart against the server-rendered catalog snapshot: entries whose `reference` is absent or `available: false` drop, quantities clamp, duplicate references keep the first entry, the custom amount survives only while standalone payments stay enabled, and exactly one localized "cart was updated" notice appears when anything changed — the cart never trusts stored data beyond item identity. Totals are exact BigInt arithmetic at the grammar's 6-place scale (never `Number`, never floats), grouped per resolved currency code and never summed across currencies; a null-code group renders without a code label. No server cart exists; the cart's only checkout affordance is the 9.1.3 command below.
- **Sessionless cart checkout command (9.1.3):** `POST /api/store/[slug]/cart/checkout` is an unlocalized, dynamic, sessionless route with `Cache-Control: no-store` on every outcome and no origin guard. Before JSON parsing or service work the bounded single-process public limiter may return only an empty no-store `429` (one additive closed surface `storefront-cart-checkout-submit`, the same 12-per-minute submit class as the other submit surfaces); the server-request-log inventory gains exactly the one literal template `/api/store/[slug]/cart/checkout`. The body is exactly `{ items: [{ reference, quantity }] }` — the browser cart contributes only product identity and quantity, never price, currency, or title; a `custom-amount` member, any foreign key, an empty or over-twenty-line cart, a duplicate reference, or a quantity outside 1–9,999 is the one opaque empty `400`. The command revalidates everything against locked persisted rows (owner, products, and registry pair under shared row locks, the same service-fenced active-dependency posture as V2 link creation): the slug resolves only to an `ACTIVE` merchant `USER` with an enabled storefront (anything else is the one opaque empty `404`), every `reference` must be that owner's active non-archived product (a stale or cross-owner reference is the opaque `400`), and every line's resolved currency code (product code, else store default) must be one identical code with an active registry mapping (null, mixed, or unmapped codes are the opaque `400`). Success issues exactly one active `SINGLE_USE` `PRODUCT_LINES` Commerce V2 link with null expiry, owned by the storefront owner and built from the locked product rows and registry pair through the delivered owner service reused server-side (a principal synthesized from the locked owner row, never authority beyond the active merchant owner) — no cart table, no order, no attempt, and no provider call at issuance; issued links are ordinary merchant-owned V2 rows (visible in the owner directory, deactivatable, `paid`-projected on settlement). The success body is exactly `201 { paymentLinkIdentifier }` — never owner, amounts, pair UUIDs, or a composition echo — and thrown service faults (identifier-collision conflict or the dependency-deactivation race) propagate to the request-log `failed` record, never a mapped body. The page's cart-checkout control renders only for a populated product-only cart (a custom-amount member keeps 9.2.1's separate command); on `201` it clears only that store's cart key and redirects to `/pay/[identifier]`, and on any failure the cart stays intact behind one opaque localized error. Until 9.3.1 delivers the branded V2 checkout, a V2 identifier on `/pay/[identifier]` renders the generic unavailable view — this task proves issuance, clear, and redirect, not V2 page rendering.

## Implemented slices

- **Task 5.1.1:** Owner columns on the account carry the slug (unique nullable index), both display names, accent color, and `storefront_enabled` defaulting to `false`, with database checks matching the application formats and enable-requires-slug. The server-only `src/auth/storefront-settings.ts` service validates Slug/Display-name/Accent-color V1, enforces enable-requires-slug, and maps uniqueness collisions to an opaque conflict. The bilingual owner dashboard card saves through `POST /storefront`, which re-authorizes the cookie principal and returns only empty `401`/`403` or opaque `?storefront=changed|failed|conflict` redirects. No public `/store/` page exists yet.
- **Task 7.1.2:** The account gains the five extended columns (theme id and layout with closed-set checks, logo media identifier without a foreign key, standalone-payments flag defaulting to true, default currency code with the `AAA`–`ZZZ` bounds check). The settings service merges absent-versus-clear input over the current row, gates new currency assignments on the registry's `requireActivePair`, and orchestrates logo replacement through the media boundary's identifier-based owner-fenced `activateOwned`/`orphanOwned` (activate → save → orphan, with compensating orphan on save failure). `POST /storefront` forwards extended fields only when the form carries them, keeping the legacy dashboard card safe. The public `/store/[slug]` projection surfaces the resolved theme id, resolved layout, and logo identifier only. The settings UI and logo upload remain with task 7.1.3.
- **Task 7.1.3:** The merchant `/settings` route gains the sectioned bilingual storefront workspace (Settings workspace V1): identity, appearance with live `data-theme-preview` mock and logo block, independent payments toggles, and the default-currency select with its disabled-when-unmapped explained state. `POST /storefront/logo` stages logo uploads (one literal request-log entry); the client boundary omits unchanged extended fields from the save payload so an unchanged since-deactivated currency save succeeds. The run-bound `store-settings:evidence` contract binds six themes × two locales × three widths plus interaction captures (staged-logo preview, remove→official-fallback, currency states, keyboard traversal, click/Enter native POSTs).
- **Task 9.1.1:** The sessionless `/store/[slug]` projection extends from branding-only to the redacted public catalog defined in the amended Public redaction boundary: the owner's active, non-archived products grouped by active category (localized names, deterministic closed ordering, uncategorized group last, empty categories omitted) with per-product opaque UUID `reference`, bilingual title/description, exact-decimal price, resolved display currency code (product code, else store default, else null), image media identifier, and the `available` eligibility verdict, plus the derived `standalonePayments` capability boolean. Reads stay bounded (explicit `take` caps on categories and products, zero catalog reads when the slug does not resolve); slug validation, the one opaque null outcome, the V1 link-driven `products` member, and the page rendering are unchanged. The deliberate boundary amendment (product-UUID cart reference and resolved display currency code) applies to this projection only; every V1 DTO stays frozen and no route, mutation, rate-limit surface, or UI changes.
- **Task 9.1.2:** The sessionless `/store/[slug]` page becomes the bilingual branded catalog experience defined in Public page and browser cart V1: the owner theme scoped by `data-theme-preview` on `<main>` with the validated accent, the logo through the media read or the official merchant fallback, the grouped catalog as the single browsing surface in the `boxed` or `table` layout (the V1 link-driven list no longer renders; its DTO member stays byte-frozen), the standalone custom-amount first item labelled by the amended `standalonePaymentCurrencyCode` member, per-product 1–9,999 quantity steppers, and the slug-scoped versioned browser-local cart with hydration-time stale-item recovery (one localized notice), exact BigInt per-currency totals never summed across currencies, and no checkout control. Loading skeleton, enabled-but-empty, opaque unavailable, and opaque error-plus-retry states are explicit. The run-bound `storefront:evidence` contract binds six themes × two locales × three widths on the boxed layout plus interaction captures (table layout, cart add/quantity/reload-persistence/stale-recovery, standalone off, logo and fallback, empty, unavailable, 320px reflow).
- **Task 9.1.3:** The sessionless cart checkout command defined in its requirement bullet above is delivered: `src/checkout/storefront-cart-checkout.ts` revalidates the browser cart against locked owner/product/registry rows and issues one owner-derived active `SINGLE_USE` `PRODUCT_LINES` V2 link through the delivered owner service (no order, attempt, or provider side effect); `POST /api/store/[slug]/cart/checkout` answers the closed opaque 429-before-parse/400/404/`201 { paymentLinkIdentifier }` set with one additive 12-per-minute rate-limit surface and one literal request-log entry. The page's cart section gains its only primary action — the product-only checkout control that clears only this store's cart key and redirects to `/pay/[identifier]` on issuance, keeps the cart intact behind one opaque localized error on failure, and never renders with a custom-amount member. The `storefront:evidence` contract rebinds with the checkout control, hidden-control, opaque-failure, and issued-redirect captures.
- **Task 9.2.2:** The public projection gains exactly the additive `checkoutDataPolicy` member defined in the amended Public redaction boundary, and the storefront custom-amount item gains one pay action linking to `/store/[slug]/pay?amount=<draft>` (prefill only, revalidated against the canonical amount grammar client-side and again by 9.2.1 server-side). The sessionless `/store/[slug]/pay` page delivers the standalone-payment buyer experience defined in [[specs/checkout-and-order-lifecycle|Checkout and order lifecycle]] ("Standalone payment buyer experience (9.2.2)"): the storefront theme/accent scoping and logo treatment reused as-is, the policy-exact amount/customer form, QR/copy, capability polling with retry, every terminal and failure view, and the return-to-store link, with the token-check whitelist extended by exactly this one route. The run-bound `standalone-payment:evidence` / `:verify` pair binds the themed grid and every state capture against seeded rows with zero provider calls.

## Out of scope

- The public `/store/[slug]` page, its rendering fallbacks, and product/link eligibility belong to Phase 5.2.
- Checkout `/pay/[identifier]` pages keep the platform design system; owner accent colors never reach them.

## Open

- Resolved by the delivered page (5.2/9.1.2): when the visitor's locale has no stored display name, the public page renders the localized generic fallback name ("QR Pagamentos storefront" / "Vitrine QR Pagamentos"); there is no cross-locale display-name fallback.
