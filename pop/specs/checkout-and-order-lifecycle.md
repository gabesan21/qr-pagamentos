## What it covers

This spec defines the durable owner, customer-data, and payment-state contract for payment-link checkout and resulting orders. Provider transport details remain in the Nautt integration spec.

## Requirements

- Every product, payment link, and link-generated order has one persisted owner account. A payment link may reference only a product with the same persisted owner; persistence and server operations reject an owner mismatch. An authenticated account may access only its own products, links, checkout policy, and orders. Administrator authority over users, global settings/catalog, and protected order inspection does not create an implicit cross-owner product or payment-link management path; public access is limited to an active link's checkout and its opaque payment-status capability.
- The account-level checkout data policy defaults to `NONE`. The only supported policies are `NONE`, `NAME_EMAIL`, `EMAIL`, `NAME_EMAIL_CPF`, and `NAME_EMAIL_CPF_ADDRESS`.
- Public checkout renders and validates exactly the fields required by the link owner's policy. Trusted server state, rather than browser input, determines the owner, products, currency, amount, policy, and provider credential.
- A link-generated order persists the payment-link identity, owner identity, amount and currency values used for the provider attempt, the policy applied, and the customer data accepted for that attempt.
- Customer data is available only to the order owner and administrators through protected interfaces. It is not included in public status responses, payment-link resolution responses, logs, or URLs.
- **Customer snapshot V1:** an order has exactly four customer members: nullable `name`, nullable `email`, nullable `cpf`, and nullable `address`. The policy tuple is exact: `NONE = (null, null, null, null)`; `NAME_EMAIL = (name, email, null, null)`; `EMAIL = (null, email, null, null)`; `NAME_EMAIL_CPF = (name, email, cpf, null)`; and `NAME_EMAIL_CPF_ADDRESS = (name, email, cpf, address)`. Every non-null member is required; no policy accepts an additional customer field.
- **Name, email, and CPF normalization:** `name` is Unicode NFC, trimmed of leading/trailing Unicode whitespace, 1–160 Unicode code points, and contains no control character. `email` is Unicode NFC, trimmed, 3–254 Unicode code points, contains no Unicode whitespace or control character, and has one non-empty local part and domain separated by `@`; its case is preserved. `cpf` accepts only the usual formatted or unformatted Brazilian CPF input, is persisted as exactly 11 ASCII digits, and must pass the CPF check-digit validation. Blank or malformed input is rejected; fields are never silently invented or coerced.
- **Brazil address V1:** `address` is a fixed structured snapshot, not free-form JSON, with required `street`, `number`, `district`, `city`, `stateUf`, `postalCode`, and `country`, plus optional nullable `complement`. `street` is 1–160, `number` 1–32, `district` 1–120, `city` 1–120, and `complement` 1–160 Unicode code points when supplied. These text members are NFC-normalized, trimmed, and reject control characters; blank optional `complement` becomes `null`. `stateUf` is persisted uppercase and must be one of the 27 Brazilian UFs (`AC`, `AL`, `AP`, `AM`, `BA`, `CE`, `DF`, `ES`, `GO`, `MA`, `MT`, `MS`, `MG`, `PA`, `PB`, `PR`, `PE`, `PI`, `RJ`, `RN`, `RS`, `RO`, `RR`, `SC`, `SP`, `SE`, `TO`). `postalCode` accepts only `NNNNNNNN` or `NNNNN-NNN`, and is persisted as eight ASCII digits. `country` is the literal persisted value `BR`. Limits apply after normalization. The persisted model has fixed members/columns only: no opaque address blob, unknown key, or future country is permitted without a new approved contract.
- Customer snapshots, including every address member, are never publicly exposed, provider-facing, logged, or placed in a URL. They may be selected only by a future re-authorized owner/administrator projection.
- The only public checkout mutation is the unlocalized, sessionless, dynamic `POST /api/payment-links/[identifier]/checkout`, always `Cache-Control: no-store`. It accepts only JSON `{ idempotencyKey, customer }`: a syntactically bounded opaque client retry key and an exact policy-valid `CustomerSnapshotV1`; it never accepts a browser owner, price, currency/provider UUID, credential, link/order identity, or status. Before JSON parsing or checkout work, the bounded single-process public API limiter may return only an empty no-store `429`. Invalid request shape/snapshot is an empty no-store `400`; every malformed, missing, inactive, expired, or otherwise unavailable trusted-link state is one indistinguishable empty no-store `404`; redacted pre-dispatch provider unavailability is an empty no-store `503`.
- The checkout operation derives and locks the active same-owner link/product/policy, canonical amount and pair snapshots, and owner credential from persisted server state. It persists no raw client retry key: a key-held server digest creates a durable unique `(payment_link_id, retry_key_verifier)` attempt. The reservation also stores a keyed verifier of the exact canonical accepted request (persisted link identity, retry key, contract version, policy snapshot, and normalized `CustomerSnapshotV1`), never its serialized request body. Thus the same canonical request is the only public replay that can bind to that attempt; a reused key with a policy-valid changed customer payload or another link identifier gets the indistinguishable empty no-store `404` and never a capability or attempt data. Independently malformed or policy-invalid input remains the normal empty no-store `400`, regardless of whether the retry key was ever used. One short transaction records the active-link snapshot, request/key verifiers, capability state, and reservation; after its one quote, a second short transaction claims that quote and attaches the same-owner local provider order before provider dispatch. No transaction spans provider I/O. A `SINGLE_USE` link remains available until the existing atomic authoritative confirmation claim; pending, rejected, cancelled, expired, failed-to-start, and indeterminate attempts never consume it.
- Checkout makes one trusted quote and exactly one `POST /orders/onramp` for a committed attempt; it never retries after dispatch or depends on provider idempotency. A complete result makes the local payment-link order `PENDING`; every post-dispatch ambiguity is durably `INDETERMINATE`. A durable known provider UUID may use only the existing one-read owner-bound authoritative recovery/reconciliation seam; unknown UUID ambiguity remains manual and never authorizes another POST.
- On creation, the same transaction gives the attempt a cryptographically random server-only capability derivation nonce, capability-key version, expiry, and verifier. The raw `statusCapability` is never persisted: it is deterministically re-derived from that nonce, the immutable attempt identity and expiry, and the retained server key for the recorded version, then checked/stored only as a verifier. Key material for a recorded version remains available only until its last unexpired capability. This lets an identical request safely receive the same bearer after a restart without storing or logging it; the nonce alone is not a bearer and cannot derive one without the server key.
- The public accepted response is only `{ payment: { state, pixCopyPaste?, pixQrCodeUrl? }, statusCapability }`: QR fields are the existing normalized optional provider fields, and `statusCapability` is a high-entropy opaque bearer value stored only as a verifier. `201` represents a complete pending capability and `202` represents the same request-bound attempt still creating or indeterminate. A duplicate or concurrent identical submission reads the fenced reservation and may re-derive and return that exact response, but it never quotes, attaches, dispatches, recovers, or re-POSTs Nautt. The capability is reissued only while its persisted expiry is in the future, its revocation marker is unset, and the source link is still active and unexpired; expiry is `min(link expiry when present, reservation time + 24 hours)`. Disabling or expiring a link prevents reissue, and any explicit future owner-side capability revocation must set the marker atomically. Expired/revoked/mismatched attempts produce no capability and no public state distinction. It includes no customer member, local/provider/owner/link identifier, provider envelope, key, or error; capability, retry key, verifiers, nonce, and canonical request data never appear in logs, URLs, errors, or cacheable responses.
- Task 4.2.2 adds only the unlocalized sessionless page `/pay/[identifier]` and `POST /api/payment-links/[identifier]/checkout/status`, always dynamic and `Cache-Control: no-store`. The page's server-only presentation projection is exactly `{ product: { title, description, price }, checkoutPolicy }`, where `checkoutPolicy` is one of `NONE`, `NAME_EMAIL`, `EMAIL`, `NAME_EMAIL_CPF`, or `NAME_EMAIL_CPF_ADDRESS`; an unavailable identifier/state renders one generic unavailable view. Before JSON parsing or status work, the bounded single-process public API limiter may return only an empty no-store `429`. The status request accepts only JSON `{ statusCapability }`; a successful `200` is exactly `{ payment: { state, pixCopyPaste?, pixQrCodeUrl? } }`, with `state` limited to `CREATED`, `PENDING`, `INDETERMINATE`, `CONFIRMED`, `REJECTED`, `CANCELLED`, `EXPIRED`, or `REFUNDED`. It validates the raw bearer only by the recorded capability-key version's re-derived verifier, immutable attempt binding, future expiry, and unset revocation marker; it performs no link lookup, recovery, provider call, or mutation. Invalid JSON is empty no-store `400`; every syntactically valid missing, mismatched, expired, revoked, or concurrent-loser capability outcome is the same empty no-store `404`. No success body includes any identifier, customer data, error, expiry, retry/verifier/nonce/key material, or state outside that closed vocabulary, so the route cannot become a status oracle.
- A single-use payment link is consumed only when one linked order reaches confirmed successful payment. Pending, failed, cancelled, or indeterminate attempts do not consume it.
- An expired link cannot create a new checkout order. A reusable link accepts successful payments until the owner disables it or it expires.
- Concurrent settlement notifications cannot yield more than one successful order for a single-use link.
- **Settlement map V1:** this is a closed provider-to-local mapping based solely on an owner-bound authoritative `GET /orders/{uuid}` reconciliation already defined by the Nautt contract. Provider notification payloads, event names, recovered-history fields, and unknown provider status strings are not settlement evidence and cause no local transition. `new → PENDING`; `processing`, `paid`, and `finished → CONFIRMED`; `rejected → REJECTED`; `canceled → CANCELLED`; `expired → EXPIRED`; and `refunded → REFUNDED`. No other provider status is mapped. `CONFIRMED` is the only successful local state; only the three explicitly listed authoritative provider statuses may enter it.
- A reconciliation may apply this map only through one transaction that matches the attached provider order's owner, immutable provider UUID, observed reconciliation version, and current authoritative mapped status, then conditionally matches the local order's current version and eligible state. `CREATED` never reconciles because it has no attached provider order. `PENDING` and `INDETERMINATE` may move to `PENDING`, `CONFIRMED`, `REJECTED`, `CANCELLED`, or `EXPIRED`; `CONFIRMED` may move only to `REFUNDED`; all other terminal states are immutable. A version/current-state mismatch, an unattached or cross-owner provider order, an unknown status, or a losing single-use claim is a fenced no-op/opaque loser outcome, not a retry or alternate success. The successful mapping atomically records the one single-use claim before marking `CONFIRMED`; an already matching state is idempotent and never creates another claim.
- Task 4.1.2 creates persistence and the server-only reconciliation seam only. It makes no Nautt request and changes no polling, webhook, or recovery execution; a later task supplies those existing authoritative reads to this seam.

## Implemented slices

The page uses the persisted/default locale and cancels pending polls while hidden or unmounted.

## Commerce V2 orders, snapshots, comments, and local outcomes (additive contract — link slice delivered by 8.1.2; order slice delivered by 8.1.3)

The `payment_link_v2`/`payment_link_v2_line` link model this section references is **delivered** by task 8.1.2 (see [[specs/catalog-and-payment-links|Catalog and payment links]], Commerce V2 section), and the order slice is **delivered** by task 8.1.3: `order_v2`/`order_v2_line`, `order_comment_v2`, `order_local_outcome_v2`, `checkout_attempt_v2`, `payment_link_v2_single_use_settlement`, and the nullable `provider_order.order_v2_id` exist with the pinned constraints, indexes, and least-privilege grants; `src/orders/order-v2.ts` delivers owner `AD_HOC` creation, the server-only `LINK` creation seam, and the V2 settlement CAS with the atomic single-use claim; `src/orders/order-engagement-v2.ts` delivers comments and local outcomes; `src/orders/order-v2-view.ts` delivers the additive owner/admin projections; `POST /orders-v2` and `POST /orders-v2/[id]` are the owner mutation routes. The V2 link service's financial-edit gate now observes the real `checkout_attempt_v2` existence read. The V2 public checkout is **delivered** by 9.3.1 (checklist item 4: sessionless attempt reservation/replay/capability execution against a V2 link, in the dedicated section below). Every V1 guarantee in this spec is unchanged: V1 orders, checkout attempts, capabilities, the settlement map, and reconciliation CAS behave exactly as specified above, and no V1 row is ever mutated, wrapped, or migrated by Commerce V2. The link model this section references is defined by [[specs/catalog-and-payment-links|Catalog and payment links]] (Commerce V2 section).

- **Order sources.** A Commerce V2 order is a new record in a new `order_v2` table with a `source` vocabulary of exactly `LINK`, `AD_HOC`, or `STANDALONE` (the third value was settled and delivered by task 9.2.1 — an `AD_HOC` variant was rejected because `AD_HOC`'s pinned invariant is owner-only, stateless, and dispatch-free), immutable per row after creation and extensible only by a later approved additive contract. A `LINK` order is created only by the sessionless public checkout against an active, unexpired V2 link, under the same trusted-server-state discipline as V1. An `AD_HOC` order is created only by an authenticated owner through a re-authorized owner mutation (origin-guard first, empty `401`/`403`, opaque outcomes); under this contract it has no public/sessionless creation surface, no checkout attempt or capability, and no provider dispatch. A `STANDALONE` order is created only by the sessionless standalone checkout (9.2.1 section below) against an enabled storefront: it holds no link (`payment_link_v2_id` null), has no order lines, snapshots a fixed server-side bilingual description constant pair (never browser text), carries the V1 state vocabulary from `CREATED`, and reconciles under the settlement map V1. V1 `payment_link_order` rows are untouched and keep reading through the existing projections.
- **Monetary snapshot.** At creation the server derives and persists an immutable monetary snapshot on the order: for a `PRODUCT_LINES` link, one snapshot line per link line (product reference, quantity, and the canonical exact-decimal unit price at creation) plus the server-computed total; for a `FIXED_AMOUNT` link or an `AD_HOC` order, the bilingual description and the canonical amount. The currency pair is snapshotted as its two provider UUIDs, exactly as V1. All values are canonical positive ASCII decimal strings in the product-price grammar; totals are computed with exact-decimal arithmetic and never through JavaScript `Number`. The snapshot is never rewritten by later product/category/archival edits, link edits or version forks, deactivation, or deletion.
- **Customer snapshot policy.** V2 orders reuse the policy-exact `CustomerSnapshotV1` unchanged: the same four members, the same exact policy tuples, the same closed policy set, and the same normalization rules. A `LINK` order snapshots the link owner's account-level checkout data policy at checkout time, as V1 does; an `AD_HOC` order records the owner-chosen policy from the same closed set with exactly the matching tuple supplied by the owner. No new customer field and no policy outside the closed set is permitted, and the V1 exposure fences (never public, provider-facing, logged, or in a URL) apply unchanged.
- **Comment model.** An owner comment thread lives in a new append-only `order_comment_v2` table. Each comment carries its order identity, the author's principal identity (always the order's owner — administrators and customers never comment), a body of 1–2,000 Unicode code points (NFC, trimmed, internal line breaks preserved, control characters other than line breaks rejected), `created_at`, a nullable `edited_at`, and a version. Comments are appended, never deleted; a comment may be edited only by its author through expected-version CAS, which stamps `edited_at`. Comments are visible only to the order owner through the re-authorized owner projection and to administrators through the read-only global projection — never public, never logged, never in a URL.
- **Local operator outcome model.** Local finalize/cancel lives in a new append-only `order_local_outcome_v2` history: each entry carries the order identity, an outcome from the closed set `LOCAL_FINALIZED` | `LOCAL_CANCELLED`, an optional note (same text rules as comments, nullable), the actor principal identity (always the order's owner), and `created_at`. The current local outcome is the latest entry — there is no pointer update and no clear operation; appending supersedes. Entries are never edited or deleted, giving the audit trail by construction. Setting an outcome is a re-authorized owner mutation protected by CAS on the order's lifecycle version.
- **Precedence against authoritative Nautt state.** The settlement map V1 and the versioned reconciliation CAS remain the sole authority over the payment `state`; a local outcome never writes, overwrites, masks, or shadows `state`, and projections expose `state` and the current local outcome as separate fields. A local outcome never consumes a `SINGLE_USE` link, never blocks, alters, or falsifies reconciliation, and never attaches or modifies a provider order. A later authoritative reconciliation applies normally regardless of any local outcome (a locally cancelled order that later confirms becomes `CONFIRMED` with its local outcome still visible, and the owner may append a new outcome); a locally finalized order reconciles exactly as any other.
- **Order lifecycle vocabulary.** `LINK` and `STANDALONE` orders reuse the exact V1 closed state vocabulary (`CREATED`, `PENDING`, `INDETERMINATE`, `CONFIRMED`, `REJECTED`, `CANCELLED`, `EXPIRED`, `REFUNDED`), the settlement map V1, and the versioned CAS transition rules unchanged. `AD_HOC` orders as scoped by this contract carry no payment state (`state` is absent) and are not reconciled; their operator-facing lifecycle is exactly the local-outcome metadata above.
- **Attempt-binding generalization.** V2 link checkouts use a new `checkout_attempt_v2` table that preserves the V1 semantics verbatim: the unique `(payment_link_v2_id, retry_key_verifier)` reservation, the keyed verifier over the exact canonical accepted request, the capability nonce/key-version/expiry/verifier discipline, the two short transactions around one quote and one `POST /orders/onramp`, and the identical replay outcomes. The V1 `checkout_attempt` table and its `(payment_link_id, retry_key_verifier)` uniqueness are untouched, and no V1 fence is weakened. Under this contract `AD_HOC` orders create no attempts, capabilities, retries, or provider dispatch. Standalone checkouts (9.2.1) use the separate additive `standalone_checkout_attempt` table — the same reservation/replay/capability columns bound to `order_v2_id` (unique, composite owner-bound restrictive FK) with replay uniqueness keyed by `(owner_id, retry_key_verifier)`, because no link exists to namespace the retry key; reusing `checkout_attempt_v2` was impossible without dropping its non-null link FK, which the safe migration language cannot express. V2 single-use consumption extends the existing claim model to a new `payment_link_v2_single_use_settlement` table with the same atomic claim-before-`CONFIRMED` semantics.

## Commerce V2 persistence shape, index strategy, and compatibility fences

- **Migration shape — additive new tables plus one nullable additive column.** The inventory below uses only constructs the safe migration language expresses: `createTable` with typed columns, `addColumn` (nullable or with a typed constant default), `createIndex` over plain column lists, `addConstraint`/`validateConstraint` (primary key, unique, composite foreign key, and checks built from closed comparisons, boolean composition, null tests, and closed-set membership), and `grant`/`revoke`. Because the language admits no regex, function, or trigger, four invariants live at the service boundary instead of the database: the 24-character identifier format (the database keeps `VARCHAR(24)` plus uniqueness only), the canonical decimal grammar (the database keeps `TEXT` only), active-dependency enforcement (service-fenced serialization, never a trigger), and the `order_v2` source vocabulary with its link/state coherence (a closed-set check on `source` could never be dropped to admit a later additive source value, and a "present exactly when" check could never be relaxed, so the vocabulary and per-source link/state presence are service-fenced, not database checks). All `id` values and timestamps are application-supplied; no `gen_random_uuid()` or `CURRENT_TIMESTAMP` default is assumed. The inventory: `payment_link_v2` (id, unique identifier, owner FK, closed-set `composition_kind`, nullable bilingual description and amount required exactly when `FIXED_AMOUNT` — expressible as an or/null-test check, currency-pair FK, closed-set `link_type`, nullable expiry, active flag, CAS version, timestamps, `(id, owner_id)` uniqueness); `payment_link_v2_line` (composite owner-bound FKs to link and product, line position bounded 1–20 by check with per-link position uniqueness — together enforcing the one-to-twenty line count that a cross-row count check cannot express — quantity bounded 1–9,999 by check, per-link product uniqueness); `order_v2` (owner FK, `TEXT` `source` with the service-fenced closed vocabulary (currently exactly `LINK` | `AD_HOC`), nullable composite owner-bound FK to the link, nullable `state` with a closed-set check on non-null values only, lifecycle CAS version, immutable monetary snapshot columns including amount/currency-UUID pair/bilingual description, closed-set policy check, the same fixed customer columns as V1, nullable settled timestamp, `(id, owner_id)` uniqueness); `order_v2_line` (composite owner-bound FKs to order and product, line position bounded 1–20 by check, quantity check, unit price, per-order product and position uniqueness); `checkout_attempt_v2` (mirror of the V1 attempt columns rebound to V2 identities, with `(payment_link_v2_id, retry_key_verifier)` uniqueness); `payment_link_v2_single_use_settlement` (mirror of the V1 claim rebound to V2 identities); `order_comment_v2` (owner-bound order FK, author FK, body, version, created/edited timestamps); `order_local_outcome_v2` (owner-bound order FK, closed-set outcome, nullable note, actor FK, created timestamp); and on `provider_order` exactly one nullable `order_v2_id` column with a composite owner-bound FK and owner-scoped uniqueness. ## Sessionless standalone payment orders (9.2.1 — delivered)

This section settles the source-value question deferred by the Commerce V2 contract: standalone payments arrive as the third `order_v2.source` value `STANDALONE` with a dedicated `standalone_checkout_attempt` table, delivered server-side only (the buyer UI belongs to 9.2.2). Every V1 guarantee above is unchanged; no V1 module, table, DTO, or dispatch behavior is touched.

- **Routes.** Two unlocalized, dynamic, sessionless routes, always `Cache-Control: no-store`: `POST /api/store/[slug]/checkout` and `POST /api/store/[slug]/checkout/status`. They mirror the V1 checkout/status outcome matrix exactly: before JSON parsing or service work, the bounded single-process public limiter may return only an empty no-store `429` (new closed surfaces `standalone-checkout-submit` and `standalone-payment-status-poll`, burst/refill mirroring checkout and status); invalid JSON or shape is the empty no-store `400`; every unavailable outcome is one indistinguishable empty no-store `404`; redacted pre-dispatch provider unavailability is the empty no-store `503`; success is `201`/`202` `{ payment: { state, pixCopyPaste?, pixQrCodeUrl? }, statusCapability }` for checkout and `200 { payment: { state, pixCopyPaste?, pixQrCodeUrl? } }` with the closed V1 state vocabulary for the capability-only status route — never a status oracle. The origin guard never applies (sessionless). The server-request-log inventory gains exactly the two literal templates `/api/store/[slug]/checkout` and `/api/store/[slug]/checkout/status`.
- **Sessionless trust posture.** The browser supplies only the slug (path), an opaque retry key, the amount string, and the customer snapshot — body exactly `{ idempotencyKey, amount, customer }`; nothing else is accepted: no owner, currency, total, status, provider UUID, credential, or order identity. The amount is validated against the canonical product-price grammar (exact positive ASCII decimal, never `Number`) and snapshot-locked server-side. Owner, policy, currency pair, the fixed bilingual description constant pair, and expiry are derived from locked persisted state inside the reservation transaction (owner row `FOR UPDATE`; registry pair `FOR SHARE`).
- **Store-default-currency resolution and failure mode.** The slug resolves to an owner with `storefront_enabled AND storefront_standalone_payments_enabled`; the stored `storefront_default_currency_code` resolves through the registry's active-pointer seam (`supported_exchange_currency` → active `catalog_currency_pair`) to the pair's two provider UUIDs. Every failure — unknown or disabled slug, standalone toggle off, null stored code, deactivated mapping, inactive pair — is the one indistinguishable empty no-store `404`. There is never a `BRL`/other-code fallback; "a stored code survives later deactivation" is a reads-only rule and never applies to dispatch.
- **Retry fencing and capability.** Unique `(owner_id, retry_key_verifier)` reservation — the store owner is the retry namespace because no link exists. The keyed request verifier covers the canonical accepted request (contract version, owner identity, retry-key verifier, policy snapshot, validated amount, normalized `CustomerSnapshotV1`). An identical replay re-derives and returns the existing capability only while unexpired, unrevoked, and the storefront + standalone toggles are still enabled (the analog of the V1 link-active gate); a reused key with any changed payload is the opaque `404`. Replays perform zero quote/attach/dispatch/recovery. Capability TTL is reservation time + 24 hours (no link expiry exists). The raw capability is never persisted or logged, only its verifier.
- **Dispatch and state fencing.** Mirrors V1 verbatim: one short reservation transaction (order `CREATED` + attempt `RESERVED` with nonce/key-version/expiry/verifiers), a `markCreating` CAS, one quote, one `POST /orders/onramp` attached to the V2 order identity (the additive `provider_order.order_v2_id` attach — never reusing `payment_link_order_id`), `markPending` moving the order to `PENDING`; every post-dispatch ambiguity is durably `INDETERMINATE`, never retried, and no transaction spans provider I/O.
- **Settlement.** Webhook-driven only (poll/recover wiring deferred, no consumer): after the authoritative owner-bound GET reconciliation persists status/version, a provider order attached to `order_v2_id` settles the standalone order through the versioned CAS — no link join, no single-use claim — with exact observed identities/versions. The V1 settle path remains unwired (open question, below).
- **Read-side coherence.** The owner directory `source` filter admits `STANDALONE`; merchant analytics provider-confirmed sales are (`LINK` ∪ `STANDALONE`) `CONFIRMED` in-period while locally finalized stays `AD_HOC`-only (never merged); the funnel reads both attempt tables without double-counting; best-sellers and per-link metrics are untouched (standalone orders have no products or link); recent activity renders the new source through the existing summary projection.

## Public link terminal states (9.3.2 — delivered)

This section delivers the explicit terminal behavior of `/pay/[identifier]` for Commerce V2 links after payment, deactivation, expiry, or invalid access. Every V1 guarantee above is unchanged: the V1 render path, V1 consumed/unavailable semantics, and every V1 surface stay byte-frozen, and no route, rate-limit surface, or server-request-log inventory changed. `REUSABLE` links are never consumed and keep the normal checkout view.

- **Paid terminal view.** A consumed `SINGLE_USE` V2 link renders a server-rendered, branded, localized already-paid view through the same presentation read as the checkout branch, which now returns a discriminated outcome — checkout view, paid view, or the one opaque null. The page renders the paid view with no form, no polling client, and no mutation affordance.
- **Paid-view content boundary.** The paid DTO carries exactly: the owner's persisted branding (localized display name, logo media identifier, resolved theme with the design-system default, and validated accent — resolved from the owner record independent of `storefront_enabled`, exactly as the checkout branch), one explicit localized already-paid statement with a non-color marker (icon plus text), and the link's public composition summary (the localized product lines or the fixed bilingual description) with the exact-decimal total and the server-resolved display currency code (unmapped pair → the explicit localized unlabeled treatment). This content was already public to any identifier holder while the link was active; the only new disclosure is the single sanctioned bit "this link was consumed". The paid view never carries: order/payment state or any timestamp (including the claim's `claimedAt` and `orderV2Id`), refund state, customer/payer data, attempt/capability/verifier/retry material, provider data, currency-pair UUIDs, owner identity beyond the public display name/logo, the checkout policy, or link internals (state, version, expiry, active flag).
- **Claim-keyed consumption.** The paid branch reads only the persisted `payment_link_v2_single_use_settlement` claim — never a join or read of live order state. A later `REFUNDED` (or any order state change), owner deactivation, link expiry, or line-product deactivation never flips, annotates, or degrades the paid view; an unclaimed link keeps every 9.3.1 availability gate (active, unexpired, publicly active line products), and the opaque null still covers malformed, unknown, inactive, expired, line-product-unavailable, and missing-member outcomes as one indistinguishable view.
- **Evidence.** The `checkout:evidence`/`checkout:evidence:verify` pair extends to 127 captures: the 9.3.1 grid and states unchanged, plus the paid terminal grid (both composition kinds × six persisted themes × both locales × 375/768/1440), the unbranded paid view, and the inactive/expired opaque regressions. Claim-keying is proven at runtime: every consumed order is flipped to `REFUNDED` and one consumed link carries a past expiry before any paid capture, and the paid views persist unchanged.

## Standalone payment buyer experience (9.2.2 — delivered)

The sessionless `/store/[slug]/pay` page is the bilingual buyer experience on top of 9.2.1's routes: an unlocalized, `force-dynamic` App Router page with no new API route and no rate-limit/request-log inventory change. It resolves the persisted locale exactly like the storefront page, re-reads the public storefront projection, and renders the one opaque unavailable view (unknown/disabled slug or standalone payments off — the same null-projection outcome, unscoped, with the localized return-to-store link as the only affordance). Otherwise it scopes the resolved owner theme with `data-theme-preview` plus the validated `--storefront-accent` declaration (the token-check whitelist gains exactly this one route), renders the logo through `/media/[identifier]` or the official merchant-fallback lockup, and hands the journey to one focused client boundary. The storefront custom-amount item gains one pay action linking to `/store/[slug]/pay?amount=<draft>` — the query value is prefill only: it fills the draft only while it matches the canonical positive-decimal amount grammar, the client revalidates on submit, and 9.2.1 validates again server-side.

- **Trust posture.** The client never trusts browser owner, currency, total, or status: the submit body is exactly `{ idempotencyKey, amount, customer }`, validated client-side against the canonical amount grammar and the policy-exact required-field set, and the displayed amount fact is the buyer's own submitted draft labelled by `standalonePaymentCurrencyCode` (null → unlabeled), rendered as a canonical decimal string with tabular figures — never `Number`/`Intl` money math. The owner's checkout data policy reaches the form through the additive `checkoutDataPolicy` member of the public storefront projection (the deliberate 9.2.2 redaction-boundary amendment — the same public-safe exposure V1 already ships as `checkoutPolicy` through the sessionless presentation read; the server re-derives the policy from the locked owner row on every command, so the member never grants authority).
- **Client state union.** The closed client payment state set is exactly the union of 9.2.1's accept states (`RESERVED`, `CREATING`, `PENDING`, `INDETERMINATE`) and the V1 status vocabulary (`CREATED`, `PENDING`, `INDETERMINATE`, `CONFIRMED`, `REJECTED`, `CANCELLED`, `EXPIRED`, `REFUNDED`). `RESERVED`/`CREATING`/`CREATED` render the waiting treatment (the existing "preparing payment" label, never an error and never a destructive badge); the terminal set is the unchanged V1 one (`CONFIRMED` success badge versus the destructive failure badge for `REJECTED`/`CANCELLED`/`EXPIRED`/`REFUNDED`).
- **Polling, retry, and return semantics.** Polling reuses V1's exported polling controller unchanged: 5-second interval, visibility-aware pause, `1s·2^n` backoff, three consecutive failures surfacing the localized status error with a manual retry, and any `404` (submit, poll, or expired capability) collapsing to the one opaque unavailable view; `503`/network submit failures keep the form behind one opaque retryable error that reuses the same idempotency key. The localized return-to-store link is present on the initial, waiting, failure, and terminal views. The run-bound `standalone-payment:evidence` contract binds six themes × two locales × 375/768/1440 plus state captures (prefill, amount/policy variants, waiting, QR/copy, polling status error with manual retry, CONFIRMED and destructive terminals, expired capability, opaque submit failure, unavailable, standalone off, 320px reflow) against seeded attempt/order/provider rows whose capability HMAC the harness computes from its own disposable key — polling exercises the real capability verification path with zero provider calls, and live submit → provider dispatch stays covered by 9.2.1's route tests.

## Storefront one-time link issuance (9.1.3 — delivered)

The sessionless storefront cart command (`POST /api/store/[slug]/cart/checkout`, defined in [[specs/storefront-and-customization|Storefront and customization]]) issues one active `SINGLE_USE` `PRODUCT_LINES` Commerce V2 link per accepted product-only cart, owned by the storefront owner and built only from locked server state. Issuance is link creation only: it creates no `order_v2`, no `checkout_attempt_v2`, no capability, and no provider dispatch, and it never settles or consumes anything. Every lifecycle invariant of this contract applies to the issued row unchanged — the immutable composition/pair/type, the service-fenced active-dependency enforcement at creation, the read-time expiry/lifecycle derivation, and the single-use claim recorded only when one linked order reaches confirmed successful payment. The public V2 checkout execution that consumes these links (attempt reservation, order creation, provider dispatch) remains task 9.3.1's boundary; until it lands, the issued identifier renders the generic unavailable view on `/pay/[identifier]`.

## Merchant analytics definitions (8.4.1)

This section pins the durable business definitions behind the owner-scoped merchant analytics projection delivered by `src/orders/merchant-analytics.ts` (one re-authorized active-`USER` read; server-only, no HTTP route — task 8.4.2's dashboard server component consumes the service directly; administrator/global analytics stays with 10.1.1, which reuses the definitions below globally as pinned in [[specs/administrative-foundation|Administrative foundation]] ("Administrator analytics definitions (10.1.1)") while this projection stays owner-scoped and unchanged by that reuse). The projection reads Commerce V2 data only: V1 tables are never read, V1 remains frozen, and the exclusion holds by definition rather than by filter. Every definition below is reproducible from persisted fields alone; no definition ever requires a provider call.

- **Reporting timezone and closed periods.** One fixed reporting timezone, `America/Sao_Paulo` (DST-free since 2019, so an exact UTC−03:00 offset; deterministic, never owner-configurable, never derived from browser data). The period set is closed: `today` (the current calendar day so far), `7d` (the last 7 calendar days including today), and `30d` (the last 30 calendar days including today). Each period is calendar-day aligned in the reporting timezone and materializes server-side as exact half-open UTC bounds `[from, to)` — `to` is always the start of the next reporting day, so "so far" needs no special case. A period outside the closed set is the typed invalid-period outcome and performs no reads.
- **Sales volume — two members, never merged.** Provider-confirmed sales are `LINK` and `STANDALONE` orders (the union since 9.2.1) with `state = CONFIRMED` and `settled_at` inside the period bounds. Locally finalized sales are `AD_HOC` orders whose current local outcome (the latest `order_local_outcome_v2` entry) is `LOCAL_FINALIZED` with that entry's `created_at` inside the period bounds. The two members are computed, exposed, and consumed separately — never summed, netted, or otherwise merged — preserving the fence that a local outcome never writes, masks, or shadows the authoritative `state`. Every monetary sum groups by the order's snapshotted `(currency_uuid, exchange_currency_uuid)` pair and accumulates canonical decimal amounts as BigInt micro-units (10^6), never through JavaScript `Number` and never across currency groups. Currency groups are ordered by amount descending, then redacted code ascending (absent code last), then the internal pair identity ascending (never exposed).
- **Currency labels.** A currency group is labeled only through the durable registry read-only: the `supported_exchange_currency` pointer code plus the `catalog_currency_pair` label for the snapshotted pair; a snapshotted pair with no current pointer exposes a null code with the pair label, and an unmatched pair fails closed to null code and null label. Provider UUIDs never appear in the DTO.
- **Funnel — conversion and abandonment.** The funnel is defined over the owner's `checkout_attempt_v2` and `standalone_checkout_attempt` rows (both tables since 9.2.1; each order is attempt-bound in exactly one of them, so the union never double-counts) created inside the period bounds, classified only from the persisted `created_at`, `capability_expires_at`, and the bound order's `state`: converted = the attempt's bound order reached `CONFIRMED`; abandoned = not converted and `capability_expires_at` at or before the read instant; in-progress = the remainder. In-progress attempts are excluded from both rate denominators: conversion rate = converted / (converted + abandoned), abandonment rate = abandoned / (converted + abandoned), each an exact-decimal string truncated to four fraction digits and null when its denominator is zero.
- **Best sellers.** A bounded top-5 by confirmed quantity: the sum of `order_v2_line` snapshot quantities per product over in-period provider-confirmed orders, with per-currency-group revenue computed as exact-decimal `quantity × unit_price` sums under the monetary rules above. Ordering is quantity descending with a deterministic tie-break on internal product identity (never exposed). Bilingual titles come from the current same-owner `product` rows; archived or deactivated products still appear, because the revenue and quantity come from the immutable order-line snapshots.
- **Per-link metrics.** Over the owner's V2 payment links only: attempts created in period, provider-confirmed orders settled in period, and confirmed volume per currency group, exposed for every link with in-period activity (attempts or confirmed orders), ordered by confirmed orders descending, attempts descending, then the public-safe 24-character identifier ascending. The active-link count covers all of the owner's V2 links regardless of period activity.
- **Recent activity.** A bounded (5) most-recent owner order feed reusing the `order-v2-view.ts` summary semantics, redacted to source, bilingual description, amount, the redacted currency label, `state`, the current local outcome, `created_at`/`settled_at`, and the public-safe link identifier.
- **Redaction and scoping fences.** Every read re-authorizes the active `USER` principal and filters `owner_id` server-side. The DTO carries aggregates, counts, rates, bilingual labels, redacted currency labels, and 24-character link identifiers only — never customer snapshot members, order/attempt/link/product internal UUIDs, retry keys, verifiers, capability/nonce/key material, or provider data. There is no administrator or global entry point, no mutation, and no pagination beyond the pinned bounds.
