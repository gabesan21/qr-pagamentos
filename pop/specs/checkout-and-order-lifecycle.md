## What it covers

This spec defines the durable owner, customer-data, and payment-state contract for payment-link checkout and resulting orders. Provider transport details remain in the Nautt integration spec.

## Requirements

- Every product, payment link, and link-generated order has one persisted owner account. A payment link may reference only a product with the same persisted owner; persistence and server operations reject an owner mismatch. An authenticated account may access only its own products, links, checkout policy, and orders. Administrator authority over users, global settings/catalog, and protected order inspection does not create an implicit cross-owner product or payment-link management path; public access is limited to an active link's checkout and its opaque payment-status capability.
- The account-level checkout data policy defaults to `NONE`. The only supported policies are `NONE`, `NAME_EMAIL`, `EMAIL`, `NAME_EMAIL_CPF`, and `NAME_EMAIL_CPF_ADDRESS`.
- Public checkout renders and validates exactly the fields required by the link owner's policy. Trusted server state, rather than browser input, determines the owner, products, currency, amount, policy, and provider credential.
- A link-generated order persists the payment-link identity, owner identity, amount and currency values used for the provider attempt, the policy applied, and the customer data accepted for that attempt.
- Customer data is available only to the order owner and administrators through protected interfaces. It is not included in public status responses, payment-link resolution responses, logs, or URLs.
- **Customer snapshot V1:** an order has exactly four customer members: nullable `name`, nullable `email`, nullable `cpf`, and nullable `address`. The policy tuple is exact: `NONE = (null, null, null, null)`; `NAME_EMAIL = (name, email, null, null)`; `EMAIL = (null, email, null, null)`; `NAME_EMAIL_CPF = (name, email, cpf, null)`; and `NAME_EMAIL_CPF_ADDRESS = (name, email, cpf, address)`. Every non-null member is required; no policy accepts an additional customer field.
- **Name, email, and CPF normalization:** `name` is Unicode NFC, trimmed of leading/trailing Unicode whitespace, 1–160 Unicode code points, and contains no control character. `email` is Unicode NFC, trimmed, 3–254 Unicode code points, contains no Unicode whitespace or control character, and has one non-empty local part and domain separated by `@`; its case is preserved. `cpf` accepts only the usual formatted or unformatted Brazilian CPF input, is persisted as exactly 11 ASCII digits, and must pass the CPF check-digit validation. Blank or malformed input is rejected; fields are never silently invented or coerced.
- **Brazil address V1:** `address` is a fixed structured snapshot, not free-form JSON, with required `street`, `number`, `district`, `city`, `stateUf`, `postalCode`, and `country`, plus optional nullable `complement`. `street` is 1–160, `number` 1–32, `district` 1–120, `city` 1–120, and `complement` 1–160 Unicode code points when supplied. These text members are NFC-normalized, trimmed, and reject control characters; blank optional `complement` becomes `null`. `stateUf` is persisted uppercase and must be one of the 27 Brazilian UFs (`AC`, `AL`, `AP`, `AM`, `BA`, `CE`, `DF`, `ES`, `GO`, `MA`, `MT`, `MS`, `MG`, `PA`, `PB`, `PR`, `PE`, `PI`, `RJ`, `RN`, `RS`, `RO`, `RR`, `SC`, `SP`, `SE`, `TO`). `postalCode` accepts only `NNNNNNNN` or `NNNNN-NNN`, and is persisted as eight ASCII digits. `country` is the literal persisted value `BR`. Limits apply after normalization. The persisted model has fixed members/columns only: no opaque address blob, unknown key, or future country is permitted without a new approved contract.
- Customer snapshots, including every address member, are never publicly exposed, provider-facing, logged, or placed in a URL. They may be selected only by a future re-authorized owner/administrator projection.
- The only public checkout mutation is the unlocalized, sessionless, dynamic `POST /api/payment-links/[identifier]/checkout`, always `Cache-Control: no-store`. It accepts only JSON `{ idempotencyKey, customer }`: a syntactically bounded opaque client retry key and an exact policy-valid `CustomerSnapshotV1`; it never accepts a browser owner, price, currency/provider UUID, credential, link/order identity, or status. Before JSON parsing or checkout work, the bounded single-process public API limiter may return only an empty no-store `429`. Invalid request shape/snapshot is an empty no-store `400`; every malformed, missing, inactive, expired, or otherwise unavailable trusted-link state is one indistinguishable empty no-store `404`; redacted pre-dispatch provider unavailability is an empty no-store `503`.
- The checkout operation derives and locks the active same-owner link/product/policy, canonical amount and pair snapshots, and owner credential from persisted server state. It persists no raw client retry key: a key-held server digest creates a durable unique `(payment_link_id, retry_key_verifier)` attempt. The reservation also stores a keyed verifier of the exact canonical accepted request (persisted link identity, retry key, contract version, policy snapshot, and normalized `CustomerSnapshotV1`), never its serialized request body. Thus the same canonical request is the only public replay that can bind to that attempt; a reused key with a policy-valid changed customer payload or another link identifier gets the indistinguishable empty no-store `404` and never a capability or attempt data. Independently malformed or policy-invalid input remains the normal empty no-store `400`, regardless of whether the retry key was ever used. One short transaction records the active-link snapshot, request/key verifiers, capability state, and reservation; after its one quote, a second short transaction claims that quote and attaches the same-owner local provider order before provider dispatch. No transaction spans provider I/O. A `SINGLE_USE` link remains available until the existing atomic authoritative confirmation claim; pending, rejected, cancelled, expired, failed-to-start, and indeterminate attempts never consume it.
- Checkout makes one trusted quote and exactly one `POST /orders/onramp` for a committed attempt; it never retries after dispatch or depends on provider idempotency. A complete result makes the local payment-link order `PENDING`; every post-dispatch ambiguity is durably `INDETERMINATE`. A durable known provider UUID may use only the existing one-read owner-bound authoritative recovery/reconciliation seam; unknown UUID ambiguity remains manual and never authorizes another POST.
- On creation, the same transaction gives the attempt a cryptographically random server-only capability derivation nonce, capability-key version, expiry, and verifier. The raw `statusCapability` is never persisted: it is deterministically re-derived from that nonce, the immutable attempt identity and expiry, and the retained server key for the recorded version, then checked/stored only as a verifier. Key material for a recorded version remains available only until its last unexpired capability. This lets an identical request safely receive the same bearer after a restart without storing or logging it; the nonce alone is not a bearer and cannot derive one without the server key.
- The public accepted response is only `{ payment: { state, pixCopyPaste?, pixQrCodeUrl? }, statusCapability }`: QR fields are the existing normalized optional provider fields, and `statusCapability` is a high-entropy opaque bearer value stored only as a verifier. `201` represents a complete pending capability and `202` represents the same request-bound attempt still creating or indeterminate. A duplicate or concurrent identical submission reads the fenced reservation and may re-derive and return that exact response, but it never quotes, attaches, dispatches, recovers, or re-POSTs Nautt. The capability is reissued only while its persisted expiry is in the future, its revocation marker is unset, and the source link is still active and unexpired; expiry is `min(link expiry when present, reservation time + 24 hours)`. Disabling or expiring a link prevents reissue, and any explicit future owner-side capability revocation must set the marker atomically. Expired/revoked/mismatched attempts produce no capability and no public state distinction. It includes no customer member, local/provider/owner/link identifier, provider envelope, key, or error; capability, retry key, verifiers, nonce, and canonical request data never appear in logs, URLs, errors, or cacheable responses.
- Task 4.2.2 adds only the unlocalized sessionless page `/pay/[identifier]` and `POST /api/payment-links/[identifier]/checkout/status`, always dynamic and `Cache-Control: no-store`. The page's server-only presentation projection is exactly `{ product: { title, description, price }, checkoutPolicy }`, where `checkoutPolicy` is one of `NONE`, `NAME_EMAIL`, `EMAIL`, `NAME_EMAIL_CPF`, or `NAME_EMAIL_CPF_ADDRESS`; an unavailable identifier/state renders one generic unavailable view. Before JSON parsing or status work, the bounded single-process public API limiter may return only an empty no-store `429`. The status request accepts only JSON `{ statusCapability }`; a successful `200` is exactly `{ payment: { state, pixCopyPaste?, pixQrCodeUrl? } }`, with `state` limited to `CREATED`, `PENDING`, `INDETERMINATE`, `CONFIRMED`, `REJECTED`, `CANCELLED`, `EXPIRED`, or `REFUNDED`. It validates the raw bearer only by the recorded capability-key version's re-derived verifier, immutable attempt binding, future expiry, and unset revocation marker; it performs no link lookup, recovery, provider call, or mutation. Invalid JSON is empty no-store `400`; every syntactically valid missing, mismatched, expired, revoked, or concurrent-loser capability outcome is the same empty no-store `404`. No success body includes any identifier, customer data, error, expiry, retry/verifier/nonce/key material, or state outside that closed vocabulary, so the route cannot become a status oracle.
- A single-use payment link is consumed only when one linked order reaches confirmed successful payment. Pending, failed, cancelled, or indeterminate attempts do not consume it.
- An expired link cannot create a new checkout order. A reusable link accepts successful payments until the owner disables it or it expires.
- Concurrent settlement notifications cannot yield more than one successful order for a single-use link.
- **Settlement map V1:** this is a closed provider-to-local mapping based solely on an owner-bound authoritative `GET /orders/{uuid}` reconciliation already defined by the Nautt contract. Provider notification payloads, event names, recovered-history fields, and unknown provider status strings are not settlement evidence and cause no local transition. `new → PENDING`; `processing`, `paid`, and `finished → CONFIRMED`; `rejected → REJECTED`; `canceled → CANCELLED`; `expired → EXPIRED`; and `refunded → REFUNDED`. No other provider status is mapped. `CONFIRMED` is the only successful local state; only the three explicitly listed authoritative provider statuses may enter it.
- A reconciliation may apply this map only through one transaction that matches the attached provider order's owner, immutable provider UUID, observed reconciliation version, and current authoritative mapped status, then conditionally matches the local order's current version and eligible state. `CREATED` never reconciles because it has no attached provider order. `PENDING` and `INDETERMINATE` may move to `PENDING`, `CONFIRMED`, `REJECTED`, `CANCELLED`, or `EXPIRED`; `CONFIRMED` may move only to `REFUNDED`; all other terminal states are immutable. A version/current-state mismatch, an unattached or cross-owner provider order, an unknown status, or a losing single-use claim is a fenced no-op/opaque loser outcome, not a retry or alternate success. The successful mapping atomically records the one single-use claim before marking `CONFIRMED`; an already matching state is idempotent and never creates another claim.
- Task 4.1.2 creates persistence and the server-only reconciliation seam only. It makes no Nautt request and changes no polling, webhook, or recovery execution; a later task supplies those existing authoritative reads to this seam.

## Implemented slices

- **Task 4.3.1:** The server-only `src/orders/order-view.ts` projection is the single re-authorized seam through which order data leaves persistence: a bounded most-recent owner list/detail and a global administrator list/detail. It exposes only order identity, payment-link identifier, bilingual product title, amount/currency-pair label, state, lifecycle timestamps, applied policy, and the exact policy-shaped `CustomerSnapshotV1` — never verifiers, nonce, key material, or provider data. Cross-owner, malformed, and missing order identities share one opaque "unavailable" outcome. A persisted `checkoutDataPolicy` outside the closed enum exposes no customer data: the projection fails closed to the all-null `CustomerSnapshotV1`. The bilingual `/orders` owner views and read-only `/admin/orders` views re-resolve the cookie principal on every read and hold no mutation surface.
- **Task 4.2.2:** Bilingual `/pay/[identifier]` renders the redacted product and only the policy-required customer fields, submits the opaque checkout request, presents QR/copy-paste data, and polls the capability-bound status endpoint without exposing order or customer data. The page uses the persisted/default locale and cancels pending polls while hidden or unmounted.

## Commerce V2 orders, snapshots, comments, and local outcomes (additive contract — link slice delivered by 8.1.2; order slice delivered by 8.1.3)

The `payment_link_v2`/`payment_link_v2_line` link model this section references is **delivered** by task 8.1.2 (see [[specs/catalog-and-payment-links|Catalog and payment links]], Commerce V2 section), and the order slice is **delivered** by task 8.1.3: `order_v2`/`order_v2_line`, `order_comment_v2`, `order_local_outcome_v2`, `checkout_attempt_v2`, `payment_link_v2_single_use_settlement`, and the nullable `provider_order.order_v2_id` exist with the pinned constraints, indexes, and least-privilege grants; `src/orders/order-v2.ts` delivers owner `AD_HOC` creation, the server-only `LINK` creation seam, and the V2 settlement CAS with the atomic single-use claim; `src/orders/order-engagement-v2.ts` delivers comments and local outcomes; `src/orders/order-v2-view.ts` delivers the additive owner/admin projections; `POST /orders-v2` and `POST /orders-v2/[id]` are the owner mutation routes. The V2 link service's financial-edit gate now observes the real `checkout_attempt_v2` existence read. What remains undelivered is the V2 public checkout itself (checklist item 4: sessionless attempt reservation/replay/capability execution against a V2 link), which stays with 9.3.1 — no V2 public/sessionless route exists. Every V1 guarantee in this spec is unchanged: V1 orders, checkout attempts, capabilities, the settlement map, and reconciliation CAS behave exactly as specified above, and no V1 row is ever mutated, wrapped, or migrated by Commerce V2. The link model this section references is defined by [[specs/catalog-and-payment-links|Catalog and payment links]] (Commerce V2 section).

- **Order sources.** A Commerce V2 order is a new record in a new `order_v2` table with a `source` vocabulary of exactly `LINK` or `AD_HOC` under this contract, immutable per row after creation and extensible only by a later approved additive contract (task 9.2.1 is the known first candidate). A `LINK` order is created only by the sessionless public checkout against an active, unexpired V2 link, under the same trusted-server-state discipline as V1. An `AD_HOC` order is created only by an authenticated owner through a re-authorized owner mutation (origin-guard first, empty `401`/`403`, opaque outcomes); under this contract it has no public/sessionless creation surface, no checkout attempt or capability, and no provider dispatch. Sessionless standalone payment orders — direct order reservation, provider dispatch, replay/timeout fencing, and opaque capability polling without a link record — are an approved roadmap extension explicitly deferred to task 9.2.1, which will settle whether they arrive as a third source value or an `AD_HOC` variant admitting attempts, capabilities, provider dispatch, payment state, and reconciliation under the V1 sessionless fences. This contract deliberately leaves that extension open: nothing below encodes the current owner-only scope in a way the safe migration language could not relax additively. V1 `payment_link_order` rows are untouched and keep reading through the existing projections.
- **Monetary snapshot.** At creation the server derives and persists an immutable monetary snapshot on the order: for a `PRODUCT_LINES` link, one snapshot line per link line (product reference, quantity, and the canonical exact-decimal unit price at creation) plus the server-computed total; for a `FIXED_AMOUNT` link or an `AD_HOC` order, the bilingual description and the canonical amount. The currency pair is snapshotted as its two provider UUIDs, exactly as V1. All values are canonical positive ASCII decimal strings in the product-price grammar; totals are computed with exact-decimal arithmetic and never through JavaScript `Number`. The snapshot is never rewritten by later product/category/archival edits, link edits or version forks, deactivation, or deletion.
- **Customer snapshot policy.** V2 orders reuse the policy-exact `CustomerSnapshotV1` unchanged: the same four members, the same exact policy tuples, the same closed policy set, and the same normalization rules. A `LINK` order snapshots the link owner's account-level checkout data policy at checkout time, as V1 does; an `AD_HOC` order records the owner-chosen policy from the same closed set with exactly the matching tuple supplied by the owner. No new customer field and no policy outside the closed set is permitted, and the V1 exposure fences (never public, provider-facing, logged, or in a URL) apply unchanged.
- **Comment model.** An owner comment thread lives in a new append-only `order_comment_v2` table. Each comment carries its order identity, the author's principal identity (always the order's owner — administrators and customers never comment), a body of 1–2,000 Unicode code points (NFC, trimmed, internal line breaks preserved, control characters other than line breaks rejected), `created_at`, a nullable `edited_at`, and a version. Comments are appended, never deleted; a comment may be edited only by its author through expected-version CAS, which stamps `edited_at`. Comments are visible only to the order owner through the re-authorized owner projection and to administrators through the read-only global projection — never public, never logged, never in a URL.
- **Local operator outcome model.** Local finalize/cancel lives in a new append-only `order_local_outcome_v2` history: each entry carries the order identity, an outcome from the closed set `LOCAL_FINALIZED` | `LOCAL_CANCELLED`, an optional note (same text rules as comments, nullable), the actor principal identity (always the order's owner), and `created_at`. The current local outcome is the latest entry — there is no pointer update and no clear operation; appending supersedes. Entries are never edited or deleted, giving the audit trail by construction. Setting an outcome is a re-authorized owner mutation protected by CAS on the order's lifecycle version.
- **Precedence against authoritative Nautt state.** The settlement map V1 and the versioned reconciliation CAS remain the sole authority over the payment `state`; a local outcome never writes, overwrites, masks, or shadows `state`, and projections expose `state` and the current local outcome as separate fields. A local outcome never consumes a `SINGLE_USE` link, never blocks, alters, or falsifies reconciliation, and never attaches or modifies a provider order. A later authoritative reconciliation applies normally regardless of any local outcome (a locally cancelled order that later confirms becomes `CONFIRMED` with its local outcome still visible, and the owner may append a new outcome); a locally finalized order reconciles exactly as any other.
- **Order lifecycle vocabulary.** `LINK` orders reuse the exact V1 closed state vocabulary (`CREATED`, `PENDING`, `INDETERMINATE`, `CONFIRMED`, `REJECTED`, `CANCELLED`, `EXPIRED`, `REFUNDED`), the settlement map V1, and the versioned CAS transition rules unchanged. `AD_HOC` orders as scoped by this contract carry no payment state (`state` is absent) and are not reconciled; their operator-facing lifecycle is exactly the local-outcome metadata above. Task 9.2.1's sessionless standalone orders will carry payment state and reconcile under the settlement map V1, and this vocabulary admits that extension without redefining any existing term.
- **Attempt-binding generalization.** V2 link checkouts use a new `checkout_attempt_v2` table that preserves the V1 semantics verbatim: the unique `(payment_link_v2_id, retry_key_verifier)` reservation, the keyed verifier over the exact canonical accepted request, the capability nonce/key-version/expiry/verifier discipline, the two short transactions around one quote and one `POST /orders/onramp`, and the identical replay outcomes. The V1 `checkout_attempt` table and its `(payment_link_id, retry_key_verifier)` uniqueness are untouched, and no V1 fence is weakened. Under this contract `AD_HOC` orders create no attempts, capabilities, retries, or provider dispatch; the `checkout_attempt_v2` binding is designed so task 9.2.1 can extend it to standalone orders (attempts bound to an order without a link row) as a further additive amendment. V2 single-use consumption extends the existing claim model to a new `payment_link_v2_single_use_settlement` table with the same atomic claim-before-`CONFIRMED` semantics.

## Commerce V2 persistence shape, index strategy, and compatibility fences

- **Migration shape — additive new tables plus one nullable additive column.** The inventory below uses only constructs the safe migration language expresses: `createTable` with typed columns, `addColumn` (nullable or with a typed constant default), `createIndex` over plain column lists, `addConstraint`/`validateConstraint` (primary key, unique, composite foreign key, and checks built from closed comparisons, boolean composition, null tests, and closed-set membership), and `grant`/`revoke`. Because the language admits no regex, function, or trigger, four invariants live at the service boundary instead of the database: the 24-character identifier format (the database keeps `VARCHAR(24)` plus uniqueness only), the canonical decimal grammar (the database keeps `TEXT` only), active-dependency enforcement (service-fenced serialization, never a trigger), and the `order_v2` source vocabulary with its link/state coherence (a closed-set check on `source` could never be dropped to admit a later additive source value, and a "present exactly when" check could never be relaxed, so the vocabulary and per-source link/state presence are service-fenced, not database checks). All `id` values and timestamps are application-supplied; no `gen_random_uuid()` or `CURRENT_TIMESTAMP` default is assumed. The inventory: `payment_link_v2` (id, unique identifier, owner FK, closed-set `composition_kind`, nullable bilingual description and amount required exactly when `FIXED_AMOUNT` — expressible as an or/null-test check, currency-pair FK, closed-set `link_type`, nullable expiry, active flag, CAS version, timestamps, `(id, owner_id)` uniqueness); `payment_link_v2_line` (composite owner-bound FKs to link and product, line position bounded 1–20 by check with per-link position uniqueness — together enforcing the one-to-twenty line count that a cross-row count check cannot express — quantity bounded 1–9,999 by check, per-link product uniqueness); `order_v2` (owner FK, `TEXT` `source` with the service-fenced closed vocabulary (currently exactly `LINK` | `AD_HOC`), nullable composite owner-bound FK to the link, nullable `state` with a closed-set check on non-null values only, lifecycle CAS version, immutable monetary snapshot columns including amount/currency-UUID pair/bilingual description, closed-set policy check, the same fixed customer columns as V1, nullable settled timestamp, `(id, owner_id)` uniqueness); `order_v2_line` (composite owner-bound FKs to order and product, line position bounded 1–20 by check, quantity check, unit price, per-order product and position uniqueness); `checkout_attempt_v2` (mirror of the V1 attempt columns rebound to V2 identities, with `(payment_link_v2_id, retry_key_verifier)` uniqueness); `payment_link_v2_single_use_settlement` (mirror of the V1 claim rebound to V2 identities); `order_comment_v2` (owner-bound order FK, author FK, body, version, created/edited timestamps); `order_local_outcome_v2` (owner-bound order FK, closed-set outcome, nullable note, actor FK, created timestamp); and on `provider_order` exactly one nullable `order_v2_id` column with a composite owner-bound FK and owner-scoped uniqueness. Grants follow least privilege: comment and outcome tables receive no runtime `DELETE`; outcome history and settlement claims receive no runtime `UPDATE`; snapshot line tables receive `SELECT`/`INSERT` only.
- **Additivity proof.** The inventory mutates no V1 row, edits no baseline migration, drops no `NOT NULL`, renames or retypes nothing, backfills nothing, and adds no trigger, function, expression, or destructive DDL/DML. V1 projections (`src/orders/order-view.ts`, the public resolution and checkout DTOs), V1 identifiers, and V1 order history read exactly as today; V2 orders surface through new additive projections, and any extension of the existing owner/admin order reads is a later task's additive change to the projection, never to V1 data.
- **Index strategy (owner-scoped, keyset-friendly).** `payment_link_v2`: `(owner_id, created_at, id)` and `(owner_id, active, created_at, id)` for the 8.2.1 directory; `order_v2`: `(owner_id, created_at, id)`, `(owner_id, source, created_at, id)`, `(owner_id, state, created_at, id)` for the 8.3.1 filters with default page size 20, and `(payment_link_v2_id, created_at, id)` for the 8.2.3 drilldown; `order_comment_v2` and `order_local_outcome_v2`: `(order_id, created_at, id)`; `checkout_attempt_v2`: `(owner_id, capability_expires_at)` mirroring V1. Remaining 8.3.1 filters (date bounds, payer text, provider/local UUID equality) compose over the owner-scoped keyset indexes without new design.
- **Task 8.3.1 (owner order directory).** `src/orders/order-v2-directory.ts` delivers the owner-scoped V2 order directory on the data-directory foundation: registered filters `source` (`LINK`|`AD_HOC`), `money` (`USD`|`FIAT`), exact-calendar-day `from`/`to` bounds on `created_at` (ungrammatical or nonexistent days are the zero-I/O invalid outcome), `link` (exact V2 link identifier), and `q` (a UUID value matches `order_v2.id` or the related `provider_order.provider_order_uuid` by equality; any other bounded text matches payer name/email/cpf by owner-scoped case-insensitive containment), page sizes 10/20/50/100 with default 20, and the `(created_at desc, id desc)` keyset order. The `money` classification resolves server-side only: the registry has no pair-to-code read, so the adapter reads the durable `(currency_uuid, exchange_currency_uuid)` pair behind the active `USD` supported-exchange-currency pointer directly from the registry tables (read-only); an order is USD exactly when its snapshotted pair equals that active USD pair, and every other order — another active code or a deactivated/unmapped pair — is FIAT. Rows reuse the `order-v2-view.ts` summary projection; no mutation, rendering, or administrator variant is added.
- **Task 8.2.3 (link order drilldown).** The read-only `/links/v2/[id]/orders` list and `/links/v2/[id]/orders/[orderId]` detail are **delivered**: the list reuses the 8.3.1 directory entry with the parent link's identifier force-bound server-side into the `link` filter and a drilldown-bound path, and the detail renders the `order-v2-view.ts` projection only when the order's `paymentLinkV2Identifier` matches the parent identifier — every other case shares the one opaque unavailable outcome; no mutation, no currency-pair UUID rendering.
- **Reconciliation fences restated for V2.** The settlement map V1 is unchanged and remains the only state authority for `LINK` orders; the single-use claim is extended, not altered — one atomic claim recorded before `CONFIRMED` in the V2 claim table, with pending/rejected/cancelled/expired/indeterminate attempts never consuming; the versioned reconciliation CAS is preserved on `order_v2` with the same owner/provider-UUID/version/current-state match; provider notification payloads remain non-evidence; under this contract `AD_HOC` orders attach no provider order and reconciliation touches `LINK` orders only, with task 9.2.1 extending the same settlement map and CAS to sessionless standalone orders.
- **Closed route-inventory impact.** The public rate-limit surface and the server-request-log inventory keep every V1 entry unchanged. Tasks 8.1.2/8.1.3 add no public sessionless route: V2 link management, ad-hoc order creation, comments, and local outcomes are authenticated owner POSTs whose literal route templates are added to the server-request-log inventory by the implementing tasks. Any future V2 public checkout/status route extends the closed public rate-limit inventory explicitly in its owning task, with one task owning the final merge.

## Merchant analytics definitions (8.4.1)

This section pins the durable business definitions behind the owner-scoped merchant analytics projection delivered by `src/orders/merchant-analytics.ts` (one re-authorized active-`USER` read; server-only, no HTTP route — task 8.4.2's dashboard server component consumes the service directly; administrator/global analytics stays with 10.1.1). The projection reads Commerce V2 data only: V1 tables are never read, V1 remains frozen, and the exclusion holds by definition rather than by filter. Every definition below is reproducible from persisted fields alone; no definition ever requires a provider call.

- **Reporting timezone and closed periods.** One fixed reporting timezone, `America/Sao_Paulo` (DST-free since 2019, so an exact UTC−03:00 offset; deterministic, never owner-configurable, never derived from browser data). The period set is closed: `today` (the current calendar day so far), `7d` (the last 7 calendar days including today), and `30d` (the last 30 calendar days including today). Each period is calendar-day aligned in the reporting timezone and materializes server-side as exact half-open UTC bounds `[from, to)` — `to` is always the start of the next reporting day, so "so far" needs no special case. A period outside the closed set is the typed invalid-period outcome and performs no reads.
- **Sales volume — two members, never merged.** Provider-confirmed sales are `LINK` orders with `state = CONFIRMED` and `settled_at` inside the period bounds. Locally finalized sales are `AD_HOC` orders whose current local outcome (the latest `order_local_outcome_v2` entry) is `LOCAL_FINALIZED` with that entry's `created_at` inside the period bounds. The two members are computed, exposed, and consumed separately — never summed, netted, or otherwise merged — preserving the fence that a local outcome never writes, masks, or shadows the authoritative `state`. Every monetary sum groups by the order's snapshotted `(currency_uuid, exchange_currency_uuid)` pair and accumulates canonical decimal amounts as BigInt micro-units (10^6), never through JavaScript `Number` and never across currency groups. Currency groups are ordered by amount descending, then redacted code ascending (absent code last), then the internal pair identity ascending (never exposed).
- **Currency labels.** A currency group is labeled only through the durable registry read-only: the `supported_exchange_currency` pointer code plus the `catalog_currency_pair` label for the snapshotted pair; a snapshotted pair with no current pointer exposes a null code with the pair label, and an unmatched pair fails closed to null code and null label. Provider UUIDs never appear in the DTO.
- **Funnel — conversion and abandonment.** The funnel is defined over the owner's `checkout_attempt_v2` rows created inside the period bounds, classified only from the persisted `created_at`, `capability_expires_at`, and the linked order's `state`: converted = the attempt's linked order reached `CONFIRMED`; abandoned = not converted and `capability_expires_at` at or before the read instant; in-progress = the remainder. In-progress attempts are excluded from both rate denominators: conversion rate = converted / (converted + abandoned), abandonment rate = abandoned / (converted + abandoned), each an exact-decimal string truncated to four fraction digits and null when its denominator is zero.
- **Best sellers.** A bounded top-5 by confirmed quantity: the sum of `order_v2_line` snapshot quantities per product over in-period provider-confirmed orders, with per-currency-group revenue computed as exact-decimal `quantity × unit_price` sums under the monetary rules above. Ordering is quantity descending with a deterministic tie-break on internal product identity (never exposed). Bilingual titles come from the current same-owner `product` rows; archived or deactivated products still appear, because the revenue and quantity come from the immutable order-line snapshots.
- **Per-link metrics.** Over the owner's V2 payment links only: attempts created in period, provider-confirmed orders settled in period, and confirmed volume per currency group, exposed for every link with in-period activity (attempts or confirmed orders), ordered by confirmed orders descending, attempts descending, then the public-safe 24-character identifier ascending. The active-link count covers all of the owner's V2 links regardless of period activity.
- **Recent activity.** A bounded (5) most-recent owner order feed reusing the `order-v2-view.ts` summary semantics, redacted to source, bilingual description, amount, the redacted currency label, `state`, the current local outcome, `created_at`/`settled_at`, and the public-safe link identifier.
- **Redaction and scoping fences.** Every read re-authorizes the active `USER` principal and filters `owner_id` server-side. The DTO carries aggregates, counts, rates, bilingual labels, redacted currency labels, and 24-character link identifiers only — never customer snapshot members, order/attempt/link/product internal UUIDs, retry keys, verifiers, capability/nonce/key material, or provider data. There is no administrator or global entry point, no mutation, and no pagination beyond the pinned bounds.
