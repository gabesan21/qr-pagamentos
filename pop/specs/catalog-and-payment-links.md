## What it covers

This spec defines the administrator-managed catalog of Nautt provider UUIDs, account-owned products, and payment links that expose those products to buyers.

## Requirements

- Only authenticated administrators may create, update, deactivate, or delete catalog records.
- Authenticated account owners create, update, deactivate, or delete only their own products and create, activate, deactivate, or revoke only their own payment links. Administrators retain the separate global catalog role but have no implicit cross-owner product or payment-link management path.
- Catalog records live in PostgreSQL and are versioned through normal Prisma migrations.
- Every protected catalog or owner-mutating route re-authorizes the cookie principal and returns only its documented empty `401`/`403` protected outcomes or opaque owner outcome, never disclosing a target record to an unauthorized caller.
- The application remains bilingual (`pt-BR`/`en`); all user-visible labels, validation messages, and empty states are dictionary-backed.

### Nautt currency and payment-method catalog

- Administrators manage **currency pairs** (`currency_uuid`, `exchange_currency_uuid`, `label`) and **payment methods** (`payment_method_uuid`, `label`) that the application will allow on products and payment links.
- UUIDs are validated as non-empty canonical UUID strings at the server boundary; malformed values are rejected with a localized validation outcome.
- The application never sources these UUIDs from environment variables, request headers, or browser input; they are always read from this catalog.
- A currency pair or payment method can be marked inactive; inactive records cannot be selected for new payment links but do not break existing links.
- The catalog UI reuses the shared shadcn-based admin design system, responsive tables, and accessible forms.

### Supported exchange currencies (dynamic registry)

- The ISO 4217 alphabetic code (uppercase `[A-Z]{3}`, format-validated at the service boundary, with a database `AAA`–`ZZZ` bounds check as defense-in-depth) is the only application currency identity; there is no closed code list anywhere in code or schema.
- Each active mapping binds one code to the administrator-registered Nautt `currency_uuid` and `exchange_currency_uuid` (canonical lowercase, validated at the server boundary, sourced only from the admin mutation — never from environment variables, headers, or owner browser fields) plus a display label carried by the pair row. No other provider semantics (direction, limits, `deposit_fields`) are modeled or inferred.
- The `supported_exchange_currency` pointer table is the sole authority for code-based new-selection eligibility: one pointer row per code (primary key), with `pair_id` unique and a restrictive foreign key to the retained catalog pair. The legacy catalog `active` flag keeps governing legacy code-less rows only.
- Registration inserts the pair row and the pointer in one serializing transaction; replacement inserts the new pair row or re-points to a retained historical row and moves the pointer atomically; deactivation removes only the pointer row. Pair rows are immutable retained history: their UUID columns never change after insert and the application never physically deletes or remaps them (runtime holds no `DELETE` on `catalog_currency_pair`).
- Re-registering a `(currency_uuid, exchange_currency_uuid)` pair already present never inserts a second row: a new-mapping request receives one typed duplicate-pair conflict, while replace re-points the pointer to the retained row — the sanctioned restore path after a mistaken deactivation. The pair uniqueness constraint is preserved unchanged.
- Deactivation removes only new-selection eligibility: existing links, order snapshots, and read projections keep their recorded UUID meaning.
- The deterministic default is the active `BRL` mapping when one exists, otherwise an explicit no-default/unavailable result; the resolver never falls back to another code, insertion order, label order, or an inactive row.
- Missing configuration is a normal operational state: dependent features (store default in 7.1.2, product currency in 7.2.2, standalone checkout dispatch in 9.2.1) require an active mapping only at new-assignment time and consume the shared resolver's discriminated available/unavailable read or its typed `NoActiveExchangeCurrencyMapping` error. Task 7.1.2's store default currency is the first consumer: assignment gates on an active mapping and fails the save opaquely otherwise, while a stored code keeps reading as-is after a later deactivation. Task 9.2.1's sessionless standalone checkout resolves the store's stored default code server-side through the same active-pointer seam at dispatch time (a deactivated mapping or inactive pair is the checkout's one opaque unavailable outcome, never a fallback); it adds no new registry surface.
- Only an active administrator mutates mappings through the re-authorized `POST /admin/exchange-currencies` route (origin-guard first, empty `401`/`403`, opaque outcomes); active owners read only active redacted `{ code, label }` choices — no provider UUIDs, inactive rows, or timestamps — and no public/sessionless discovery surface exists. The administrator management UI is the exchange-currencies section of the `/admin/settings` hub (delivered by 10.4.1) reading the admin-only redacted `listMappings`; register, replace, and deactivate post to that same route and redirect back to `/admin/settings?…`.

### Products

- Authenticated account owners manage only their own products with: internal name, public title (i18n), description (i18n), exact-decimal price, active/inactive status.
- Each owner may maintain categories with required `pt-BR` and English names. Names are Unicode-trimmed, nonblank, single-line, at most 160 code points, stored without case folding or internal-whitespace rewriting, and exact-unique per owner and locale.
- Categories are retained after one-way deactivation and use nonnegative expected-version CAS for edits and deactivation. Unknown, stale, inactive, malformed, cross-owner, and deleted-owner targets share opaque protected/conflict outcomes and cannot partially mutate state.
- A product's current category is nullable and owner-bound. Existing products remain uncategorized without backfill. A referenced category can be deactivated only with an explicit distinct active category of the same owner; every current product is reassigned atomically before the source becomes inactive. Without references, no replacement is required.
- Category reassignment changes only the product's current organization. It never rewrites product values, payment links, order snapshots, identifiers, provider data, or any V1 public DTO. Ordinary product create/edit selects or clears the current category through the same nullable composite same-owner key; assigning a category requires an active category of the same owner, while clearing is always allowed. Reassignment moves every referencing product regardless of archival state, since it rewrites only organization, never history.
- A product's currency is nullable catalog metadata (`[A-Z]{3}`, format-validated at the service boundary with a database `AAA`–`ZZZ` bounds check as defense-in-depth). Assigning or changing a non-null code requires an active supported-exchange-currency mapping at assignment time through the shared resolver; its absence surfaces only the typed `NoActiveExchangeCurrencyMapping` signal mapped to one opaque mutation outcome. Clearing to null never requires a mapping, a stored code survives a later mapping deactivation, and currency-less products remain valid with no backfill or default inference. Product currency never rewrites existing payment links (which bind `currencyPairId` directly) or orders, and never enters V1 public DTOs; it appears only in owner-scoped product management data.
- A product carries at most one catalog image through the canonical media boundary. The product row stores only the opaque 43-character media identifier with **no** database foreign key (physical ORPHANED reclaim must never be blocked by product references, and the media boundary never exposes internal ids or revisions to callers); the invariant is service-fenced: a product may reference only an `ACTIVE` same-owner `PRODUCT_IMAGE` object. Assignment activates the caller-staged object (`STAGED → ACTIVE`) before the product save; replacement or removal orphans the previous object (`→ ORPHANED`, 24 h grace) only after the save succeeds, with a best-effort compensating orphan of the just-activated object on save failure. Public image bytes ride the existing `GET /media/[identifier]` ACTIVE-only read; product management adds exactly one owner-only staging route (`POST /products/images`: origin-guarded, bounded multipart rejected above 5 MiB before decode, one opaque identifier with `no-store`, and one opaque empty failure outcome) plus the `/catalog` workspace upload UI; it adds no public projection wiring.
- Archival is a one-way terminal deactivation: archiving stamps `archived_at` and forces `active = false` in the same expected-version CAS mutation and is irreversible. An archived product cannot be edited, reactivated, re-archived, or assigned category/currency/image (every mutation CAS excludes archived rows); it stays readable in the owner list with its archived state. New-link ineligibility needs no new enforcement surface: `active = false` engages the existing baseline `payment_link_require_active_dependencies` trigger and the existing active-only picker exactly as V1 deactivation does. "Links and orders stay intact" is a **data-level** invariant only — link rows and the policy-exact order snapshots are preserved byte-for-byte, while checkout presentation of links to the archived product becomes unavailable, identical to V1 deactivation semantics. Archival works for products referenced by links or orders (where V1 `delete` is database-restricted); V1 `delete` semantics for unreferenced products stay unchanged.
- A product price is persisted and exchanged inside the server as one canonical positive ASCII decimal string. Its grammar is `^(?:0|[1-9][0-9]{0,11})(?:\.[0-9]{0,5}[1-9])?$`, with the all-zero value excluded: no sign, exponent, comma, grouping separator, surrounding whitespace, leading integer zero, or trailing fractional zero is accepted. This gives at most 12 integer digits, 6 fractional digits, and 18 total digits; values outside those precision/scale limits are rejected rather than rounded. The application never converts the value through JavaScript `Number`.
- The protected product form accepts that canonical dot-decimal contract; it does not silently trim or rewrite malformed prices. Presentation alone formats the exact value according to the persisted `pt-BR` or `en` locale and never changes the stored canonical value.
- Internal names are required and limited to 128 Unicode code points; each public title is required and limited to 160 Unicode code points; each public description is required and limited to 2,000 Unicode code points.
- Text fields are validated after removing leading and trailing Unicode whitespace. The trimmed value is persisted; whitespace-only values are rejected. Internal whitespace is preserved, but internal names and public titles reject CR/LF and therefore remain single-line; descriptions preserve internal spaces and line breaks. Limits apply to the trimmed persisted value.
- A product can be deactivated; inactive products cannot be linked to new payment links.
- Product mutations are atomic and idempotent where practical; concurrent edits are rejected with an opaque conflict outcome.
- A failed product or category mutation (`conflict|failed`) redirects back to the form that submitted it — product create to `/catalog/products/new`, update/active/archive to that product's detail, category actions to `/catalog/categories` — with the same closed opaque notice; the merchant's typed values are restored client-side from a session draft only under that notice (14.1.1). Archived products render their form read-only in a non-submitting container.
- Public read surfaces for checkout expose only redacted product fields: public title, description, and price. The application-internal public-product read boundary is server-only and accepts a trusted canonical product UUID plus the closed `pt-BR` or `en` locale. Each uncached read must query only an active product and return either `null` (malformed, absent, or inactive are indistinguishable) or exactly `{ title, description, price }`, selecting the requested locale's persisted public title/description. `price` remains the unchanged canonical positive ASCII decimal string; it is never converted through `Number`, formatted, rounded, or paired with a currency here. The result excludes every identifier, internal/admin field, state/version/timestamp, and provider field. This boundary creates no HTTP route, UI, dictionary copy, payment-link binding, or checkout behavior.

### Payment links

- An authenticated account owner generates a payment link bound to exactly one active product with that same owner and one active currency pair. Creation atomically persists the matching owner and checks both dependencies at its commit boundary; it mutually serializes with their activation-state changes: a deactivation committed first rejects generation, while a deactivation that follows a successful creation leaves the existing link intact.
- Links may be **reusable** (many checkouts, e.g. a donation link) or **single-use**. A single-use link is consumed only by the atomic settlement claim written when one linked order reaches confirmed successful payment; manual revocation stays available at any time. **Delivered reality:** the claim mechanism exists on both sides (4.1.2 for V1, 8.1.3 for V2) and 9.2.1 wired webhook reconciliation to the V2 settle only — the V1 settle service still has no production caller, so a V1 `SINGLE_USE` link is never consumed in production (tracked in `pop/open_questions/2026-07-26-v1-settle-wiring-gap.md`, resolution deferred to its own modification).
- Each link carries: slug/identifier, optional expiration timestamp, active/inactive flag, created-at metadata.
- The link identifier is unique, URL-safe, and non-sequential; it is derived server-side and never editable.
- **Task 3.3.2 public-resolution contract — approved at yolo 003:** `GET /api/payment-links/[identifier]` is unlocalized and sessionless. It accepts only the exact persisted 24-character URL-safe identifier, without trimming, case-folding, or other transformation, chooses only `pt-BR` or `en` through the request `Accept-Language` negotiation, and returns `Cache-Control: no-store` on every outcome. An active, unexpired link whose product remains publicly active returns exactly `{ product: { title, description, price }, currencyPair: { currencyUuid, exchangeCurrencyUuid } }`; `price` stays the exact canonical decimal string. The two currency UUIDs are the sole provider identifiers permitted because later checkout quoting needs the configured pair. No cookies, session/principal lookup, dictionary, UI, route-localized preference, IDs, link metadata, admin fields, pair label/status, timestamps, type, or other provider data may be read or returned. Malformed, absent, inactive, expired, and product-unavailable links all return the same empty `404` with `no-store`; expiry is evaluated at read time only. Before locale negotiation or the public-link read, the route uses the bounded single-process public API limiter: its only denied outcome is an empty `429` with `no-store`. This endpoint makes no mutation, including automatic expiry inactivation or `SINGLE_USE` consumption, and makes no checkout, order, or provider request.

## Commerce V2 payment links (additive contract — fully delivered)

The record design, composition kinds, currency-pair binding, service-fenced active-dependency enforcement, identifier continuity, expiry/type persistence, CAS edit fork gate, and additive public resolution below are **delivered** by task 8.1.2, and the derived `active/inactive/expired/paid` lifecycle projection with its merchant directory is **delivered** by task 8.2.1 over 8.1.3's orders/settlement. The bilingual owner management flows and the supersede/new-version fork UX are **delivered** by task 8.2.2, and the read-only per-link order drilldown with its read-time order count is **delivered** by task 8.2.3. The V2 public checkout is **delivered** by task 9.3.1 (sessionless reservation/replay/capability execution over `checkout_attempt_v2` and the branded `/pay/[identifier]` V2 branch, with the link-derived `paid` lifecycle becoming reachable through real single-use settlements); the public terminal states of `/pay/[identifier]` are **delivered** by task 9.3.2 — a consumed `SINGLE_USE` link renders the claim-keyed branded paid view (public composition summary, exact total, display currency code, and owner branding only), while malformed, unknown, inactive, expired, and otherwise unavailable identifiers keep the one opaque unavailable view, and every V1 guarantee in this spec is unchanged: V1 links, identifiers, public DTOs, order history, and the baseline `payment_link_require_active_dependencies` trigger behave exactly as specified above, and no V1 row is ever mutated, wrapped, or migrated by Commerce V2.

- **Record design — new tables, never V1 column reuse.** A Commerce V2 payment link is a new record in a new `payment_link_v2` table with its composition in a new `payment_link_v2_line` table; V1 `payment_link` gains no columns, no relaxed `NOT NULL`, and no trigger change. The V1 `product_id`/`currency_pair_id` columns are `NOT NULL` with owner-bound references guarded by an insert trigger that the immutable baseline and the safe migration language can neither edit nor extend to new checks, so multi-item and product-less compositions cannot exist on the V1 row; new tables are the only additive shape that keeps every V1 row valid byte-for-byte.
- **Composition kind.** Each V2 link carries exactly one immutable composition kind from the closed set `PRODUCT_LINES` | `FIXED_AMOUNT`, chosen at creation and never changed. `PRODUCT_LINES` carries one to twenty ordered lines, a bound enforced by a line-position check of 1–20 plus per-link position uniqueness (a cross-row count check is inexpressible in the safe migration language); each line references one active same-owner product through the nullable-free owner-bound composite key and carries a positive integer quantity from 1 to 9,999, and the same product may not appear twice on one link. `FIXED_AMOUNT` carries no product line: it holds a required bilingual public description (one value per supported locale `pt-BR`/`en`, each 1–160 Unicode code points, trimmed, single-line, following the product-title text normalization) and one required canonical positive ASCII decimal amount in exactly the product-price grammar. A link never mixes kinds and never accepts an additional composition member.
- **Currency-pair binding.** Every V2 link, including `FIXED_AMOUNT`, binds one administrator-catalog currency pair that is active at creation through the same restrictive reference as V1. The pair is a financial member: it never changes after creation. Deactivation of the pair later leaves existing links and their order snapshots intact, exactly as in V1.
- **Active-dependency enforcement.** The safe migration language cannot create triggers, so the V1 commit-boundary trigger cannot extend to V2. V2 creation instead verifies inside one transaction that every referenced product is an active same-owner row and the pair is active, reading them with shared row locks that serialize against their deactivation: a deactivation committed first rejects creation; a deactivation committed after creation leaves the link intact. This invariant is service-fenced, never reintroduced as a database trigger.
- **Identifier continuity.** The V2 public identifier uses exactly the V1 grammar — 24 URL-safe characters derived server-side from 18 random bytes — and shares one global namespace with V1: generation retries against collisions in both tables, each table enforces its own uniqueness, and an identifier is never editable, reused, or reissued. V1 identifiers keep resolving through the V1 route only.
- **Expiry and type.** `expires_at` is nullable and evaluated at read time only, never by a stored mutation, exactly as in V1. The closed `SINGLE_USE` | `REUSABLE` type is immutable after creation and follows the V1 consumption semantics: a link is consumed only when one linked order reaches confirmed successful payment; pending, rejected, cancelled, expired, failed-to-start, and indeterminate attempts never consume it.
- **Lifecycle status vocabulary (for the 8.2.1 directory).** The only persisted lifecycle facts are `active`, `expires_at`, type, and creation metadata. Every other link state is a derived read projection, never a stored column: `active` (active and unexpired), `inactive` (owner-deactivated), `expired` (read-time expiry on an active link), `paid` (a `SINGLE_USE` link with its confirmed single-use claim, or a `REUSABLE` link with at least one `CONFIRMED` order), the type state, and the share state (the public identifier URL). No derived state is ever persisted, and no state outside this vocabulary exists.
- **Immutable-version edit fork.** The financial members (composition kind, lines, quantities, description, amount, currency pair) are editable with expected-version CAS only while no checkout attempt exists for the link. Once the first checkout attempt exists, financial edits are rejected and the only path is the roadmap fork: a new immutable link version is a new V2 link record with a fresh identifier that supersedes the old link; the old record, identifier, and order history stay intact and resolvable, and the owner may deactivate it. The non-financial members (expiry, active flag) remain editable at any time through the same CAS. Editing never rewrites any order snapshot. **Delivered shape:** the attempt-existence check is a named service seam that 8.1.3 wired to the real `checkout_attempt_v2` existence read, 9.3.1 delivered the V2 checkout execution that populates it, and 8.2.2 delivered the supersede/new-version UX (`/links/new?from=<id>` prefills the composition with a fresh server-generated identifier).
- **Public-resolution DTO evolution.** `GET /api/payment-links/[identifier]` and its exact V1 DTO, outcomes, rate-limit surface, and redaction discipline are frozen: a V1 identifier never returns a V2-shaped payload. The V2 public-resolution contract implemented by 8.1.2 is additive only: it may add new members to a V2 resolution response, must keep the same sessionless exact-token acceptance, `no-store` on every outcome, uniform empty `404`, closed `pt-BR`/`en` negotiation, and redaction discipline (no owner, admin, state, version, timestamp, or provider data beyond the pair UUIDs required for quoting), and must never remove, rename, or retype any V1 member for V1 links.
- **Sessionless owner-derived issuance (9.1.3).** The storefront cart checkout command defined in [[specs/storefront-and-customization|Storefront and customization]] creates owner-derived `SINGLE_USE` `PRODUCT_LINES` V2 links by reusing the delivered owner creation service server-side — never the owner POST route — with a principal synthesized from the locked storefront-owner row (an `ACTIVE` merchant `USER`; nothing else ever resolves). Every invariant above applies unchanged: the immutable composition kind, the one active pair binding, the shared-row-lock active-dependency enforcement, the identifier continuity, and the read-time lifecycle derivation. Composition, prices, currency, and pair derive exclusively from locked product rows and the registry; the browser contributes only product identity and quantity. Issued links are ordinary merchant-owned V2 rows — visible in the owner directory, deactivatable, and `paid`-projected on settlement — and issuance adds no administrator capability and no new owner mutation surface.
