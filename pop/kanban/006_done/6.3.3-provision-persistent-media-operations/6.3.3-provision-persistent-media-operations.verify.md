## Round-3 blocker resolution

Commit `f788811` adds a post-failure classification in `install/update.sh:401-412`:
when `compose up -d --no-deps --force-recreate app` fails, it inspects
`compose ps -aq app`; a new container identity (recreate succeeded, target
crashed on startup) seals `rollback_target_failure target-health`, and only a
failure leaving no new container stays `target-recreate`. Adversarial review:

- **No misroute of genuine recreate failures:** a genuine orchestration
  failure leaves no new container (or only the old one), so it still seals
  `target-recreate`; both branches run the identical image-only rollback, so
  even a boundary misclassification could not change recovery behavior, only
  the evidence label — and the label chosen (crashed new container =
  target-health) is semantically correct.
- **No wrong `result=` leak:** `rollback_target_failure` always ends in `die`,
  so the `target-health` branch can never fall through to the `target-recreate`
  seal; the sealed string is exactly `result=target-health-failed-previous-image-healthy`.
- **Contract preserved:** the added `compose ps`/`compose logs` calls are
  read-only; no retry of one-shot helpers, no second re-entry, no moving-ref
  handoff, no new network/secret access; recreate still happens only after
  bootstrap/migration/identity-seed helpers pass, matching the root AGENTS.md
  update contract ("Target-health rollback is image-only against retained
  database/media state").
- **Evidence grammar:** the appended `failed_container=<id>` records no
  forbidden field (no mountpoint, in-volume path, media identifier/digest,
  database value, credential, or secret path) and matches the pre-existing
  `previous_app_container=` practice.
