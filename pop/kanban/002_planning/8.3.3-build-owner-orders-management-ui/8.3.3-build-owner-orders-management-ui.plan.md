# Plan — [[8.3.3-build-owner-orders-management-ui]]

- **Stage:** 002_planning · **Responsible:** planner agent

## Objective and expected result

- **Objective:** Deliver the bilingual responsive owner orders management UI over the delivered 8.3.1 directory query (`src/orders/order-v2-directory.ts`), the 8.1.3/8.3.2 engagement mutations (`POST /orders-v2/[id]`: `append-comment` / `edit-comment` / `set-outcome`), and the `order-v2-view.ts` projections: a Commerce V2 order directory at `/orders` (payer, source/link, state, local-outcome, amount, date facts; `source`/`money`/`from`/`to`/`link`/`q` filters; page sizes 10/20/50/100 with a localStorage preference), a V2 detail view at `/orders/v2/[id]` with the comment thread (append + author edit under CAS) and guarded local-outcome actions, and all loading/empty/filtered-empty/invalid-query/error states. The read-only V1 ledger stays as the legacy section below the V2 directory and `/orders/[id]` keeps serving V1 detail (exact 8.2.1 `/links` coexistence pattern); the shell route map is untouched — `/orders` remains the single merchant nav entry.
- **Observable result:** From `/orders` the merchant searches and filters V2 orders, paginates by keyset cursors, keeps the chosen page size across visits without a URL param, opens an order to read payer/lines/comments, posts and edits comments, sets `LOCAL_FINALIZED`/`LOCAL_CANCELLED` behind a confirmation, and sees only the closed opaque `?orders-v2=commented|comment-edited|outcome-set|failed` notices in both locales at 320–1440px.

## Strategy

UI + wiring only; the directory-query, engagement-service, and route contracts are fixed. Mirror the delivered `/links` workspace (`src/app/(merchant)/links/`): server components, `requireMerchantShellContext`, `WorkspaceHeading`, the `DataDirectory` composition, native GET toolbar and native POST action forms, observation-only client boundaries (busy announcement, disable-after-payload, per DESIGN.md). Three deliberate seams, each minimal and additive: (1) the mutation redirect target `/orders?orders-v2=<outcome>` carries a key the strict query grammar rejects (unknown keys are zero-I/O invalid), so the page strips and validates the closed notice set before canonicalization — the catalog `noticeKey` pattern; (2) the `DataDirectory` toolbar hardcodes page sizes 25/50/100 and enum-only filters, so the generic foundation gains optional role-neutral props — a registered page-size option list and generic labelled text/calendar-day filter fields — with no concrete Orders projection in `src/data-directory/`; (3) two read-projection gaps block the card objective: the summary exposes no payer columns (the table must show payer facts) and the detail exposes no `lifecycleVersion` (the delivered set-outcome route requires the expected lifecycle CAS version, which is not derivable — reconciliation also bumps it). Both are resolved by additive, server-only exposures in `src/orders/order-v2-view.ts`: the policy-exact `CustomerSnapshotV1` payer snapshot on `OrderV2Summary` (fail-closed mapping already exists) and `lifecycleVersion` on the owner detail `OrderV2View` — the comment `version` CAS field is the in-projection precedent; mutation, query, and route files stay byte-unchanged. The page-size preference is one focused client boundary: it writes the choice on change of the toolbar control and, only when the URL carries no explicit `pageSize`, navigates to the canonical URL with the stored registered size; an explicit URL value always wins and is re-stored, so no redirect loop and no server canonicalization violation. Currency pair UUIDs are never rendered; amounts render as the exact decimal string with tabular figures; `state` (null for `AD_HOC`) and the current local outcome render as separate never-color-only badges, never merged.

## Risks and abort conditions

- **Risk:** the two additive `order-v2-view.ts` exposures (payer snapshot on the summary, `lifecycleVersion` on the detail) are ruled a projection-contract violation at 005 — mitigation: sanctioned here explicitly, additive-only, comment-`version` precedent, DOX + spec lines updated in the same diff; the alternative (no payer column, no set-outcome UI) fails the card objective, so rejection means re-plan, not silent scope cut.
- **Risk:** the `orders-v2` notice param collides with strict canonicalization (unknown keys → zero-I/O invalid) — mitigation: strip and validate the closed outcome set before `canonicalizeDirectoryRequest`, exactly the catalog/8.2.2 `noticeKey` pattern; invalid values never echo.
- **Risk:** the generic toolbar extension regresses the `/links` and `/catalog` directories — mitigation: optional props only; existing `data-directory`, links, and catalog tests must pass unedited.
- **Risk:** the localStorage preference fights canonicalization (redirect loop or stripped param) — mitigation: navigate only when no explicit `pageSize` is present and the stored value is a registered size ≠ rendered default; explicit URL always wins and is re-stored; covered by page tests + evidence capture.
- **Abort if:** the delivered directory result shape, route form grammar, or redirect vocabulary deviates from what this plan states, or the UI need forces a change beyond the two sanctioned additive exposures (e.g. cursor or mutation-contract edits) — flag `blocked: true` with the conflicting evidence.
