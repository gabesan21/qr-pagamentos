## Decisões que restringem esta frente

- The three-way invalid/expired/used split is **not** implementable here: the reset service returns one `null` for all three (`src/auth/password-reset.ts:94-96,159-173`), and teaching it to distinguish them is a service change this task forbids. Ship the two states the page can prove — no token or blank token, and token present but no longer usable — each with its own localized copy, the generated `unavailable` illustration and a back-to-login action. Do not invent a third state and do not guess which cause applied.
- The success state renders on the reset page: the submit route's success redirect target becomes the reset path with a presentation-only status parameter instead of `/login?password=changed`. Every failure outcome keeps the current opaque `error=failed` redirect, and the login page's `password=changed` notice stays because the profile password route still produces it.
- Mismatch feedback is client-side only; the server keeps folding mismatch into the generic failure. The requirement hint states 12 to 128 characters, matching `validatePassword`, and both fields gain the 128 cap and the show/hide control delivered by F02's pattern.
- The 404 resolves the locale from the existing preference cookie and reads localized copy from a new `not-found` dictionary domain registered in the three aggregator files; it keeps the current projected-utility composition and adds no navigation capability.
- Reuse F02's auth card and `.auth-*` classes for both pages; if a genuinely missing rule appears, report it instead of adding CSS to a file you do not own.
