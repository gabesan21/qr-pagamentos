# Plan — 7.2.2-evolve-products-for-catalog-media

- **Task:** [[7.2.2-evolve-products-for-catalog-media]] · size L · critical · yolo

## Objective

Extend the owner product record with an optional currency code gated on the active exchange-currency mapping, a single owner-scoped catalog image through the canonical media boundary, completion of category selection in ordinary product management, and one-way archival — all additive and nullable, with exact V1 semantics for payment links, orders, and every public/history projection.

## Strategy

One cohesive cross-layer delivery: additive safe migration → schema → service/validation → owner mutation route → focused tests → spec/DOX sync. No UI (7.2.3 owns pages); the existing form route gains the new fields as validated inputs only. Historical immutability is guaranteed by construction: nothing existing is rewritten, backfilled, or re-projected.

### Settled design decisions

- **Currency (nullable, assignment-gated):** new `currency_code` (`VarChar(3)`, nullable, database `AAA`–`ZZZ` bounds check as defense-in-depth, mirroring the pointer-table doctrine). Assigning or changing a non-null code requires an active mapping at assignment time through the shared resolver from `src/auth/supported-exchange-currency.ts`; absence surfaces only the typed `NoActiveExchangeCurrencyMapping` signal mapped to one opaque route outcome. Clearing to null never requires a mapping. Products without currency remain valid (V1 catalog is currency-less); there is no backfill and no default inference. Product currency is catalog metadata only — it never rewrites existing payment links (which bind `currencyPairId` directly) or orders, and never enters V1 public DTOs.
- **Image (one per product, media-boundary owned):** new nullable `image_media_id` holding the internal media object UUID. **No database foreign key** (physical ORPHANED reclaim must never be blocked by product references); the invariant is service-fenced: a product may reference only an `ACTIVE` same-owner `PRODUCT_IMAGE` object. Assignment activates a caller-staged object (STAGED→ACTIVE) and references it; replacement or removal orphans the previous object (→ORPHANED, 24 h grace) in the same serialized product-mutation transaction sequence. Public product images ride the existing `GET /media/[identifier]` ACTIVE-only read; this task adds no media route, upload UI, or projection wiring.
- **Archival (one-way, terminal):** new nullable `archived_at` timestamp. Archival is irreversible (mirroring category deactivation doctrine): an archived product cannot be edited, reactivated, re-archived, or assigned category/currency/image, and cannot back new payment links; it stays readable by the owner list in a distinct archived state. Archival works for products referenced by links/orders (where V1 `delete` is DB-restricted); V1 `delete` semantics for unreferenced products stay unchanged. Existing links and orders are untouched. Interaction with category deactivation/reassignment: archived products are excluded from "current product" reassignment scope only if the 7.2.1 contract defines scope as active products — verify against `src/auth/product-category.ts` at execution; default rule: reassignment moves every product regardless of archival, since it rewrites only organization, never history.
- **Category completion (no redo):** product create/update values gain the nullable `categoryId` using the 7.2.1 composite same-owner key and active-category rule; deactivation/reassignment behavior from 7.2.1 is unchanged.
- **Historical-reference contract:** payment links keep their persisted pair/product binding; orders keep the policy-exact snapshots via `src/orders/order-view.ts`; the public product read stays exactly `{ title, description, price }`; `GET /api/payment-links/[identifier]` keeps its exact DTO. New fields appear only in owner-scoped product management DTOs.

## Contracts and risks

- **Contracts:** additive nullable columns only; safe-language migration via `node pop/scripts/migration-policy.mjs generate`; CAS (`version` increment) on every product mutation including archive/image/category/currency changes; owner re-authorization and opaque outcomes per existing route; exact-decimal price grammar untouched; runtime `qr_runtime` DML unchanged (no DELETE on product beyond existing V1 delete).
- **Risks:**
  - *Dangling image reference* after ORPHANED grace reclaim — mitigated by the fenced invariant (products reference only ACTIVE media; orphaning happens only inside product replacement/removal flows). Critic must verify no path orphans a referenced object.
  - *Lane race with 7.1.2* — mitigated by the migration-ID preflight rule above.
  - *Currency over-coupling* — product currency must not leak into payment-link creation or public DTOs; tests must assert V1 DTO byte-stability.
  - *Archival vs 7.2.1 reassignment scope* — resolved at execution against `product-category.ts`; either choice must be recorded in the spec.
  - *Route surface creep* — no new public/sessionless route, no rate-limiter/request-log inventory change unless a genuinely new POST action is added (archival rides the existing `/products` form route actions).
