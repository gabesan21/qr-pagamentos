# Plan — [[10.3.2-build-admin-user-directory]]

- **Stage:** 002_planning · **Responsible:** planner agent

## Objective and expected result

- **Objective:** replace the flat `/admin/accounts` account list with a bounded, read-mostly, re-authorized global user directory on the `src/data-directory/` foundation — keyset pagination over the closed 10/20/50/100 set with **default 50**, role/derived-state/created-date/search filters, per-row store state and created/last-activity evidence, explicit edit and soft-delete actions — plus a read-only user detail route that 10.3.3 extends into the profile editor.
- **Observable result:** `/admin/accounts` renders the user directory (canonical `307`s, zero-I/O invalid-query, six states) under `ADMIN_GLOBAL` cursor binding, keeping the delivered notice strip and create-account section; `/admin/accounts/[id]` serves a read-only detail with one opaque unavailable outcome; deleted users stay listed with a localized non-color deleted badge and no actions; the delivered `POST /admin/users/[id]/delete` route is surfaced unchanged; contract tests and a run-bound `admin-users:evidence` pair prove authorization, redaction, and accessibility.

Stage skills on the card are correct (clean-code + ui-change/ui-review + sync-specs across 002/004/005); nothing missing.

## Strategy

Read-mostly admin surface over delivered modules; no mutation route, no migration, no foundation edit. Pinned decisions the executor must not revisit:

1. **Query ownership: new module, never extend the mutation service.** A new server-only `src/auth/admin-user-directory.ts` runs `queryAdministratorDirectory` with the `ADMIN_GLOBAL` scope purpose (both delivered — no foundation edit), directory id `admin-users`, path `/admin/accounts`, keyset `(createdAt desc, id desc)`, and the admin-directory page-size policy `{ sizes: [10,20,50,100], defaultSize: 50 }` (10.2.1/10.2.2 precedent). `src/auth/administration.ts` and `src/auth/identity.ts` stay byte-frozen; the page stops calling `listUsers` and reads through the new module instead.
2. **Row DTO: sanctioned admin DTO + two derived facts, nothing else.** Rows carry exactly the `toAdminUserDto` fields (`id`, `username`, nullable `email`, `role`, `status`, `createdAt`, `deletedAt` — the administrator-only deletion marker, already sanctioned) plus a derived `storeState` (`active` = enabled with slug, `configured` = slug but disabled, `none`) and a derived nullable `lastActivityAt` = `max(session.lastSeenAt)` aggregate. Never expose password hashes, session ids/digests/counts/expiry, credential/provider data, profile version, locale, checkout policy, raw storefront fields beyond the derived state, or audit rows. The `lastActivityAt` aggregate and `storeState` are explicit spec amendments (last-activity evidence sanctioned by the card).
3. **Derived render state: `deleted` > `disabled` > `active`, computed at read time, never stored.** Deleted users stay listed in every result and position (history preserved, 10.2.1 precedent); the row renders the username with a localized non-color deleted badge and carries **no** edit/delete actions (every mutation on a deleted target already shares the opaque not-found outcome server-side).
4. **Filters (five, under the eight-filter cap):** `role` (closed `ADMIN`/`USER`), `state` (closed derived three), `from`/`to` (validated created calendar-day bounds, zero-I/O invalid), and `q` (username or email containment — both are sanctioned admin DTO fields). No UUID, locale, or provider filters.
5. **Actions: edit navigates, delete posts the delivered frozen route.** Edit is a plain GET link to `/admin/accounts/[id]` (the detail this task delivers). Delete is a native POST form to the delivered `POST /admin/users/[id]/delete` — byte-frozen: origin-guard, re-authorized admin, opaque `/admin?success=deleted` / `/admin?error=change-failed` redirects, whose notices `/admin` already renders. No new mutation route, no request-log inventory change, no client-side eligibility computation beyond hiding actions on deleted rows (final-active-admin protection stays server-side only).
6. **Detail-route contract for 10.3.3 (explicit).** `/admin/accounts/[id]` re-authorizes an active `ADMIN`, resolves by UUID id as a global read, and shares one opaque unavailable outcome for malformed/missing identities; deleted users remain viewable, read-only with the badge. It renders the row facts plus `storefrontSlug`/store facts and the delete form. The exported detail read (`getAdminUserDetail` in the new module) and this route path are 10.3.3's pinned contract: 10.3.3 extends **this same route** with its editor forms and safe public-store link and must not move it; owner cells in 10.2.1/10.2.2 directories repoint here when 10.3.3 lands (their specs already record the interim `/admin/accounts` target, which this task makes real).
7. **Accounts page recomposition, legacy mutation forms retire from the page.** `/admin/accounts` = existing notice strip + unchanged create-account section (posting to the delivered `/admin/users` route) + the new directory replacing the flat `Accounts` list. The legacy inline role/status/password forms leave the page; their routes stay byte-frozen and 10.3.3 (the very next dependent task) re-houses those mutations in the editor. The spec amendment records this interim window honestly. The admin dashboard, settings, and other surfaces in `admin-surface.tsx` are untouched.
8. **No schema or infrastructure change.** All reads run on the delivered schema; the `lastActivityAt` max-aggregate and containment search need no new index at this scale — if recon shows one is required, that is an abort, not a migration.

Rate-limit and request-log inventories: unchanged (SSR admin pages plus the already-inventoried delete route) — no intersection with 9.1.3/9.3.1.

## Risks and abort conditions

- **Risk:** redaction regression (session ids/digests/counts, credential/provider data, profile version, locale, checkout policy, or raw storefront fields leak admin-side) — mitigation: whitelist DTO typing + absence assertions; 005 diffs the DTO against the amended boundary.
- **Risk:** `lastActivityAt` aggregate or `q` containment scans grow unbounded — mitigation: bounded keyset reads, no offset, no new index (pinned decision 8).
- **Risk:** retiring legacy mutation forms from the page strands role/status/password capability until 10.3.3 — mitigation: routes stay live and protected; interim window recorded in the spec; 10.3.3 is the next dependent task.
- **Risk:** evidence harness conflicts with 10.2.1/10.2.2 concurrent appends — mitigation: distinct flag and seed block, rebase-level merge; never reword shared harness code.
- **Risk:** delete-form notice lands on `/admin` while the admin was on `/admin/accounts` — accepted: the delivered route's redirect contract is frozen and `/admin` already renders those notices.
- **Abort if:** the directory cannot be served from the delivered schema (missing user/session/storefront relation or column) — signal `blocked: true` with the schema evidence; a migration would violate the task constraint.
- **Abort if:** the admin UI inventory gate cannot pass without editing frozen foundation/design-system sources — signal `blocked: true` with the failing check output.
