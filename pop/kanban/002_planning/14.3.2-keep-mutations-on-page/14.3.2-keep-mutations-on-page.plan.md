# Plano — [[14.3.2-keep-mutations-on-page]]

- **Etapa:** 002_planning · **Papel:** `pop-planner` (separado da execução)

## Objetivo e resultado esperado

- **Objetivo:** every merchant mutation returns to the page that submitted it, announces its outcome through the toast bridge, and preserves typed input on failure.
- **Resultado observável:** commenting or setting a local outcome keeps the merchant on `/orders/v2/<id>`; creating a link lands on the new link's detail and editing or activating it on that link's detail; profile, TOTP and Nautt actions stay on their own page; no merchant mutation lands on `/` or on a directory, and a failed submit comes back with the typed values still in the form.

## Estratégia

Native POST + 303 redirect stays exactly as delivered — no fetch/JSON refactor, no change to authorization, CAS, validation or business outcomes. Only two things move: **where** the redirect points and **how** the outcome is announced.

The destination is always derived server-side from data the route already trusts — the route param `id`, or the submitted `action`+`id` pair — following the `productFailureTarget` precedent in `src/app/products/route.ts` (14.1.1). No route builds a destination from a client-supplied field; `resolveSettingsReturnTarget` (validated Referer) is reused only where one route legitimately serves several pages, and this task introduces no new use of it. The outcome keeps the closed query-notice vocabulary each area already owns, and the page that now receives the redirect mounts `NoticeToast` with its `<noscript>` `Alert`, as `orders-notices.tsx`/`links-notices.tsx`/`catalog-notices.tsx` already do; where a notice is painted twice today (Nautt, TOTP) the duplicate goes. Typed input survives failure through the 14.1.1 session-draft pattern, which is not catalog-specific and is promoted by F01 to a shared `src/app/form-draft.tsx`; secrets are never drafted, so the Nautt API key is excluded by name.

**Password-change decision — rotate the session, do not sign out.** `pop/specs/administrative-foundation.md:35,82` requires a password change to revoke every session server-side; the `/login?password=changed` landing is a consequence of that revocation, not a separate contract. Revocation stays atomic inside `profile.changePassword`, untouched. The route then issues **one fresh session** for the same actor (`getSessionService().create`, or `createMfaVerified` when TOTP is active so the recorded MFA fact is not silently downgraded), replaces the `qr_session` cookie and lands on `/profile?password=changed`. Every pre-existing session — including the submitting one — is still destroyed, which is the invariant the spec protects and the standard rotation-on-credential-change practice. The `qr_locale` write in that route existed only to carry the locale into an anonymous `/login` landing and goes with it. F01 rewrites `administrative-foundation.md:82` as the contract the wave-2 fronts must satisfy.

## Riscos e condições de aborto

- **Risco:** session rotation weakens the password-change guarantee — mitigação: revocation stays inside the service untouched, the route only issues a new session afterwards, and C06 requires the diff to show both.
- **Risco:** a redirect built from client input becomes an open redirect — mitigação: C07 rejects any destination not derived from a route param or the submitted `action`/`id`.
- **Risco:** a new legacy notice key breaks `/links` strict canonicalization — mitigação: it enters the closed set of `resolveLinksDirectoryQuery` like the V2 key, with its test.
- **Fora de escopo, declarado:** `POST /orders-v2` (ad-hoc create) has no UI caller and its `/orders?orders-v2=created` landing sits outside the closed notice set; `/admin/users/[id]/{role,status,password,delete}` stay byte-frozen by `administrative-foundation.md:61` and no admin mutation lands on `/`. Both are follow-up findings, not work here.
- **Abortar se:** honouring an on-page return would require changing an authorization, CAS or validation outcome — sinalizar `blocked: true` com o trecho da spec em conflito.
