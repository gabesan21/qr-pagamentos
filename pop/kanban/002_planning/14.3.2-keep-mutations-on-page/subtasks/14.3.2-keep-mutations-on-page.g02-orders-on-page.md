## O que entregar

1. **Destination.** Every branch of `POST /orders-v2/[id]` — `append-comment`, `edit-comment`, `set-outcome`, the unsupported-action fallback and the catch — returns to `/orders/v2/<id>` carrying the existing closed notice (`commented | comment-edited | outcome-set | failed`). The id comes from the route param and nothing else; `edit-comment` is no exception, since the comment belongs to the order in the path. Authorization, CAS, the opaque single failure and the `401`/`403` shapes stay byte-identical, and the redirect stays a native 303.
2. **Announcement.** The detail page accepts `searchParams`, resolves the notice against the exported closed set (reject anything else by rendering no notice — never widen it), and renders the existing `OrderV2Notice`, which already pairs `NoticeToast` with its `<noscript>` `Alert`. `/orders` keeps its own notice rendering untouched.
3. **Typed input.** The comment composer, the per-comment edit form and the outcome note are free text that a failure currently discards. Give each one a draft guard from the shared primitive, keyed to its own form and restored only under the `failed` notice, following the catalog precedent. A guard observes the native submit; it never intercepts it, never turns the form into a controlled component and never changes the posted payload.

Vocabulary, dialog structure and the outcome-editor redesign are **not** this task — the audit rows about `<details>` forms and template vocabulary belong elsewhere. Touch composition only as far as mounting the notice and the guards requires.
