## O que entregar

1. **V2 create.** `POST /payment-links-v2` already receives the created link from the service; on success redirect to that link's detail with the `created` notice. On failure return to `/links/new` with `failed` — the create form, including the `?from=<id>` new-version variant, is where the merchant was, and its typed input is restored from a draft. The identifier is server-generated and never comes from input.
2. **V2 edit and lifecycle.** `POST /payment-links-v2/[id]` returns to `/links/v2/<id>` on every branch — `edited`, `activated`, `deactivated`, unsupported action and the catch — with the id from the route param. Edit failure is the exception that returns to `/links/v2/<id>/edit` so the merchant sees the form that failed, with its input restored; the CAS conflict keeps collapsing into the same opaque `failed` (business semantics unchanged).
3. **Legacy V1.** `POST /payment-links` and `POST /payment-links/[id]` post from `/links` yet land on `/`. Return them to `/links` with a closed legacy notice (`created | revoked | failed`) resolved exactly like the V2 key inside `resolveLinksDirectoryQuery`, so strict canonicalization never sees a stray param. Reuse the existing generic outcome copy; add a dictionary key only for an outcome that has none. Then remove the dashboard's `payment-links` searchParam and its Alert, which no longer has a producer.
4. **Announcement and input.** Each page that now receives a redirect — link detail, edit and new — mounts the links notice component, which pairs `NoticeToast` with its `<noscript>` `Alert`; `/links` keeps the notice rendering it already has for the legacy key. The create and edit forms get a draft guard from the shared primitive, keyed to their own form and restored only under the failure notice, observing the native submit without intercepting it.

Radio cards, product search, running total, live preview and lifecycle guard captions are **not** this task.
