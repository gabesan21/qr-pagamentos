# Plan — [[9.3.1-build-branded-composable-checkout]]

- **Stage:** 002_planning · **Responsible:** planner agent

## Objective and expected result

- **Objective:** deliver the branded composable public checkout for Commerce V2 payment links (`PRODUCT_LINES` and `FIXED_AMOUNT`): the sessionless V2 checkout execution over `checkout_attempt_v2` (the wiring `src/checkout/AGENTS.md` reserves for this task), the additive V2 branch of the existing checkout/status API routes, and the two-column branded `/pay/[identifier]` experience — server-derived exact totals, policy-driven customer fields, PIX QR/copy, capability status polling, merchant theme/logo — in `pt-BR`/`en`, with zero trust in browser price/currency/total/status.
- **Observable result:** a buyer opening a V2 link (merchant-created or 9.1.3-issued) at `/pay/[identifier]` sees the merchant-branded two-column summary, submits the policy-exact customer form, receives QR/copy-paste from `POST /api/payment-links/[identifier]/checkout`, and polls `/checkout/status` to a terminal state. V1 links render and behave byte-identically. `pnpm check`, the new `checkout:evidence` pair, and `pnpm db:test` are green.

## Strategy

Mirror the delivered V1 checkout end to end, additive V2 branches only, per the precedent set by `GET /api/payment-links/[identifier]`. Pinned decisions the executor must not revisit:

1. **Route placement: `/pay/[identifier]` stays the single canonical public checkout route.** The page resolves V1 presentation first (render path byte-stable), then the new V2 presentation; only one opaque unavailable view when neither resolves. This makes 9.1.3's cart redirect land correctly with no 9.1.3 change. No new page route, no `[lang]` surface.
2. **API: additive V1-first V2 branches on the two existing routes** (`POST /api/payment-links/[identifier]/checkout` and `/checkout/status`), exactly the GET-route pattern. **Zero edits to `src/security/public-rate-limit.ts` and `src/observability/server-request-log.ts`** — both already wrap these literal templates. Outcome matrix mirrors V1: empty `400`/`404`/`503`, `201`/`202` with `{ payment, statusCapability }`, status `200`/one opaque `404`; `no-store` on every outcome; limiter decides before parsing.
3. **New additive service files in `src/checkout/`; the six delivered files stay byte-untouched.** `public-checkout-v2.ts` (reservation/replay/capability over `checkout_attempt_v2`), `payment-status-v2.ts` (capability status over the V2 attempt + `order_v2` + provider order), `public-checkout-v2-presentation.ts` (page read, decision 5). Fences mirror V1 (`public-checkout.ts`): one reservation transaction; link row `FOR UPDATE`; `SINGLE_USE` rejected when a `payment_link_v2_single_use_settlement` claim exists; HMAC retry/request verifiers; replay reissues only an unexpired, unrevoked capability of an active, unexpired link — never re-quotes or re-dispatches; 24h capability TTL bounded by link expiry; no transaction across provider I/O; `INDETERMINATE` on ambiguous dispatch. Consumes delivered seams only: `createFromLink` and `totalFromLines` (`src/orders/order-v2.ts`), `normalizeCustomerSnapshotV1`, the owner pricing-orders adapter, the registry pair. Order shaping stays inside `createFromLink`; no schema change.
4. **Server-derived totals, closed browser body.** Quote amount is the locked link's exact total (`totalFromLines` over snapshot lines, or the fixed amount) — never anything browser-supplied. The browser body is exactly `{ idempotencyKey, customer }`; the customer snapshot is normalized against the owner's locked `checkoutDataPolicy` (policy variants `NONE`→`NAME_EMAIL_CPF_ADDRESS`).
5. **Two-column branded composition, branding from persisted owner settings.** Item-summary column (server-rendered): merchant logo via `/media/[identifier]` with the `BrandIdentity` fallback, localized display name, composition lines (localized title/description, quantity, exact-decimal unit prices) or the fixed bilingual description, the exact-decimal total with `tabular-nums`, and the server-resolved display currency code (locked pair → active registry code; unmapped → explicit unlabeled, never a fallback code). Customer/payment column: policy form, then QR/copy/status. Columns stack on mobile. Branding resolves from the link owner's persisted storefront settings with design-system defaults (`themeId ?? DEFAULT_STOREFRONT_THEME_ID`, accent null → no override), **independent of the storefront-enabled flag** (branding ≠ store published) — flagged for the critical 003 gate. Theme applies through the delivered mechanism only: scoped `data-theme-preview` + the validated `--storefront-accent` declaration at the page root; `scripts/check-design-tokens.mjs` gains exactly one appended whitelist entry for the `/pay/[identifier]` V2 branch. No new token, primitive, or theme abstraction.
6. **Mirror V1 UX; import-only reuse.** The V2 client component mirrors `public-checkout-form.tsx` (idempotency-key retry semantics, clipboard feedback, `aria-live` status) and imports the exported `createPollingController` — zero V1 file edits. Closed client state set: accept states `RESERVED`/`CREATING`/`PENDING`/`INDETERMINATE` (waiting treatments) plus the unchanged V1 terminal set (`CONFIRMED`/`REJECTED`/`CANCELLED`/`EXPIRED`/`REFUNDED`); polling cadence identical (5s, visibility-aware, `1s·2^n` backoff, 3 failures → status-error + manual retry, `404` → one opaque unavailable). Submit `404` → opaque unavailable; `503`/network → opaque retryable error. Consumed `SINGLE_USE` links render the opaque unavailable view — the explicit paid view is **9.3.2's**, out of scope.
7. **Dictionary/theme sharing split (epoch requirement for 9.2.2 ∥ 9.3.1).** Per-domain dictionary ownership: 9.3.1 owns additions to `src/i18n/dictionaries/checkout/{en,pt-BR}.ts` only (V2-only keys: summary/total/lines/branding headings; reuses V1 state labels and policy copy verbatim); 9.2.2 owns `storefront/*` additions — disjoint files, parity pinned by `dictionaries.test.ts`. Shared theme integration is the already-delivered storefront/design-system mechanism (`--storefront-accent` + theme scoping + token-check whitelist), consumed as-is by both tasks; each appends only its own route's whitelist entry. No new shared module is created by either task.
8. **States per ui-change/DESIGN.md.** `loading.tsx` skeleton; opaque unavailable; `error.tsx` + retry; all five policy variants; inline validation (`FieldError`); submitting (disabled + `Spinner`, one primary action per section); waiting-for-payment-data; QR + copy with success/error feedback; polling status-error + manual retry; expired-capability opaque unavailable; terminal views (CONFIRMED success vs destructive failure badge). 320px fit, ≥44px targets, visible focus, labels above inputs, non-color status markers, polite announcements, QR alt text. Compose only the existing inventory (`Card`, `Field`/`Input`, `NativeSelect`, `Alert`, `Badge`, `Button`, `Spinner`, `Separator`, `Skeleton`).
9. **Evidence without provider calls.** New `checkout:evidence` / `checkout:evidence:verify` pair following the delivered pattern (compose harness, disposable DB seeded directly, themes × locales × 375/768/1440, axe). Live covers both compositions, all policy variants, branding (logo set/unset, accent, themes), unavailable/error; QR/polling/terminal states run against seeded `checkout_attempt_v2` + `order_v2` + `provider_order` rows with the capability HMAC computed by the harness from its own disposable `NAUTT_ENCRYPTION_KEY`. Live submit → provider dispatch stays covered by service/route/db tests.

## Risks and abort conditions

- **Risk:** sessionless trust regression (browser amount/currency/total/status reaches payable facts) — mitigation: decision 4 closed body + server derivation + absence assertions; 005 re-reads against the epoch Pause-if line.
- **Risk:** V1 drift via shared routes/page/polling — mitigation: additive V1-first branches, import-only reuse, V1 render path byte-stable; orchestrator diff check proves it (criterion 5).
- **Risk:** redaction regression in the presentation read (owner/pair/provider/state data leaks) — mitigation: whitelist DTO typing + absence assertions; 005 verifies against the amended boundary.
- **Risk:** decision 5's branding-when-storefront-disabled or the route-branch edits are rejected at the critical 003 gate — replan with the alternative (branding only when enabled / design-system default brand; or V2-only sub-route) and record the divergence.
- **Risk:** evidence capability seeding proves infeasible — fallback: seed via the app's disposable environment exactly as the storefront harness does; if still infeasible, signal `blocked: true`, never stub app code.
- **Abort if:** 9.1.3 or 9.2.2 merges mid-execution with a divergent shared contract (redirect target, dictionary/theme ownership) — signal `blocked: true` with the diff evidence and replan.
- **Abort if:** the branded page cannot be delivered within the existing token mechanism + one whitelist entry — signal `blocked: true` with evidence.
