# Plan — [[8.2.3-add-payment-link-order-drilldown]]

- **Stage:** 002_planning · **Responsible:** planner agent

## Objective and expected result

- **Objective:** Give the merchant a per-link order drill-down: an owner-scoped LINK-order count on the 8.2.1 link directory rows and `/links/v2/[id]` detail, navigation from a link into its orders, and a read-only link-filtered order list + order detail with the same opaque "unavailable" outcome for cross-owner, malformed, or mismatched identities.
- **Observable result:** On `/links` and `/links/v2/[id]` the owner sees how many orders each link generated and can open `/links/v2/[id]/orders` (bounded, keyset-paginated list riding 8.3.1's exact `link` filter) and `/links/v2/[id]/orders/[orderId]` (read-only detail). Another owner's link or order, or an order not belonging to the link, renders the identical unavailable state.

## Strategy

Two additive slices over delivered contracts, nothing new persisted. F01 extends the 8.2.1 projection (`src/auth/payment-link-v2-view.ts`) with one read-time `orderCount` (count of the link's `LINK`-source `order_v2` rows, all states — "orders this link generated"; the confirmed subset is already the derived `paid` signal). The count rides the existing `orders` relation select and the `(payment_link_v2_id, created_at, id)` index; per-page cost stays bounded by the directory page size. F02 builds the surface entirely under the links subtree: count column/detail row + "view orders" navigation, plus `/links/v2/[id]/orders` and `/links/v2/[id]/orders/[orderId]` server pages. The list page re-uses `queryOwnerOrderV2Directory` with its `path` parameter pointed at the drilldown route and the `link=<identifier>` filter force-bound server-side (never trust a client-supplied link value); the detail page re-uses `order-v2-view.ts`'s `getForOwner` and renders unavailable unless the returned summary's `paymentLinkV2Identifier` equals the route link identifier. No new mutation route, no rate-limit or server-request-log change (pages only), no rendering under `/orders` — the full orders management UI stays with 8.3.3. The drilldown is intentionally minimal: 8.3.3 may later subsume navigation toward `/orders?link=…`; the plan does not pre-build that.

## Risks and abort conditions

- **Risk:** count semantics drift (total vs confirmed) — mitigation: one documented `orderCount` = all `LINK`-source orders; `paid` derivation untouched.
- **Risk:** future collision with 8.3.3's `/orders` UI — mitigation: drilldown isolated under `/links/v2/[id]/orders`; spec notes 8.3.3 may later repoint navigation.
- **Abort if:** 8.3.1's directory rejects the custom `path` or exact `link` identifier filter as merged on `develop` — set `blocked: true` with the failing call evidence; never patch `order-v2-directory.ts` inside this task.
- **Abort if:** the 8.2.1 projection no longer exposes the `orders` relation/select extension point assumed above — `blocked: true` with the diff.
