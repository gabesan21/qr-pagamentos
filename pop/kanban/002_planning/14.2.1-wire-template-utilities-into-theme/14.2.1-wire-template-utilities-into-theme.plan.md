# Plano — [[14.2.1-wire-template-utilities-into-theme]]

- **Etapa:** 002_planning · **Papel:** `pop-planner` (separado da execução)

## Objetivo e resultado esperado

- **Objetivo:** project the template's utility vocabulary into Tailwind 4 `@theme inline`, add the four missing feedback `*-soft` CSS projections, and make `accent` mean the **strong** template accent while the pale tint keeps a name of its own — migrating the shadcn consumers that relied on the old meaning.
- **Resultado observável:** `bg-bg`/`bg-surface`/`bg-surface-2`, `text-text`/`-2`/`-3`, `bg|text|border-accent` with `accent-fg`/`accent-soft`, `success|warning|danger|info` plus every `-soft`, `rounded-card`/`rounded-pill`, `shadow-card`, `font-display`/`font-money`, `max-w-app`/`max-w-checkout`/`max-w-auth-form` are real utilities in all six themes with no component branching; `src/app/not-found.tsx` — already authored in this vocabulary — stops being dead CSS; `node scripts/generate-design-tokens.mjs --check` and `node scripts/check-design-tokens.mjs` stay green.

## Estratégia

The DTCG source already carries every value this task needs: `color.action.accent`, `color.action.foreground`, `color.action.soft`, `color.feedback.<x>.soft` and the `radius`/`font`/`layout`/`shadow` semantics all resolve today. So **no token JSON is edited and no audit primitive moves**: the gap is purely projection. Two mechanical steps, in this order.

1. **Projection.** `THEME_PROJECTION` in `scripts/generate-design-tokens.mjs` gains exactly four entries — `color-feedback-{success,warning,danger,info}-soft` → `color.feedback.<x>.soft` — and the generated region of `src/app/globals.css` is rewritten **only** by running `node scripts/generate-design-tokens.mjs`. Every other CSS variable the vocabulary needs (`--color-action-accent`, `--color-action-foreground`, `--color-action-soft`, `--color-surface-*`, `--color-text-*`, `--radius-panel`, `--radius-pill`, `--font-display`, `--font-numeric`, `--shadow-elevation-card`, `--shell-max`, `--checkout-max`, `--auth-form-max`) is already emitted per theme block and per `[data-theme-preview]`.
2. **`@theme inline`.** New entries bind utility names to those variables — never to literals, which `check-design-tokens.mjs` would reject since this block sits outside the generated markers. Roles are fixed: `--color-bg`←page, `--color-surface`←raised, `--color-surface-2`←secondary, `--color-text`←text primary, `--color-text-2`←text secondary, `--color-text-3`←`color.text.tertiary` (the AA projection, never the audit primitive), `--color-accent`←`color.action.accent`, `--color-accent-fg`←`color.action.foreground`, `--color-accent-soft`←`color.action.soft`, `--color-danger`/`--color-info`←`color.feedback.*`, each `--color-<role>-soft`←`color.feedback.<role>.soft`, `--radius-card`←`--radius-panel`, `--radius-pill`, `--shadow-card`←`--shadow-elevation-card`, `--font-display`, `--font-money`←`--font-numeric`, `--container-app`/`--container-checkout`/`--container-auth-form`←`--shell-max`/`--checkout-max`/`--auth-form-max`.

**Accent decision (pinned).** `--color-accent` is repointed from the pale `--accent`/`color.action.soft` to the strong `color.action.accent`, and the pale tint keeps the name the template itself gives it — `accent-soft` — so no third vocabulary is invented and the three `active:bg-accent` variants in `button.tsx` plus `has-data-checked:bg-accent` in `field.tsx` migrate to `bg-accent-soft` (same rendered color as today, so no visual change on those controls). `--color-accent-fg` is the AA-projected `color.action.foreground`, not the audit `accent-fg`: `scripts/design-tokens.test.ts` already asserts that pair at ≥4.5:1 in all six themes. The legacy shadcn `--color-accent-foreground` is left untouched and unused; the DOX records that it is not the on-accent foreground.

Theme entries whose name equals an existing generated variable (`--radius-pill`, `--font-display`) are safe: Tailwind emits `@theme` into `@layer theme`, and the unlayered `:root` blocks of `globals.css` win the cascade — the file already ships `--color-text-secondary` and `--color-text-tertiary` under exactly this pattern. `not-found.tsx` is **not edited**: it already spells `rounded-card border-border bg-surface shadow-card text-accent font-display text-text text-text-2`, so leaving it byte-identical is what proves the wiring. No page migrates and no route BEM is deleted here.

## Áreas afetadas

- `scripts/generate-design-tokens.mjs` — four `THEME_PROJECTION` entries for the feedback soft roles.
- `src/app/globals.css` — hand-edited `@theme inline` block; generated region only via the generator.
- `src/components/ui/button.tsx`, `src/components/ui/field.tsx` — the four `bg-accent` occurrences that meant the pale tint; `DESIGN.md`, `src/components/ui/AGENTS.md` and `pop/specs/application-frontend-system.md` — the vocabulary and the accent rule as durable memory.

## Riscos e condições de aborto

- **Risco:** a `bg-accent`/`text-accent` consumer escapes the grep (dynamic class) and turns solid — mitigação: grep `accent` across `src/**/*.tsx` and `src/**/*.css` before and after; the DOX line keeps a future shadcn update from silently reintroducing the pale meaning.
- **Risco:** `node_modules` absent, so `pnpm exec tsc`/`eslint` cannot run — mitigação: the two node-only scripts are the primary evidence; after two attempts, apply the stop rule (record `ambiente`, reclassify criteria 8 to `verify: user`) instead of building infrastructure.
- **Abortar se:** the vocabulary would require a new DTCG token or a change under `src/design-system/tokens/**`, or if AA forces `accent-fg` onto the audit `accent-fg` primitive — sinalizar `blocked: true` with the failing path and ratio; both change this task's premise.
