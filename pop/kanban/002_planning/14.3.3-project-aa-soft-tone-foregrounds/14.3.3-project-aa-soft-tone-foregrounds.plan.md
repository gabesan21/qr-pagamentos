# Plano — [[14.3.3-project-aa-soft-tone-foregrounds]]

- **Etapa:** 002_planning · **Papel:** `pop-planner` (separado da execução)

## Objetivo e resultado esperado

- **Objetivo:** give every soft-tinted surface an AA-projected on-soft foreground token, derived by the spec's `k`-step method in all six themes, wired through the generator and `@theme inline`, and consumed by every text-on-soft consumer — without touching a single audit primitive.
- **Resultado observável:** the four pairs the 14.2.5 gate measured below 4.5:1 (pix-paper `danger` 4.21 / `info` 4.40, cashier-daylight `success` 4.41 / `warning` 4.41) and the accent drag-over tile clear 4.5:1, while the pill keeps a tone-colored label instead of collapsing to primary text.

## Estratégia

The defect is not a missing concept: `color.feedback.<tone>.soft-foreground` already exists in `src/design-system/tokens/semantic.tokens.json`, but it is a placeholder aliasing `{theme.color.text-primary}`, absent from `THEME_PROJECTION`, absent from `@theme inline`, and consumed by nobody — so `status-badge.tsx` paints `text-<tone>` (the strong role) on `bg-<tone>-soft`. Keep the DTCG path the schema already prefers (`soft-foreground`, sibling of `foreground`); do not invent `onSoft`.

Replicate the mechanism already used for `color.text.tertiary`, `color.focus.ring` and the strong feedback roles: the projected value is a **stored literal** in `color.primitive.accessibility.<theme>.*` of `themes.tokens.json`, carrying `$extensions."com.qr-pagamentos.contrast".interpolationStep`, re-derived and pinned by `scripts/design-tokens.test.ts`. The generator stays a pure projector and must not compute color; the executor computes every value with the repository's own `deriveAccessibleProjection` from `scripts/design-token-graph.mjs` (a throwaway `node -e`, not a test run), never by hand-typed hex or hand math.

Fixed derivation contract, identical in origin/target convention to the existing strong-feedback projection (`design-tokens.test.ts:167`): origin `O` = the audit tone hex (`color.primitive.audit.template.<theme>.<tone>`; for accent, `accent`), target `P` = the theme's rendered `color.text.primary`, backgrounds = the single rendered soft surface of that same tone, `minimumRatio` 4.5, step semantics as the spec states them (`floor(O + (P - O) * k / 255 + 0.5)` per sRGB byte, first `k = 0..255` clearing the floor). Five roles per theme (`success`, `warning`, `danger`, `info`, `action`) × six themes = 30 new primitives. `action.soft-foreground` is in scope by defect class, not by extension: `image-uploader.tsx:226` renders `text-accent` on `bg-accent-soft`, ≈2.2:1 in pix-paper. Audit primitives stay byte-equal; no test file is written here (see `verify: phase`).

## Riscos e condições de aborto

- **Risco:** `14.2.5` is still in `005_closing` and its branch introduces `src/app/globals-theme-tokens.test.ts` ("exactly the 22 template utility entries") — mitigação: base the worktree on `develop` after 14.2.5 integrates; the count moves to 27 in `14.3.4`, which is expected, not a regression.
- **Risco:** a derived step could land on a hex indistinguishable from `color.text.primary`, erasing the tone — mitigação: record hex and `k` per role and report any `k` reaching 255 instead of silently shipping primary text. Hand-editing the generated region of `globals.css` is the twin risk: only `pnpm tokens:generate` writes lines 18–1180, and `--check` proves it.
- **Abortar se:** a role cannot reach 4.5:1 without leaving the `O → P` segment, or the change would require touching an audit primitive — sinalizar `blocked: true` with the failing theme/role and its measured ratios.
