# Plan — [[9.1.3-issue-storefront-one-time-links]]

- **Stage:** 002_planning · **Responsible:** planner agent

## Objective and expected result

- **Objective:** add a separately rate-limited sessionless cart command that accepts the browser cart for `/store/[slug]`, revalidates store, owner, products, quantities, currency, and limits against locked server state (never trusting browser price/currency/title), and issues one owner-derived SINGLE_USE Commerce V2 link; the browser clears only that store's cart and redirects only after successful issuance.
- **Observable result:** `POST /api/store/[slug]/cart/checkout` turns a valid product-only cart into one active `payment_link_v2` row owned by the storefront owner and answers `201 { paymentLinkIdentifier }`; every failure is the closed opaque 429/400/404 set; the `/store/[slug]` page gains a checkout control that POSTs the local cart, clears `qr-pagamentos:storefront-cart:v1:<slug>` on success, and redirects to `/pay/[identifier]`.

## Strategy

One new sessionless command plus one client control; no new persistence, no provider dispatch, no schema change. Pinned decisions the executor must not revisit (each is a spec amendment reviewed at the critical 003 gate):

1. **Sessionless trust posture — revalidate everything.** The slug is the only browser-supplied identity. The command resolves the owner and storefront-enabled state from persisted rows, maps each opaque `reference` (canonical product UUID) to the owner's active non-archived products, enforces the V2 line bounds (1–20 lines, 1–9,999 integer quantity, per-link product uniqueness), and derives prices, titles, and the currency pair exclusively from product rows and the registry — the browser cart contributes only item identity and quantity. Owner row and dependencies are read under the same service-fenced active-dependency posture as `src/auth/payment-link-v2.ts` creation.
2. **One-time link issuance semantics.** Issuance reuses the delivered `src/auth/payment-link-v2.ts` service server-side (never the owner POST route): immutable `PRODUCT_LINES` composition built from the revalidated cart, `SINGLE_USE` type, active flag on, expiry null (SINGLE_USE settlement is the terminal semantic; 9.3.2 owns terminal-state rendering). Single-currency rule: every line's resolved currency code (product code ?? store default) must be one identical code with an active registry mapping, from which the catalog pair row is derived server-side; mixed or unmapped currencies are the one opaque invalid outcome. Issued links are ordinary merchant-owned V2 rows (visible in the owner directory, deactivatable, `paid`-projected on settlement) — a deliberate, reviewed consequence. No cart table, no order, no attempt, no provider call at issuance: 9.3.1's V2 checkout execution consumes the link.
3. **Custom-amount exclusion.** The command accepts product items only; a payload carrying a `custom-amount` member is the same opaque invalid outcome. The standalone amount keeps 9.2.1's command (`POST /api/store/[slug]/checkout`); the page's cart-checkout control renders only for product-only carts.
4. **Route and inventories.** New route `POST /api/store/[slug]/cart/checkout` (9.2.1 owns `/checkout` and `/checkout/status`; separate commands per the epoch note). Mirror 9.2.1's handler shape: request-log wrap, limiter decision before parsing/locale/service work, `no-store` on every outcome, `dynamic = "force-dynamic"`, no origin guard (sessionless). Additive entries only: one submit-class rate-limit surface (same 12/min class as the other submit surfaces) and one literal request-log route `/api/store/[slug]/cart/checkout`, appended after 9.2.1's merge.
5. **Opaque failure outcomes.** Closed set: empty `429` (limiter), empty `400` (bad JSON, contract violation, mixed kinds, mixed/unmapped currency, stale/unavailable reference, empty cart), empty `404` (unknown/disabled slug or storefront). Success is exactly `201 { paymentLinkIdentifier }` — no owner, amounts, pair UUIDs, or composition echo. Thrown service faults propagate to the request-log `failed` record, never a mapped body.
6. **What the browser receives and does.** On `201` the client boundary clears only that store's cart key and redirects to `/pay/[identifier]` — the canonical public link route. Recorded sequencing fact: `/pay/[identifier]` renders V1 links today and V2 identifiers resolve only through the API branch until 9.3.1 delivers the branded V2 checkout; this task proves issuance, clear, and redirect, not V2 page rendering. On any failure the cart stays intact and one opaque localized error shows.

## Risks and abort conditions

- **Risk:** redaction/authority regression — browser data reaches payable facts, or owner/pair/provider data leaks into the response — mitigation: whitelist response typing, server-only derivation, absence assertions; 005 verifies against the amended boundary.
- **Risk:** V2 link issuance floods the merchant directory with one-time rows — mitigation: deliberate decision 2 reviewed at the critical 003 gate; lifecycle projection already handles SINGLE_USE `paid`.
- **Risk:** `/pay/[identifier]` does not render V2 links until 9.3.1, so the post-issuance landing is the generic unavailable view in the interim — mitigation: recorded sequencing fact (decision 6); abort only if the 003 critic requires a delivered landing page now.
- **Risk:** merge collision with 9.2.1's inventory entries — mitigation: the temporal gate serializes; append-only edits after rebase.
- **Abort if:** the 003 critic rejects decision 2 (real V2 rows per cart checkout) or decision 3 (custom-amount exclusion) — set `blocked: true` with the objection; replan (e.g. ephemeral draft records, or a mixed-cart fork).
- **Abort if:** 9.1.2's delivered cart envelope or 9.2.1's inventories diverge from recon on rebase — set `blocked: true` with the diff evidence.
