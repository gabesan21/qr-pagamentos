# Plan — [[8.4.2-build-merchant-dashboard-ui]]

- **Stage:** 002_planning · **Responsible:** planner agent

## Objective and expected result

- **Objective:** Replace the merchant home (`/`) empty scaffold with the bilingual merchant dashboard that consumes the delivered 8.4.1 projection (`getMerchantAnalyticsService().getForOwner(actor, period)`) and the owner storefront settings read, with KPI hierarchy, accessible sales/funnel/best-seller/per-link compositions, recent activity, period controls, explicit states, and a conditional View Store action.
- **Observable result:** An active merchant opening `/` sees localized sales, funnel, best sellers, link metrics, and recent activity for the selected period (`today`/`7d`/`30d`), explicit empty states when there is no data, and a View Store link to `/store/<slug>` only when the store is enabled with a slug; production evidence proves it across locales, themes, and viewports.

## Strategy

Server-rendered composition only: `src/app/(merchant)/page.tsx` keeps `requireMerchantShellContext()` (principal already re-resolved) and calls the analytics service and `getStorefrontSettingsService().getForOwner(principal)` in parallel — no new route, mutation, client data fetching, or projection change. The period arrives as a `?period=` searchParam over the closed set; absent/unknown values fall back to a pinned default (`7d`), and the service's `invalid-period` kind maps to the same default rendering since UI controls only emit the closed set. Period switching uses plain GET links (no POST, no origin guard, no client boundary); existing notice searchParams handling stays untouched.

Visual rules come from DESIGN.md's PIX-settlement-desk tone: no decorative charts, no generic three-card dashboard, no cross-currency totals, tabular-nums facts. Confirmed and locally finalized sales stay visibly separate (never summed — the spec fence extends to presentation); each currency group renders on its own line with its redacted code/label, and a null code/label gets an explicit localized unlabeled treatment. Any "chart" is a non-decorative ruled/proportional composition whose accessible source is a real table/list — never color-only. Every section has an explicit empty state (zero data is not an error); `loading.tsx` uses owned skeletons. View Store renders only when `storefrontEnabled === true && storefrontSlug !== null` (null settings row = hidden), as the single primary action in the header area, linking to the existing sessionless `/store/[slug]`.

## Risks and abort conditions

- **Risk:** The DTO has no time-series buckets — a trend chart is impossible without a projection change. Mitigation: compose only from delivered aggregates (per-group totals, funnel counts/rates, best sellers, per-link metrics, recent feed); never invent series or widen the projection.
- **Risk:** Populated-state evidence needs deterministic V2 CONFIRMED orders without provider calls. Mitigation: follow the existing disposable-runtime seeding approach of the run-* evidence scripts; if CONFIRMED rows cannot be seeded deterministically, reduce populated evidence to seedable states and record the limitation in the run manifest.
- **Abort if:** The delivered DTO lacks data the card's objective strictly requires (genuine projection gap) — set `blocked: true` citing the missing member; never patch `src/orders/merchant-analytics.ts` opportunistically.
- **Abort if:** `getStorefrontSettingsService().getForOwner` semantics differ from `StorefrontSettingsData | null` as read — report BLOCKED instead of guessing enablement rules.
