Blocking reasons:

1. **The 7.1.2 currency re-gating nit is not addressed anywhere in the plan.** 7.1.2's memory explicitly hands it to this task: "Re-submitting an unchanged stored currency re-gates on the registry (7.1.3 should omit unchanged fields)" (`pop/memory/7.1.2-extend-merchant-store-settings.md`). The service gates whenever the field is present and non-empty (`src/auth/storefront-settings.ts:163`), and the route includes extended fields whenever `form.has(field)` (`src/app/storefront/route.ts:35-37`). The plan describes an always-rendered currency `NativeSelect` and never states that unchanged fields are omitted on submit. Consequence: once a stored currency's mapping is later deactivated, every workspace save carries the stale code, `requireActivePair` throws, and the merchant gets opaque `?storefront=failed` on any settings change — a severity-3 defect baked into the plan. Fix is one plan line: the client omits `storefrontDefaultCurrencyCode` (and any other unchanged extended field) when the value equals the prefilled one; the server already treats absent as unchanged.

2. **Currency read-surface wording is imprecise for a critical plan.** "7.1.1's discriminated UI-prohibition signal" names no real export; the actual surfaces are `listActiveChoices` (empty array when unmapped) and `resolveDefaultChoice`'s `{ status: "unavailable" }`. State explicitly which one the server page consumes and that an empty active list — not a thrown signal — drives the disabled, explained empty state, so the executor does not wire a throwing gating primitive into a render path.

Everything else in the plan is approvable as-is; these are targeted additions, not a replan.
