# 7.1.3-build-store-settings-and-logo-management — Plan

- **Planned:** 2026-07-24 · **Planner:** 002_planning agent

## Objective

Deliver the bilingual merchant store-settings UI over 7.1.2's persistence: one
sectioned Storefront workspace in the existing `/settings` route covering
identity (slug + bilingual display names), appearance (six-theme choice with
live preview, boxed/table layout, accent color, logo upload/replace/remove with
official fallback), payments (storefront + standalone toggles), and default
currency with a disabled-when-unmapped state. The UI posts only to the existing
`POST /storefront` opaque contract plus one new logo-upload route; it adds no
new mutation semantics and never touches 7.1.2's service/route logic, media
internals, or the schema.

## Strategy

One cohesive executor, four sequential sub-fronts in one delivery. Recon first:
7.1.2 is in 004 execution — read its **merged** `src/app/storefront/route.ts`
and `src/auth/storefront-settings.ts` for the exact accepted form-field names
and the theme-id export before writing any form control. If 7.1.2 has not
landed, the task is `BLOCKED`; never code against the plan alone.

1. **Page structure (existing route, no shell change).** The merchant
   `/settings` page (`src/app/(merchant)/settings/page.tsx`) keeps its place in
   the fixed five-entry navigation; the existing
   `src/app/storefront-settings-management.tsx` card grows into the sectioned
   Storefront workspace (one `Card` per section, `Separator` between, ruled
   PIX-ledger composition per DESIGN.md):
   - **Identity** — slug + both display names, byte-identical field names and
     semantics to today (legacy contract preserved).
   - **Appearance** — theme `NativeSelect` sourced from 7.1.2's design-system
     theme-id export (never duplicate the six literals), layout
     `NativeSelect` (`boxed`/`table`), accent `Input` (existing), and the logo
     block. A **live preview** (below) sits in this section.
   - **Payments** — existing `storefrontEnabled` `Checkbox` plus the new
     `storefrontStandalonePaymentsEnabled` `Checkbox` (default checked, matching
     the persisted `DEFAULT true`); each with a bilingual help line stating the
     toggles are independent (disabled store keeps payment links reachable).
   - **Default currency** — `NativeSelect` of the registry's active redacted
     `{ code, label }` choices plus a "no default" clear option. The server page
     consumes `getSupportedExchangeCurrencyService()` read-only; when it
     signals no active mapping (7.1.1's discriminated UI-prohibition signal),
     the control renders **disabled** with an explanatory
     `FieldDescription`/`Alert` ("no exchange currency is configured yet; an
     administrator must register one") — missing configuration is a normal,
     explained state, never an error and never a hidden control.
   - Exactly one primary `Button` ("save storefront settings") submits the whole
     workspace to `POST /storefront` (absent=unchanged merge makes one save
     safe); outcomes stay exactly the opaque `?storefront=changed|failed|
     conflict` alert the page already renders.
2. **Logo UX (upload → STAGED → ACTIVE on save).** New route
   `POST /storefront/logo` (`src/app/storefront/logo/route.ts`): origin-guard
   first, re-authorizes the cookie merchant principal, accepts one
   `multipart/form-data` file, calls `getMediaService().create(actor,
   "STOREFRONT_LOGO", bytes)`, and returns only empty `401`/`403` or opaque
   relative redirects — success `/settings?storefront-logo=staged&logo=
   <identifier>` (the identifier is the public-safe media handle 7.1.2 persists,
   so carrying it in the redirect leaks nothing), failure
   `/settings?storefront-logo=failed` with no cause. The settings page reads the
   staged identifier from `searchParams`, feeds it to a hidden
   `storefrontLogoMediaIdentifier` input in the main form, and previews it via
   `GET /media/[identifier]` (owner may read `STAGED`). The main save then
   activates it and orphans the replaced logo (7.1.2's job). **Removal/clear**
   is client-side only: a "remove logo" `Button` (secondary variant) empties the
   hidden input — explicit empty clears on save per 7.1.2 — and the preview
   reverts to the official `BrandIdentity` `merchant-fallback` lockup (never a
   page-local mark). The hidden input always submits (identifier, staged value,
   or empty). Client-side hints mirror, never replace, server validation: the
   file `Input` carries `accept="image/jpeg,image/png,image/webp"` and a
   bilingual help line stating accepted types and the ≤5 MiB / ≤4096×4096
   bounds from `src/media/AGENTS.md`. A staged-then-abandoned logo stays
   `STAGED` against quota until media reconciliation — accepted and documented,
   same posture as 7.1.2's quota-leak window.
3. **Live theme/accent/layout preview (no page-local marks, no per-theme
   assets).** Generated tokens today scope to `:root[data-theme="…"]` only, so
   an in-page preview needs one additive design-system contract change:
   `scripts/generate-design-tokens.mjs` emits each theme block under an
   additional scoped selector `[data-theme-preview="<id>"]` alongside
   `:root[data-theme="<id>"]` (deterministic projection; `pnpm tokens:check`
   and the resolver-equality contract test keep both honest). The preview is a
   miniature storefront mock inside a `data-theme-preview` container — header
   rail with logo (or official fallback lockup) + store name, one sample
   product card, one primary action — composed exclusively from semantic token
   classes and existing primitives; sample copy is dictionary fixture text
   labelled as preview. Accent preview reuses the storefront mechanism: extend
   the single allowlisted inline declaration in
   `scripts/check-design-tokens.mjs` to also accept
   `style={{ "--storefront-accent": … }}` in the new preview component (same
   shape as the `/store/[slug]` exception; no other inline style anywhere).
   Layout choice swaps the mock between boxed and table arrangements. One
   focused client boundary (extending the existing
   `StorefrontSettingsManagement` pattern) observes the native form's
   `input`/`change`/`submit` events to drive the preview, announces busy state,
   and disables the whole form after the browser forms the payload — it never
   intercepts the POST.
4. **Dictionaries, states, evidence.** All new copy lands in
   `src/i18n/dictionaries/storefront/{en,pt-BR}.ts` (parity enforced by the
   existing dictionary tests); evidence follows the `profile.evidence.spec.ts`
   run-bound pattern (below).

### Mandatory states (ui-change §3, per interactive component)

- **Default/populated:** every field prefilled from `getForOwner`; theme/layout/
  currency selects resolve stored values with the service fallback chain
  (NULL theme → `pix-paper` shown as default choice; NULL layout → `boxed`).
- **Loading:** page-level owned `Skeleton` composition (`loading.tsx` beside the
  settings page if absent) and `Spinner` in the busy save/upload buttons.
- **Empty:** no logo → official merchant-fallback lockup in preview and logo
  block; no active currency mappings → disabled select + explanation (this *is*
  the currency empty state); storefront never enabled → identity section still
  fully editable with its existing help text.
- **Error:** opaque destructive `Alert` from `?storefront=failed|conflict` and
  `?storefront-logo=failed`; no validation detail, no uploaded-file echo
  (failure re-renders the last persisted logo, never the rejected file).
- **Success:** existing `?storefront=changed` status `Alert`; upload success is
  the visible staged preview plus a polite status line, not a second alert.
- **Hover/focus/disabled:** owned primitives only; visible ≥2px focus; the
  pending scope disables every control in both forms after payload formation;
  the currency select's disabled state is visually distinct and explained.

### Dictionary key plan (both locales, `storefront` domain)

Section headings/descriptions (`storefrontIdentityHeading`,
`storefrontAppearanceHeading`, `storefrontPaymentsHeading`,
`storefrontCurrencyHeading` + `…Description`); theme
`storefrontThemeLabel`/`…Help` with per-theme bilingual descriptor keys keyed by
theme id; `storefrontLayoutLabel` + `storefrontLayoutBoxed`/`storefrontLayoutTable`;
logo `storefrontLogoLabel`, `…Help` (types + size bounds), `…Upload`,
`…Remove`, `…Staged` (status line), `…UploadFailed`, `…FallbackAlt`;
currency `storefrontCurrencyLabel`, `…Help`, `…None` (clear option),
`…Unavailable` (disabled explanation); payments
`storefrontStandalonePaymentsLabel`/`…Help`; preview fixture keys
(`storefrontPreviewSample*`) marked as preview copy.

### Accessibility and evidence

- WCAG 2.2 AA by construction: labels above inputs, one primary action per
  section, ≥44×44 targets, 4.5:1 text / 3:1 focus contrast inherited from the
  token evidence, reduced motion, 320px fit, keyboard traversal through both
  forms, color never the only cue (preview changes are decorative; state is in
  text). The logo `img`/lockup carries the localized fallback alt; a staged
  logo's accessible name never exposes the identifier.
- Evidence: new `tests/store-settings.evidence.spec.ts` +
  `scripts/run-store-settings-evidence.mjs` /
  `scripts/verify-store-settings-evidence.mjs` +
  `store-settings:evidence[:verify]` package scripts + `artifacts/store-settings/`,
  cloned from the profile evidence contract: run-bound manifest, six themes ×
  two locales × 375/768/1440 captures of the settings workspace, plus
  interaction captures for staged-logo preview, remove→fallback, currency
  disabled-when-unmapped (the disposable runtime's natural state), keyboard
  traversal, and click/Enter single native POST with immediate busy/disabled.
  axe serious/critical, overflow, 44px, external-request, and console gates as
  in profile evidence; review manifest-hash-bound. If the disposable runtime
  can seed an active mapping through existing admin mutations, capture the
  enabled currency state too; otherwise that state is covered by component
  tests and recorded as a declared evidence gap.
