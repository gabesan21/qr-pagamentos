# Plan — [[9.2.2-build-standalone-payment-experience]]

- **Stage:** 002_planning · **Responsible:** planner agent

## Objective and expected result

- **Objective:** build the bilingual buyer experience for standalone (link-less) store payments on top of 9.2.1's delivered sessionless routes: amount entry, the owner-policy customer form, QR/copy-paste, capability polling with retry, every terminal/failure state, and the return-to-store path — under the epoch's zero-trust sessionless posture and the merchant's theme/branding.
- **Observable result:** from an enabled storefront's custom-amount item a buyer reaches `/store/[slug]/pay`, enters an amount and the policy-exact customer fields, receives the PIX QR/copy-paste from `POST /api/store/[slug]/checkout`, watches status via `/status` polling until a terminal state, and can return to the store — in `pt-BR`/`en`, themed like the storefront, on mobile and desktop. `pnpm check`, the new evidence pair, and `pnpm db:test` are green.

## Temporal gate (explicit)

**004 starts only after BOTH `task/9.1.2-build-storefront-catalog-and-cart` AND `task/9.2.1-implement-standalone-payment-orders` are merged into `develop`.** The plan below is written against their delivered contracts (9.2.1: routes, attempt model, capability/TTL; 9.1.2: storefront page, cart module, `standalonePayments` + `standalonePaymentCurrencyCode` projection members). If either merges with a different contract, replan before executing.

## Strategy

SSR page + one focused client boundary, mirroring the delivered V1 `/pay/[identifier]` UX; 9.2.1's HTTP routes are the only data/action channel. Pinned decisions the executor must not revisit:

1. **Page placement: new sessionless route `/store/[slug]/pay`.** A dedicated App Router page (`force-dynamic`, unlocalized, no-store posture inherited from the API routes) owns the whole standalone journey; the storefront custom-amount card (9.1.2) gains one pay action linking to `/store/[slug]/pay?amount=<draft>` — the query value is prefill only, revalidated client-side against the canonical amount grammar and again server-side by 9.2.1. "Return experience" is a localized link back to `/store/[slug]` present on waiting, failure, and terminal views. No new API route, and **zero edits to `src/security/public-rate-limit.ts` and `src/observability/server-request-log.ts`** (9.2.1/9.1.3 own those inventories; the page is SSR, outside both).
2. **Policy reaches the page through one additive projection member.** 9.2.1 derives `checkoutDataPolicy` from the locked owner server-side, but the form must know it before rendering. Add `checkoutDataPolicy` to `src/storefront/public-storefront.ts`'s redacted DTO — the same public-safe exposure V1 already ships via `public-checkout-presentation.ts` (`checkoutPolicy`). This is the task's single deliberate redaction-boundary amendment (spec + root `AGENTS.md` at closeout; flagged for the critical 003 gate). No new presentation read, no inventory change.
3. **Mirror V1, reuse without editing.** The client component mirrors `src/app/pay/[identifier]/public-checkout-form.tsx` structure (policy-driven fields, idempotency-key retry semantics, clipboard copy with feedback, `aria-live` status region) and **imports the exported `createPollingController`** — zero edits to any V1 file. Closed client state set is the union of 9.2.1's accept states (`RESERVED`, `CREATING`, `PENDING`, `INDETERMINATE`) and the V1 status vocabulary (`CREATED`, `PENDING`, `INDETERMINATE`, `CONFIRMED`, `REJECTED`, `CANCELLED`, `EXPIRED`, `REFUNDED`); `RESERVED`/`CREATING` render the waiting treatment; the terminal set is unchanged. Polling cadence mirrors V1: 5s interval, visibility-aware pause, `1s·2^n` backoff, 3 consecutive failures → localized status-error with manual retry, `404` → the one opaque unavailable view. Same opaque `404` treatment for submit unavailability; `503`/network → opaque retryable error. Never trust browser owner/currency/total/status: the body is exactly `{ idempotencyKey, amount, customer }`.
4. **Theme/branding reuse only.** The page scopes `data-theme-preview={themeId}` and the validated `--storefront-accent` declaration at its root, renders the logo via `/media/[identifier]` or the `BrandIdentity merchant-fallback` exactly as the storefront page does, and composes only existing primitives (`Card`, `Field`/`Input`, `NativeSelect`, `Alert`, `Badge`, `Button`, `Spinner`, `Separator`, `Skeleton`). `scripts/check-design-tokens.mjs` gains the new route in its existing exact-declaration whitelist (same mechanism, no new visual value). No new token, primitive, or 9.3.1 composable-checkout surface — per the epoch note, the shared theme/dictionary integration is assigned as: 9.2.2 consumes the delivered storefront mechanisms as-is and creates no competing one.
5. **States per ui-change/DESIGN.md.** Loading skeleton (`loading.tsx`); opaque unavailable (unknown/disabled slug, standalone off — same null projection outcome); opaque error + retry (`error.tsx`); amount empty/invalid (canonical grammar, inline `FieldError`); policy variants `NONE`→`NAME_EMAIL_CPF_ADDRESS`; submitting (disabled + `Spinner`, one primary action per section); waiting-for-payment-data; QR + copy with success/error feedback; polling status-error + manual retry; expired-capability opaque unavailable; terminal views (CONFIRMED success vs destructive failure badge) each with the return link; 320px fit, ≥44px targets, visible focus, non-color markers. Amounts render as canonical decimal strings with `tabular-nums`, labelled by `standalonePaymentCurrencyCode` (null → unlabeled) — never `Number`/`Intl` money math.
6. **Dictionaries.** Reuse existing `checkout` namespace keys where semantics are identical (state labels, copy/QR/privacy/error copy); add standalone-only keys (amount label/invalid, page heading, pay action, return-to-store) to the `storefront` namespace in both locales — parity pinned by `dictionaries.test.ts`.
7. **Evidence without provider calls.** New `standalone-payment:evidence` / `:verify` pair following the delivered storefront pattern (compose harness, disposable DB seeded directly, themes × locales × 375/768/1440, axe). Live covers amount/policy/validation/unavailable/return states; QR/polling/terminal states run against seeded `standalone_checkout_attempt` + `order_v2` + `provider_order` rows with the capability HMAC computed by the harness from its own known disposable `NAUTT_ENCRYPTION_KEY`. Live submit → provider dispatch stays covered by 9.2.1's route/service tests and is not duplicated.

## Risks and abort conditions

- **Risk:** sessionless trust regression (owner/currency/total/status taken from browser or URL) — mitigation: decision 3 closed body + absence assertions; 005 re-reads against the epoch Pause-if line.
- **Risk:** decision-2 amendment rejected at the critical 003 gate — replan with the alternative (amount-only page deferring policy discovery) and record the divergence; never ship a hidden policy probe.
- **Risk:** V1 drift via shared polling/copy code — mitigation: import-only reuse; orchestrator diff check proves zero V1 edits.
- **Risk:** evidence capability seeding proves infeasible (key material not reachable from the harness) — fallback: seed via the app's own disposable environment exactly as the storefront harness seeds settings; if still infeasible, signal `blocked: true` rather than stubbing app code.
- **Risk:** `RESERVED`/`CREATING` accept states mis-rendered as errors — mitigation: decision 3 union pinned; unit tests per state.
- **Abort if:** 9.1.2 or 9.2.1 merges with a contract different from the one pinned here (route shape, projection members, state vocabulary) — signal `blocked: true` and replan.
- **Abort if:** the themed page cannot be delivered within the existing token mechanism + whitelist extension (would force a new token/primitive) — signal `blocked: true` with evidence.
