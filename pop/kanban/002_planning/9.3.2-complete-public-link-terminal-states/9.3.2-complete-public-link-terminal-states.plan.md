# Plan — [[9.3.2-complete-public-link-terminal-states]]

- **Stage:** 002_planning · **Responsible:** planner agent

## Objective and expected result

- **Objective:** complete the public terminal states of `/pay/[identifier]` for Commerce V2 links: a consumed `SINGLE_USE` V2 link renders an explicit, branded, localized already-paid view, while malformed, unknown, inactive, expired, and otherwise unavailable identifiers keep the one opaque unavailable view with zero lifecycle disclosure.
- **Observable result:** a buyer (or anyone holding the URL) who opens a consumed one-time V2 link sees the merchant-branded paid confirmation with the link's public composition summary and exact total, in `pt-BR`/`en`; every other non-payable state stays indistinguishable from a nonexistent link. V1 links render and behave byte-identically. `pnpm check`, the extended `checkout:evidence` pair, and `pnpm db:test` are green.

## Strategy

Additive terminal branch over 9.3.1's delivered checkout; no new route, no API change. Pinned decisions the executor must not revisit:

1. **V2-only scope.** V1 surfaces stay byte-frozen: the V1 render path, the V1 consumed/unavailable semantics, the V1 presentation service, and every delivered V1 file are untouched. The paid view exists only for consumed `SINGLE_USE` Commerce V2 links. `REUSABLE` links are never consumed (per the spec's consumption semantics) and keep the normal checkout view unchanged.
2. **Paid-view content boundary (deliberate spec amendment, flagged for the critical 003 gate).** The paid view may show exactly: merchant branding (localized display name, logo via `/media/[identifier]` with the official fallback lockup, resolved theme + validated accent — the same resolution as 9.3.1's checkout branding, independent of the storefront-enabled flag), one explicit localized already-paid statement, and the link's public composition summary (localized product lines or the fixed bilingual description) with the exact-decimal total and the server-resolved display currency code. It never shows: order/payment state or any timestamp (including settlement date), refund state, customer/payer data, attempt/capability/verifier/retry material, provider data, currency-pair UUIDs, owner identity beyond the public display name/logo, or link internals (version, expiry, active flag). Rationale: the composition and total were already public to any identifier holder while the link was active; the only new disclosure is the single sanctioned bit "this link was consumed", which the roadmap explicitly requires.
3. **Consumption is claim-keyed, never state-keyed.** The paid branch reads only the persisted `payment_link_v2_single_use_settlement` claim. It never joins or exposes live order state, so a later `REFUNDED` (or any state change) never flips, annotates, or degrades the paid view — that would leak lifecycle beyond the sanctioned bit.
4. **Branch placement: extend 9.3.1's delivered V2 presentation read.** The presentation service (9.3.1's `public-checkout-v2-presentation.ts`, or its merged equivalent) gains the consumed check and returns a discriminated outcome — checkout view / paid view / the one opaque null (malformed, unknown, inactive, expired, line-product-unavailable, missing members). The `/pay/[identifier]` page renders the paid view server-side only: no form, no polling client, no mutation affordance. **Zero edits to routes and inventories:** the checkout reservation already rejects a claimed `SINGLE_USE` with its existing opaque outcome, status polling keeps its capability-only contract, the GET resolution route is unchanged, and the rate-limit/server-request-log inventories are untouched.
5. **Composition-only UI, evidence via the delivered pair.** The paid view composes the existing receipt-rail inventory (`Card`, `Badge`, `Alert`, `Separator`, skeletons via the delivered `loading.tsx`) with a non-color paid marker (icon + text), exact-decimal tabular amounts, 320px fit, and both locales; no new token, primitive, or whitelist entry (it renders inside the already-whitelisted V2 page root — if the merged 9.3.1 reality differs, the executor appends nothing without surfacing it). Dictionary keys append to the 9.3.1-owned `checkout/{en,pt-BR}.ts` namespace only. Evidence extends the delivered `checkout:evidence`/`checkout:evidence:verify` pair with consumed-link scenarios (claim seeded directly in the disposable database), themes × locales × 375/768/1440, axe — no new scripts, no `package.json` change.

## Risks and abort conditions

- **Risk:** disclosure creep — the paid view leaks order state, timestamps, refund state, payer data, or provider/pair data beyond the sanctioned composition + consumed bit — mitigation: whitelist DTO typing plus absence assertions (criterion 2); 005 reads the DTO/markup against the amended boundary.
- **Risk:** consumption mis-keyed to live order state, making the view a status oracle (REFUNDED flips it, timing reveals settlement) — mitigation: decision 3 pins the persisted claim as the only signal, with a dedicated test.
- **Risk:** V1 drift via the shared page/presentation branch points — mitigation: additive branches, V1 render path byte-stable, orchestrator diff check (criterion 3).
- **Risk:** 9.3.1's merged shape diverges from its approved plan (file names, branch points) — mitigation: executor binds to merged reality, not this plan's names; if the presentation seam cannot discriminate consumed without touching routes or V1 files, signal `blocked: true` with evidence.
- **Abort if:** the 003 critic rejects decision 2's content boundary — replan with the minimal variant (branding + paid statement only, no composition/total) and record the divergence.
- **Abort if:** the paid view cannot be delivered within the existing token mechanism without a new whitelist entry or inline style — signal `blocked: true` with evidence.
