# Plan — [[10.3.1-implement-user-soft-delete-lifecycle]]

- **Stage:** 002_planning · **Responsible:** planner agent

## Objective and expected result

- **Objective:** define and implement auditable, terminal user soft deletion for both roles: an administrator-only delete lifecycle with final-active-admin safety, atomic session revocation and public-surface withdrawal, permanent identifier retention, an append-only deletion audit record, and untouched historical order/link/product attribution — without weakening any existing redaction, opaque-outcome, or frozen-V1 contract.
- **Observable result:** an administrator can delete a user through a new protected `POST /admin/users/[id]/delete` route; the deleted user can never authenticate or be reached publicly again (storefront and every payment link withdrawn in the same transaction), every session dies atomically, an audit row records actor/target/timestamp, all historical orders keep their owner attribution, and downstream tasks (10.1.1, 10.2.1, 10.2.2, 10.3.2) gain an explicit lifecycle model plus a `deletedAt` field on the admin user DTO to plan against.

## Strategy

One additive migration plus one cohesive service/route extension; no UI (10.3.2 owns the directory and its delete action), no new public surface. Pinned decisions the executor must not revisit (reviewed at the critical 003 gate):

1. **Lifecycle model rides `deleted_at`, not the status enum.** The immutable baseline pins `user_status_closed CHECK (status IN ('ACTIVE','DISABLED'))`, and the safe migration language cannot drop or replace a check — a `DELETED` status is inexpressible and permanently so. Soft deletion is therefore: additive nullable `user.deleted_at` timestamp (application-supplied, like the V2 tables) **plus** `status='DISABLED'` written in the deletion transaction. Effective states: `deleted_at IS NULL` + `ACTIVE` → active; `deleted_at IS NULL` + `DISABLED` → suspended (reversible, existing behavior); `deleted_at IS NOT NULL` → terminally deleted (status stays `DISABLED`). Every existing gate — sign-in (`credential.status !== "ACTIVE"` with exactly-one scrypt preserved), principal resolution, `countActiveAdmins`, `/admin-access` — keeps working byte-identically because deletion always pairs the marker with `DISABLED`.
2. **Terminal — no reactivation.** `changeStatus(..., "ACTIVE")`, `changeRole`, and `changePassword` against a `deleted_at`-marked target are rejected through the same opaque failed/not-found outcomes (the service fences terminality, never a database construct). `DISABLED` remains the only reversible suspension. MFA does not exist in this product (spec defers TOTP) — explicitly out of scope; the card's "session/reset/MFA revocation" resolves to: sessions deleted atomically in the deletion transaction (existing `revokeSessions`), owner-initiated Nautt reset/password routes become unreachable because authentication is impossible, and admin resets are fenced by decision 2.
3. **Withdrawal by service-level writes in one transaction, never by editing frozen reads.** The deletion transaction (under the existing authorization advisory lock, reusing the `mutateAdminSafety` final-admin pattern — a deleted admin is already `DISABLED` and never counted) additionally: sets `storefront_enabled=false` (the `/store/[slug]` projection already resolves only enabled storefronts — withdrawn with zero projection edits); sets `active=false` on every V1 `payment_link` and V2 `payment_link_v2` of the target (the baseline `payment_link_require_active_dependencies` trigger is INSERT-only, so bulk update cannot trip it; `src/auth/payment-link.ts`, the V2 service, and all public reads stay byte-frozen). Products, categories, orders, comments, outcomes, provider data: untouched — attribution rows keep `owner_id`, nothing cascades (FKs are already `Restrict`).
4. **Identifier retention: permanent, no reuse.** Username, nullable email, and storefront slug rows are never rewritten or freed; the existing unique constraints keep them reserved forever. This preserves historical attribution display and audit integrity at zero cost.
5. **Audit via a new append-only table.** `user_deletion` (application-supplied UUID id and timestamp, restrictive FK to `app.user`, actor user id — plain UUID column, no FK, so actor deletion never fences history, `created_at`) with runtime `SELECT`/`INSERT` only, relation-guarded in bootstrap exactly like the V2 append-only tables. One row per deletion, written inside the same transaction.
6. **Media/credential behavior: retained and unreachable.** Zero provider calls and zero decryption at deletion (same posture as the Nautt reset contract). The `nautt_credential` row stays; it is unreachable because the owner can never authenticate and administrators have no owner-credential capability (the denial-only route is untouched). Media objects keep their lifecycle — storefront/product images stop being published because every publishing surface is withdrawn; the opaque 43-character identifiers are the only residual direct-read path, unchanged.
7. **Admin read contract for downstream.** The safe admin user DTO (`toUserDto` source + administration list) gains `deletedAt: Date | null`; the principal-resolution read is unchanged (status gate suffices). Public and merchant projections never expose deletion state — surfaces are withdrawn instead of annotated. Admin global order/link projections (10.2.x) may join owner username + deletion marker through the admin-scoped user read; this task delivers the field and the lifecycle, not those projections.
8. **Route and observability.** `POST /admin/users/[id]/delete` follows the existing `/admin/users/[id]/{password,role,status}` subroute pattern: origin-guard first, re-authorized cookie admin, empty `401`/`403`, opaque `/admin?...` redirects (success/failed, one shared failure cause — including final-admin, unknown, and already-deleted targets), and exactly one new literal `server-request-log` entry. No page, form, or dictionary work.

## Risks and abort conditions

- **Risk:** 9.2.1 migration conflict — mitigation: regenerate/re-timestamp the manifest against current `develop` at execution; never hand-edit another task's migration.
- **Risk:** link deactivation seen as touching frozen V1 — mitigation: the freeze covers files/routes/trigger/DTO; this is a runtime write from the administration store, and the INSERT-only trigger cannot fire. Explicitly reviewed at the critical 003 gate.
- **Risk:** partial withdrawal (transaction too large / lock contention) — mitigation: single transaction under the existing advisory lock; test asserts all-or-nothing.
- **Risk:** redaction regression via the audit/admin read — mitigation: DTO whitelist typing plus absence assertions; no public surface changes at all.
- **Abort if:** the 003 critic rejects decision 1 (`deleted_at` + `DISABLED` model), decision 3 (withdrawal via service writes), or decision 4 (permanent retention) — set `blocked: true` with the objection and replan.
- **Abort if:** the safe migration language cannot express the table/grants as designed — evidence the generator failure, set `blocked: true`, and replan the persistence shape.
