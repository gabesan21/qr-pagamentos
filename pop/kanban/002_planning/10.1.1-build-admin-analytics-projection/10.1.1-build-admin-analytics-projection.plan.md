# Plan — [[10.1.1-build-admin-analytics-projection]]

- **Stage:** 002_planning · **Responsible:** planner agent

## Objective and expected result

- **Objective:** define the durable administrator analytics definitions (spec) and implement the server-only, re-authorized, redacted global analytics projection behind them: platform-wide registered/active/deleted users, orders by source/state, finalized vs abandoned funnel, links, products, exact per-currency volume, conversion, and bounded top-owner/top-product leaderboards — with zero payer data, zero credential/provider data, and owner identity limited to username plus the 10.3.1 deletion marker.
- **Observable result:** a new `src/orders/admin-analytics.ts` service (same posture as 8.4.1's merchant projection: no HTTP route, no mutation) returns a period-parameterized global DTO that 10.1.2's `/admin` dashboard server component will consume directly; contract tests prove the redaction boundary, the exact-decimal discipline, and that V1 tables, the merchant DTO, and every frozen surface are untouched.

## Strategy

Pure read-projection task; no route, no UI (10.1.2 owns rendering), no mutation surface. Pinned decisions the executor must not revisit (reviewed at the critical 003 gate):

1. **Global aggregates only — no per-owner analytics drilldown.** The DTO is platform-wide: every metric aggregates across all owners. The only per-owner data is the bounded top-owner leaderboard, and its identity is exactly `{ username, deleted }` per the 10.3.1 downstream read contract — never email, internal UUID, credential state, or store data. Owner-level exploration belongs to the 10.2.x directories, not to analytics.
2. **Period handling identical to the merchant precedent.** Closed set `today`/`7d`/`30d`, fixed `America/Sao_Paulo` reporting timezone (UTC−03:00, DST-free), calendar-day-aligned half-open UTC bounds, invalid period is a typed no-read outcome. The executor reuses the exported pure helpers from `src/orders/merchant-analytics.ts` (`resolvePeriodBounds`, period vocabulary); if a needed pure helper is not exported (decimal-unit parse/format), it is exported additively there with zero behavior change — no helper module is extracted and the merchant DTO/service stays byte-compatible.
3. **Sales and funnel definitions mirror the pinned merchant semantics, globally.** Provider-confirmed sales (`LINK` ∪ `STANDALONE`, `state = CONFIRMED`, `settled_at` in period) and locally finalized sales (`AD_HOC` latest outcome `LOCAL_FINALIZED` in period) are computed and exposed separately, never merged. Sums group by the snapshotted `(currency_uuid, exchange_currency_uuid)` pair as BigInt micro-units (10^6), never JS `Number`, never cross-currency; labels come only from the durable registry read (null code/label fail-closed, pair UUIDs never exposed). The funnel unions `checkout_attempt_v2` and `standalone_checkout_attempt` (each order attempt-bound in exactly one — never double-counted) with the same converted/abandoned/in-progress classification and exact-decimal four-digit rates, null on zero denominator.
4. **Commerce V2 only.** V1 tables are never read — the exclusion holds by definition, exactly as 8.4.1 pinned. Link metrics cover `payment_link_v2` only; product counts cover the `product` catalog (active vs archived counts); best sellers come from immutable `order_v2_line` snapshots (archived/deactivated products still appear; bilingual titles from current rows).
5. **Deleted-account semantics ride 10.3.1.** History is durable: soft-deleted owners' orders, attempts, links, and snapshots remain inside every aggregate (attribution is preserved and immutable). `registeredTotal` counts every persisted user row (deleted included); `activeNow` counts only `status = ACTIVE` with `deleted_at IS NULL`; `deletedTotal` is exposed separately. Top-owner rows carry the deletion marker so 10.1.2 can render withdrawn owners distinctly. Nothing is rewritten, anonymized, or excluded retroactively.
6. **Authorization and redaction boundary.** One server-only entry receiving the already-resolved active `ADMIN` principal (exact role denial before any I/O, mirroring `requireUserPrincipal` usage in the merchant service). The DTO carries aggregates, counts, rates, bilingual labels, redacted currency labels, usernames + deletion markers, and 24-character link identifiers only — never customer snapshot members, owner emails, internal UUIDs, retry keys, verifiers, capability/nonce/key material, or provider data. No administrator route is added in this task; 10.1.2 consumes the service from the `/admin` server component, exactly as 8.4.2 consumed the merchant service.
7. **Bounded, index-backed reads.** Leaderboards and feeds are hard-bounded (top-5 owners, top-5 products); period windows bound every aggregate. The executor first shapes queries against the delivered 8.1.2/8.1.3 indexes; only where a global query shape lacks support (e.g. `order_v2 (state, settled_at)`, attempt-table `created_at`) may it add additive plain-column indexes through one canonical `migration.safe.json` migration — never an expression/partial index, never a baseline edit.

## Risks and abort conditions

- **Risk:** redaction regression — payer snapshot, owner email/UUID, credential/provider data, or internal identifiers leak into the DTO — mitigation: whitelist DTO typing plus explicit absence assertions; 005 reads the DTO against the spec boundary.
- **Risk:** cross-currency or cross-member summing fabricates a meaningless total (the roadmap's USD fork) — mitigation: decisions 3 pin per-pair BigInt groups and never-merged members; tests assert no merged field exists; the stored asset is labeled through the registry, never as fabricated USD.
- **Risk:** funnel double-count across the two attempt tables — mitigation: the attempt-binding invariant (exactly one table per order) is asserted in tests over both tables.
- **Risk:** doc/write-set collision with in-flight 9.3.1 (`src/checkout/`, checkout spec) or 10.3.1 (`src/auth/`, admin spec, root `AGENTS.md`) — mitigation: the temporal gate plus disjoint code write sets; F03 edits land after 10.3.1 merges and the orchestrator serializes shared spec/AGENTS files.
- **Risk:** unbounded global scans on growing tables — mitigation: period-window bounds plus F01's index evaluation; leaderboards hard-capped.
- **Abort if:** the 003 critic rejects decision 1 (global-only scope), decision 5 (deleted-owner semantics), or decision 6 (no route / service-only posture) — set `blocked: true` with the objection and replan.
- **Abort if:** a needed index is inexpressible in the safe migration language — evidence the generator failure, set `blocked: true`, replan the query shape (bounded scan acceptable at MVP scale only with explicit 003 sign-off).
