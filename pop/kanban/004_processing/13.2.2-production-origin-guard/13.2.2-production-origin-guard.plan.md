# Plan — [[13.2.2-production-origin-guard]]

- **Stage:** 002_planning · **Role:** `pop-planner` (separate from execution)

## Objective and expected result

- **Objective:** a loopback operator origin (`PUBLIC_ORIGIN`, `NAUTT_WEBHOOK_CALLBACK_URL`) is refused in production unless one explicit allowance variable is set, and the installer supplies that allowance whenever the operator's own chosen origin is loopback.
- **Observable result:** a production deployment misconfigured with a loopback origin fails at container startup with a message naming the variable and the allowance and never the value; the user's current local loopback install keeps installing and booting with no manual edit; real HTTPS deployments are unaffected.

## Strategy

One rule, one place. `src/net/local-origin.ts` keeps `isAcceptableOperatorOrigin` as the shape rule and gains the single production decision (allowance + `NODE_ENV === "production"` read inside it). `loadPublicOrigin` and `validateNauttWebhookCallbackUrl` call that one function and hold no loopback or environment logic of their own.

The startup gate is `container/runtime.mjs`. It matters that `:15` today still enforces HTTPS-only for the callback and so already contradicts the 2026-09-22 loopback allowance: it is the only surface that can literally refuse to start, so it adopts the same rule (loopback only with the allowance) and extends it to the file-backed `PUBLIC_ORIGIN` (`PUBLIC_ORIGIN_FILE`, then `PUBLIC_ORIGIN`). Because `.mjs` cannot import the TypeScript module, this is the one permitted restatement of the rule; it must mirror the validator's wording and stay fail-closed. The TypeScript guard is the call-time defense for runs outside the container.

The allowance is `ALLOW_LOOPBACK_OPERATOR_ORIGINS`, honored only when its trimmed value is exactly `1`; anything else counts as absent (no truthiness, fail closed). Per decision 4 the installer derives it from the origins it already validates in `validate_operator_origin`, forwards it to the app container and prints a visible local-testing warning; it never rewrites the operator's `install/.env`, which is why the existing install keeps working untouched. Env whitelists must accept the key as optional so a hand-edited `install/.env` does not `die`, and `compose.yaml` must declare it with `${…:-}`, never `:?`, so backup/restore/uninstall keep composing.

## Risks and abort conditions

- **Risk:** the container startup preflight and the TypeScript validator drift apart again (they are already apart today, `container/runtime.mjs:15`) — mitigation: criterion 1 plus a comment in each place naming the other as its twin.
- **Risk:** installer-derived allowance means an `install.sh` deployment is never blocked by the guard — accepted: that is decision 4's shape; enforcement targets hand-rolled compose/PaaS deploys, paired with the installer warning. Flagged for the 003 approver.
- **Risk:** a required `:?` on the new compose variable would break `backup.sh`/`restore.sh`/`uninstall.sh` — mitigation: criterion 6.
- **Risk:** `NODE_ENV` is `production` during `next build`; a rule evaluated at module load would break builds — mitigation: the decision stays inside the existing call-time loaders, never at module scope.
- **Abort if:** honoring the guard would require changing `NAUTT_API_BASE_URL`, the webhook registration surface, or the accepted loopback host set — flag `blocked: true` with the file:line that forces it.
