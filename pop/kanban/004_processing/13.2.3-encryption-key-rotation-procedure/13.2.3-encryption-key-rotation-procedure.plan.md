# Plano — [[13.2.3-encryption-key-rotation-procedure]]

- **Etapa:** 002_planning · **Papel:** `pop-planner` (separado da execução)

## Objetivo e resultado esperado

- **Objetivo:** give `NAUTT_ENCRYPTION_KEY` and `TOTP_ENCRYPTION_KEY` a rotation path — a dual-key read window in the application, an idempotent one-shot rewrap of every stored ciphertext, the operator procedure in the runbook, and the spec amendment closing `nautt:69`.
- **Resultado observável:** an operator replaces either key on a running self-hosted deployment without losing access to any stored Nautt API key, webhook secret or TOTP secret, and without key material reaching a log, an argument or the repository.

## Estratégia

**Design pinned: dual-key window, no schema change (option a).** Only three columns hold ciphertext (`nautt_credential.encrypted_api_key`, `nautt_credential.encrypted_webhook_secret`, `totp_credential.encrypted_secret`). AES-256-GCM's auth tag makes "wrong key" an exact, safe failure, so trial decryption (current, then the optional previous key) identifies the wrapping key without storing a version. A per-row `key_version` column (option b) would add a durable migration, a `db-contract-check`/migration-baseline change and a new invariant, and would still need the same read window — cost without benefit for three small tables. Env contract pinned for every front: optional `NAUTT_ENCRYPTION_KEY_PREVIOUS` and `TOTP_ENCRYPTION_KEY_PREVIOUS`, same base64url/32-byte grammar as the current keys, file-backed secrets `nautt_encryption_key_previous` / `totp_encryption_key_previous`. Absent previous key = today's behavior exactly; present but malformed = loud failure, never a silent skip. Encryption always uses the current key.

`NAUTT_ENCRYPTION_KEY` is also the MAC key for checkout capability bearers (24 h TTL) and directory cursors. These are not stored ciphertext and cannot be rewrapped, so the read window must cover **verification** too (rederive with current, then previous), otherwise rotation kills in-flight payment pages. `CAPABILITY_KEY_VERSION` is a derivation-string version, not key material: it stays `v1` — bumping it would invalidate every attempt.

Rotation is an **explicit, separate operation**. The installer contract forbids rotating, regenerating or overwriting continuity material during install/update, and that stays true: no install/update path rotates implicitly; the rewrap is a profile-gated one-shot the operator runs on purpose, with a verified backup as precondition and the app stopped, like `migrate`. Rewrap writes are conditional on the observed ciphertext and touch no other column — `credential_revision` is the credential-replacement CAS token and a rewrap is not a replacement. TOTP recovery codes are SHA-256 digests, not ciphertext: nothing to rewrap, and no scheme may be invented for them.

## Riscos e condições de aborto

- **Risco:** a rewrap clobbers a concurrent onboarding CAS — mitigação: app stopped for the operation **and** updates conditional on the observed ciphertext, never rewriting `credential_revision` or `webhook_registration_state`.
- **Risco:** in-flight checkout capabilities and cursors die at rotation — mitigação: verification fallback to the previous key, and the runbook keeps the window open at least 24 h (capability TTL) before dropping it.
- **Risco:** a backup taken before rotation restores ciphertext the new key cannot read; TOTP recovery-code digests look rotatable but are not — mitigação: the runbook binds each backup to the key set of its creation, requires retaining the old key while such backups live, and states that recovery codes survive untouched.
- **Abortar se:** a CAS-safe idempotent rewrap turns out to require a schema change, or the capability/cursor fallback would need `CAPABILITY_KEY_VERSION` semantics to change — sinalizar `blocked: true` com evidência file:line; a decisão de desenho volta para 002.
