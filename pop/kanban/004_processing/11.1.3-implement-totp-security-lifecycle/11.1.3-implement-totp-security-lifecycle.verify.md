## Resumo

O pedido original foi parcialmente atendido: as rotas, o serviço TOTP, o challenge cookie, o audit de recovery e a maioria dos gates estão implementados. No entanto, há três falhas bloqueantes que violam o spec `pop/specs/identity-security.md` e quebram a operação real em container:

1. O digest dos recovery codes usa HMAC-SHA256 com chave vazia em vez de SHA-256 puro (violando o invariante do spec).
2. O runtime do container não carrega o segredo file-backed `TOTP_ENCRYPTION_KEY` a partir de `/run/secrets/totp_encryption_key`, deixando a aplicação sem chave em produção.
3. O schema declara `replayCounter` como `BigInt @db.BigInt`, mas a migration gerou a coluna como `INTEGER`, gerando divergência schema/migration.

## Achados

### Bloqueante 1 — Recovery-code digest não é SHA-256

- **Arquivo:** `src/auth/totp.ts:121-123` e `src/auth/totp.ts:138-139`
- **Problema:** A função `digest()` e a geração de recovery codes usam `createHmac("sha256", Buffer.alloc(0))`. O spec `identity-security.md` exige explicitamente "stored only as SHA-256 digests". HMAC-SHA256 com chave vazia **não é equivalente** a SHA-256 puro e é um anti-pattern.
- **Correção esperada:** Usar `createHash("sha256")` para os recovery codes.

### Bloqueante 2 — `TOTP_ENCRYPTION_KEY` não é carregada do arquivo no runtime

- **Arquivo:** `container/runtime.mjs:30-33` e `src/lib/totp-crypto.ts:44-54`
- **Problema:** `compose.yaml:117` passa `TOTP_ENCRYPTION_KEY_FILE: /run/secrets/totp_encryption_key` e monta o secret `totp_encryption_key`, mas `container/runtime.mjs` só lê `nautt_encryption_key` e exporta `NAUTT_ENCRYPTION_KEY`. O processo filho (`server.js`) nunca recebe `TOTP_ENCRYPTION_KEY`, então `loadEncryptionKey()` lançará erro em produção.
- **Correção esperada:** Ler `/run/secrets/totp_encryption_key` em `container/runtime.mjs` e exportar `TOTP_ENCRYPTION_KEY` no `env` do `spawn`, da mesma forma que `NAUTT_ENCRYPTION_KEY`.

### Bloqueante 3 — Divergência schema/migration para `replay_counter`

- **Arquivo:** `prisma/schema.prisma:723` e `prisma/migrations/20260728211700_totp_security_lifecycle/migration.sql:7`
- **Problema:** O schema declara `replayCounter BigInt @default(0) @map("replay_counter") @db.BigInt`, mas a migration gerou `replay_counter INTEGER DEFAULT 0 NOT NULL`. Em migrations anteriores (`media_objects`) o mesmo `BigInt @db.BigInt` foi corretamente gerado como `BIGINT`, confirmando que essa divergência é real.
- **Correção esperada:** Alinhar schema e migration. Como o contador de TOTP nunca ultrapassa a faixa de `INTEGER`, a opção mais simples é alterar o schema para `Int` sem `@db.BigInt`; alternativamente, regenerar a migration para `BIGINT`.

### Nit — Admin recovery rejeita usuários `DISABLED`

- **Arquivo:** `src/auth/admin-totp-recovery.ts:120-124`
- **Observação:** O spec/plano fala em "non-deleted targets". A implementação filtra `status: "ACTIVE"`, rejeitando também usuários `DISABLED`. Não é bloqueante, mas é mais restritivo que o contrato.
