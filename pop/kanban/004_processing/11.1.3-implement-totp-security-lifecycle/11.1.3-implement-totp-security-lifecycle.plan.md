# Plano — [[11.1.3-implement-totp-security-lifecycle]]

- **Stage:** 002_planning · **Responsible:** planner agent

## Objective and expected outcome

- **Objective:** Implement the server-side TOTP lifecycle: encrypted secret enrollment/confirmation, owner disablement, clock-skew and replay-protected validation, one-time hashed recovery codes, session revocation, and auditable administrator recovery.
- **Observable result:** A merchant with active TOTP must enter a valid TOTP code or recovery code after password proof; the profile shows opaque enrollment outcomes; an administrator can auditably disable TOTP for any non-deleted account.

## Strategy

Keep this task backend-contract only; the challenge/profile UI belongs to [[11.1.4-build-mfa-challenge-and-recovery-ui]]. Reuse the AES-256-GCM helper pattern under a new `TOTP_ENCRYPTION_KEY`, separate from Nautt credentials. Add additive tables for the credential, recovery codes, and recovery audit.

Login becomes two-step for TOTP-enabled users: password proof issues a short-lived `qr_mfa_challenge` cookie; a second POST validates TOTP/recovery code and promotes the challenge to a full `qr_session`. Disabling TOTP revokes target sessions and appends an audit row.

## Execution fronts
### F01 — Schema and encryption foundation
- **Deliverable:** Safe migration adding `totp_credential`, `totp_recovery_code`, `totp_recovery_action`; bootstrap grant re-pin; `TOTP_ENCRYPTION_KEY` env wiring.
- **Owns:** `prisma/schema.prisma`, migration, `prisma/bootstrap.sql`, env/compose/install files, `src/lib/totp-crypto.ts`.
- **Criteria:** 1, 2, 8, 9.

### F02 — TOTP lifecycle service
- **Deliverable:** `src/auth/totp.ts`: secret generation/encryption, RFC 6238 validation with ±1-step clock skew, replay counter, recovery-code hashing/consumption, state transitions.
- **Owns:** `src/auth/totp.ts`, `src/auth/totp.test.ts`.
- **Depends on:** F01.
- **Criteria:** 3, 4.

### F03 — Merchant profile TOTP routes
- **Deliverable:** Origin-guarded owner-only POST routes for enrollment, confirmation, and disablement under `/profile/totp/*`; request-log additions; opaque redirects.
- **Owns:** `src/app/profile/totp/{enroll,confirm,disable}/route.ts` + tests, `src/observability/server-request-log.ts`.
- **Depends on:** F02.
- **Criteria:** 3, 5, 6.

### F04 — Login challenge and session MFA binding
- **Deliverable:** `/login/submit` issues a short-lived challenge cookie when TOTP is active; `POST /login/totp-challenge` validates TOTP/recovery code and creates a real session; session carries optional `mfaVerifiedAt`.
- **Owns:** `src/auth/mfa-challenge.ts`, `src/auth/session.ts`, login routes + tests.
- **Depends on:** F02.
- **Criteria:** 3, 4, 5, 6.

### F05 — Administrator recovery policy
- **Deliverable:** Origin-guarded admin-only `POST /admin/users/[id]/totp-disable` that disables TOTP for non-deleted targets, appends one audit row, revokes sessions, and returns opaque redirects.
- **Owns:** `src/auth/admin-totp-recovery.ts`, `src/app/admin/users/[id]/totp-disable/route.ts` + tests.
- **Depends on:** F02.
- **Criteria:** 4, 5.

### F06 — Verification and gates
- **Deliverable:** Service/route tests, migration-policy and disposable db checks, container/installer checks, aggregate gates; sync `pop/specs/identity-security.md` at closeout.
- **Owns:** all test files touched in F01–F05.
- **Depends on:** F03, F04, F05.
- **Criteria:** 7, 8, 9.

## Order and parallelism

## Risks and abort conditions

- **Risk:** No RFC-6238 TOTP implementation in dependencies — mitigation: implement with `node:crypto` HMAC only or add a vetted dependency.
- **Abort if:** `pnpm check`, `pnpm db:test`, or `install/test.sh` fail; mark `blocked: true` with logs.
