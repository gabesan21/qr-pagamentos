# Plano — [[11.1.4-build-mfa-challenge-and-recovery-ui]]

- **Etapa:** 002_planning · **Responsável:** agent planejador

## Objetivo e resultado esperado

- **Objetivo:** Completar a jornada de MFA com interfaces bilíngues para desafio de login, recuperação, inscrição/desativação de TOTP e segurança do perfil, reutilizando os contratos entregues em 11.1.3.
- **Resultado observável:** Usuário vê tela de login adaptada ao challenge MFA, encontra uma seção de segurança no perfil para habilitar/desabilitar TOTP e gerenciar códigos de recuperação, e administrador vê ação de remoção de TOTP na conta do usuário.

## Estratégia

Backend já entrega enrollment, confirmação, disable e challenge; a UI precisa apenas de um pequeno enchimento (regeneração de recovery codes e leitura de status). O frontend segue o padrão de workspaces existentes: server components com client boundaries de observação de eventos nativos, sem interceptar POSTs. Adiciona-se a biblioteca `qrcode` para renderização SVG do provisioning URI, pois não há gerador de QR no projeto.

## Áreas afetadas

- `src/app/login/` — renderizar challenge MFA quando `?mfa=required`.
- `src/app/profile/` e `src/app/(merchant)/profile/` — seção de segurança TOTP.
- `src/app/admin/accounts/[id]/` — ação de recuperação TOTP.
- `src/auth/totp.ts`, `src/auth/totp-store.ts` — regeneração de recovery codes e leitura de status.
- `src/i18n/dictionaries/profile/` — chaves bilíngues de MFA.
- Evidence runners de `login` e `profile`.

## Frentes de execução

### F01 — Backend UI enablers

- **Entrega:** Rota `POST /profile/totp/regenerate` e query de status TOTP para o perfil.
- **Escopo:** Implementar `regenerateRecoveryCodes` no serviço, persistir novos códigos, e expor status `{ state: 'none'|'pending'|'active' }` via server-only helper usado na página de perfil.
- **Owns:** `src/auth/totp.ts`, `src/auth/totp-store.ts`, `src/app/profile/totp/regenerate/route.ts`.
- **Must not edit:** rotas existentes de enroll/confirm/disable/login/admin.
- **Depends on:** nenhuma.
- **Skills:** [[pop/skills/clean-code-change|clean-code-change]].
- **Critérios:** 1, 2, 6.

### F02 — Login MFA challenge

- **Entrega:** Página `/login` renderiza formulário de código/recovery quando `?mfa=required`, mantendo os estados de erro genéricos e acessibilidade.
- **Escopo:** Ajustar `page.tsx` para ler o challenge cookie e o query param; criar client boundary `totp-challenge-form.tsx` que observa submit nativo e alterna TOTP/recovery code.
- **Owns:** `src/app/login/page.tsx`, `src/app/login/totp-challenge-form.tsx`.
- **Must not edit:** `src/app/login/submit/route.ts`, `src/app/login/totp-challenge/route.ts`.
- **Depends on:** F01 (não diretamente, mas o fluxo depende do backend 11.1.3).
- **Skills:** [[pop/skills/ui-change|ui-change]].
- **Critérios:** 3, 4, 7.

### F03 — Profile TOTP security workspace

- **Entrega:** Seção de TOTP no perfil com estados `none`/`pending`/`active`, cards de enrollment (QR + recovery codes), confirmação, desativação e regeneração de códigos.
- **Escopo:** Estender `ProfileManagement` com `TotpSecuritySection`; criar componentes client para QR, copy, e formulários nativos que postam às rotas existentes; utilizar dirty-field omission para não postar campos não alterados.
- **Owns:** `src/app/profile/profile-management.tsx`, `src/app/profile/totp-section.tsx`, `src/app/profile/totp/*.tsx`.
- **Must not edit:** rotas de backend 11.1.3.
- **Depends on:** F01.
- **Skills:** [[pop/skills/ui-change|ui-change]].
- **Critérios:** 1, 2, 5, 6, 7.

### F04 — Admin TOTP recovery affordance

- **Entrega:** Botão de remoção de TOTP na página `/admin/accounts/[id]` para alvos não deletados, com confirmação via `<details>` nativo.
- **Escopo:** Adicionar card de ações de segurança reutilizando o padrão de confirmação destrutiva da página; postar para `/admin/users/[id]/totp-disable`.
- **Owns:** `src/app/admin/accounts/[id]/page.tsx` e componentes locais.
- **Must not edit:** `src/app/admin/users/[id]/totp-disable/route.ts`.
- **Depends on:** nenhuma.
- **Skills:** [[pop/skills/ui-change|ui-change]].
- **Critérios:** 5, 7.

### F05 — i18n, evidence e testes

- **Entrega:** Chaves bilíngues e atualização dos evidence runners de login/profile para cobrir os novos estados.
- **Escopo:** Adicionar chaves em `src/i18n/dictionaries/profile/en.ts` e `pt-BR.ts`; ajustar `login.evidence.spec.ts` e `profile.evidence.spec.ts` (ou scripts) para capturar challenge e TOTP; manter `pnpm check` e `pnpm profile:evidence`, `pnpm login:evidence` passando.
- **Owns:** `src/i18n/dictionaries/profile/`, `tests/login.evidence.spec.ts`, `tests/profile.evidence.spec.ts`.
- **Must not edit:** specs duráveis além do que for necessário para refletir UI.
- **Depends on:** F02, F03, F04.
- **Skills:** [[pop/skills/ui-change|ui-change]], [[pop/skills/sync-specs|sync-specs]].
- **Critérios:** 1, 5, 7, 8.

## Riscos e condições de aborto

- **Risco:** `qrcode` adiciona dependência — mitigação: usar versão estável, tipos `@types/qrcode`, e renderização SVG sem canvas.
- **Abortar se:** evidence runner exigir ambiente de produção real — sinalizar `blocked` e reportar.
