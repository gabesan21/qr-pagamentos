# Plan — [[10.2.1-build-admin-orders-directory]]

- **Stage:** 002_planning · **Responsible:** planner agent

## Objective and expected result

- **Objective:** give administrators a bounded, read-only, re-authorized global Commerce V2 order directory on the `src/data-directory/` foundation — keyset pagination over the closed 10/20/50/100 set with **default 50**, source/money/date/link filters, payer + local/provider-ID search, owner attribution with navigation, and a read-only V2 detail view — while the delivered V1 admin ledger stays byte-frozen below it.
- **Observable result:** `/admin/orders` renders the V2 global directory (canonical `307`s, zero-I/O invalid-query, six states) above the unchanged V1 list; `/admin/orders/v2/[id]` serves a read-only V2 detail with one opaque unavailable outcome; soft-deleted owners keep full attribution with a localized deleted marker; contract tests and a run-bound `admin-orders:evidence` pair prove authorization, redaction, and accessibility.

Stage skills on the card are correct (clean-code + ui-change/ui-review + sync-specs); nothing missing.

## Strategy

Pure additive read surface; no mutation, no migration, no edits to frozen V1/V2 services or views. Pinned decisions the executor must not revisit:

1. **Query ownership: new module, never extend the owner directory.** A new server-only `src/orders/order-v2-admin-directory.ts` mirrors the delivered `order-v2-directory.ts` shape but runs `queryAdministratorDirectory` with the `ADMIN_GLOBAL` scope purpose (both delivered by the foundation — no foundation edit), directory id `admin-order-v2`, path `/admin/orders`, same `(createdAt desc, id desc)` keyset and seek tuple, and its own page-size policy `{ sizes: [10,20,50,100], defaultSize: 50 }`. Filters stay inside the eight-filter cap: `source` (closed enum), `money` (USD/FIAT via the durable active-USD registry pair, same mapping as the owner directory), `from`/`to` (validated calendar days, zero-I/O invalid), `link` (exact 24-char identifier), plus `q` (UUID equality on local/provider order IDs, otherwise policy-column payer-text containment). The merchant directory file is not touched.
2. **Redaction surface: summary DTO + owner attribution only.** Rows reuse `toOrderV2Summary`/`orderV2SummarySelect` unchanged and additively select the owner relation's `username` + `deletedAt` — nothing else. The policy-exact payer snapshot already on the summary is the sanctioned administrator payer exposure (spec amendment records this explicitly). No provider data, verifiers, capability material, lifecycle fields, or owner email/id leave persistence; provider order UUIDs are match-only inside `q`, never rendered.
3. **Deleted-owner rendering: history preserved, never filtered.** 10.3.1 preserves attribution, so rows of soft-deleted owners stay listed in every result and aggregate position; the owner cell renders the username with a localized non-color deleted badge (the administrator-only `deletedAt` fact, admin surface only). Eligibility is never altered by deletion.
4. **Owner navigation: interim target.** The owner cell links to the delivered `/admin/accounts` surface; the spec records that 10.3.3 (user profile editor) repoints this link to the per-user profile route. No new user route in this task.
5. **Detail view: read-only composition, two reads, zero edits to delivered modules.** `/admin/orders/v2/[id]` re-authorizes the admin, calls the delivered `order-v2-view.ts` `getForAdmin` (keeps the one opaque unavailable outcome for cross/malformed/missing IDs), and issues one bounded owner-attribution read (`username`, `deletedAt`) from the new module. It renders the exported read-only `OrderV2DetailCard` facts/lines/payer plus owner attribution; the comment thread and local-outcome forms stay owner-only and are not rendered for administrators. V1 `/admin/orders/[id]` is untouched.
6. **No schema or infrastructure change.** Directory reads run on the delivered schema; the global payer-text `contains` search needs no new index at this scale — if recon shows one is required, that is an abort, not a migration.

Rate limiting and request-log inventories: unchanged (SSR admin pages, no API routes) — no intersection with 9.1.3.

## Risks and abort conditions

- **Risk:** redaction regression (provider data, lifecycle fields, owner email/id, raw customer columns beyond the policy tuple leak admin-side) — mitigation: additive whitelist select + absence assertions; 005 diffs the DTO against the amended boundary.
- **Risk:** owner attribution read breaks the one opaque unavailable outcome — mitigation: attribution read only after `getForAdmin` returns found; test both paths.
- **Risk:** global payer-text search scans grow — mitigation: bounded keyset reads, no offset; no index in this task (pinned decision 6).
- **Risk:** evidence seeding cannot produce a soft-deleted owner with orders — mitigation: drive deletion through the delivered `POST /admin/users/[id]/delete` after order creation in the harness.
- **Abort if:** the global directory cannot be served from the delivered schema (missing owner relation/column) — signal `blocked: true` with the schema evidence; a migration would violate the task constraint.
- **Abort if:** redacting payer data per the admin contract conflicts with the card's payer-search requirement in a way the spec amendment cannot resolve — signal `blocked: true` with the conflicting text.
