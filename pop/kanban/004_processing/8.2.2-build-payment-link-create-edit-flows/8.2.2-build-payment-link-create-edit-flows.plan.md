# Plan — [[8.2.2-build-payment-link-create-edit-flows]]

- **Stage:** 002_planning · **Responsible:** planner agent

## Objective and expected result

- **Objective:** Deliver the owner-safe bilingual management flows for Commerce V2 payment links over the delivered 8.1.2 backend: create (product-cart `PRODUCT_LINES` and `FIXED_AMOUNT`), edit (expiry anytime; financial composition under expected-version CAS), activate/deactivate, and opaque outcome notices, all under the merchant `/links` workspace delivered by 8.2.1.
- **Observable result:** From `/links` the merchant creates both composition kinds through validated bilingual forms, edits allowed fields from the link detail, activates/deactivates with confirmation, sees localized success/failure notices on `/links`, and shares the public identifier (share affordance already delivered by 8.2.1, preserved and covered by evidence).

## Strategy

Build UI + wiring only; the mutation contract of `src/auth/payment-link-v2.ts` and its two routes is fixed. Pages are server-rendered under `src/app/(merchant)/links/` reusing the catalog workspace patterns: native form POSTs, `WorkspaceHeading`, `Field`/`NativeSelect` primitives, observation-only pending submit (`CatalogSubmit` analog), and dirty-field omission so untouched financial members post nothing and never trip the checkout-attempt gate. The lines editor is one focused client component that manages 1–20 ordered lines (add/remove, quantity 1–9,999, per-link product uniqueness hinted client-side but enforced by the service) and serializes into the hidden `lines` JSON field the route already parses. Two genuine seams require minimal additive server reads (no mutation-contract change): (1) edit/new-version prefill needs `version` and line `productId`s, which neither the 8.1.2 service facade nor the redacted 8.2.1 view expose — add a small server-only owner read module that reuses the delivered `createPaymentLinkV2Store(...).findOwned` behind `requireUserPrincipal` with canonical-UUID validation and one opaque `null` outcome; (2) create-form pickers need active same-owner products and active currency pairs — reuse the existing V1 `getPaymentLinkService().listForOwner` owner data read (read-only; do not edit the frozen V1 module). Route redirects repoint from `/?payment-links-v2=…` to `/links?payment-links-v2=…` (exact 7.2.3 catalog precedent: behavior unchanged, targets only), with the closed outcome set `created|edited|activated|deactivated|failed` extracted before directory canonicalization (catalog `noticeKey` pattern) and rendered as bilingual notices. The immutable-version fork UX is honest and minimal: the edit form explains bilingually that composition locks after the first checkout attempt, the failed outcome stays opaque, and a "new version" affordance links to `/links/new?from=<id>`, prefilled server-side from the current composition (fresh identifier stays server-generated). Public checkout preview is out of scope (9.3.1 owns V2 checkout); "preview" here is the read-only detail rendering plus the share URL/copy already delivered. i18n extends the `payment-links-directory` dictionary domain in both locales; evidence extends the existing `links:evidence` pair driving the real UI.

## Risks and abort conditions

- **Risk:** edit prefill needs `version`/`productId` neither exposed read provides — mitigation: the single additive owner-read module over the delivered store; never extend the redacted 8.2.1 view with version/productIds and never change the mutation service.
- **Risk:** the `payment-links-v2` notice param collides with strict directory canonicalization (unknown params `307`-strip or invalidate) — mitigation: strip and validate the closed notice set before `canonicalizeDirectoryRequest`, exactly the catalog `noticeKey` pattern; invalid values yield the zero-I/O invalid-query state.
- **Risk:** expiry grammar is UTC `YYYY-MM-DDTHH:mm` and future-only on genuine assignment; prefilled past expiry resubmitted unchanged would fail — mitigation: dirty omission (unnamed until changed) plus bilingual UTC help text, matching the V1 form.
- **Risk:** financial edit on an attempt-locked link fails opaquely and may confuse — mitigation: bilingual lock explanation on the edit form plus the `/links/new?from=<id>` new-version affordance; the redirect stays the single opaque `failed`.
- **Abort if:** the delivered routes/service deviate from the documented action/outcome vocabulary, or prefill cannot be served without changing the mutation contract or the redacted view — flag `blocked: true` with the conflicting evidence.
