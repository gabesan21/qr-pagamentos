# Plan — [[M-19.1-default-currency-without-probe]]

- **Stage:** 002_planning · **Role:** `pop-planner` (isolated from implementation)

## Objective and observable result

- **Objective:** newly created merchant accounts automatically receive the system's first eligible active payment method's currency as their storefront default conversion currency. Active admin-registered methods become immediately selectable by merchants without performing a pre-order quote probe, and the merchant "Test pair" button and probe gating are removed from the settings UI and save path.
- **Observable result:** creating a user through the administrator panel sets their default currency without manual configuration if an active method exists; on `/settings`, the default currency select can be changed to any active method and saved immediately with no test button or reachability blocker; saving reports success and stores the currency on the account.

## Strategy

Execute across two tightly scoped fronts:
1. **F01 (Backend initialization & selection contract):** Update user creation (`createAdministrationService.createUser`) to resolve and assign the active default currency code when provisioning a merchant account, with deterministic fallback to none when no valid active method exists. Remove the `isSelectable` probe-evidence requirement from `createStorefrontSettingsService.update` and `createAdminUserProfileService.updateStorefront` so that any administrator-registered active mapping is valid for assignment.
2. **F02 (Merchant settings UI & obsolete probe removal):** In `StorefrontSettingsManagement` (`src/app/storefront-settings-management.tsx`) and `MerchantSettingsPage` (`src/app/(merchant)/settings/page.tsx`), remove the "Test pair" form, probe status display, and probe-evidence data fetching from the currency settings card. Ensure the select directly controls the default currency and saves reliably.

## Risks and abort conditions

- **Risk:** Existing orders or payment links relying on probe evidence. *Mitigation:* Evidence records remain untouched in DB for historical audits; only the new-assignment gate is removed.
- **Risk:** System has zero active currency mappings at user creation time. *Mitigation:* Graceful fallback to `null` without throwing errors.
- **Abort if:** Database migration or schema change is required (existing fields are sufficient).
