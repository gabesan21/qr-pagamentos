# Plano — [[14.5.3-converge-catalog-settings-profile]]

- **Etapa:** 002_planning · **Papel:** `pop-planner` (separado da execução)

## Objetivo e resultado esperado

- **Objetivo:** bring `/catalog/**`, `/settings` and `/profile` to the template's merchant operation surface — flat product form with drag-and-drop uploader and sticky preview, category maintenance, store controls (swatch grid, segmented layout, color picker, logo uploader, confirm-gated switch, radio cards, Nautt actions) and the template TOTP enrollment order — composed over the delivered native mutations.
- **Resultado observável:** a merchant creates a product in one flat form with the store's default currency pre-selected, a dragged image and inline errors; configures the store with swatches, a segmented layout, a color picker, a logo uploader and a confirm-gated store switch; and enrolls TOTP by scanning the QR, copying the manual secret, confirming the code inline and only then saving the recovery codes.

## Estratégia

Presentation over the delivered mutations. `src/auth/**`, `src/integrations/**`, `src/media/**`, `src/data-directory/**`, `src/components/ui/**` and every `route.ts` are read-only; the 14.1.1 failure returns, the 14.3.2 on-page notices and the `FormDraftGuard` drafts stay as delivered. Two client bridges make the template order reachable with zero route bytes changed, because both routes already encode their outcome in the 303 target (`relative-redirect.ts:4`): the TOTP confirm is submitted by `fetch` and branched on the `totp` param of the followed redirect, so a wrong code is inline and the enroll codes stay in component memory until the last step; and the logo `stage` posts the unchanged multipart form to `/storefront/logo`, reading `logo=<identifier>` from the same followed redirect. Recovery codes are never persisted anywhere, an unreadable param falls back to the native reload, and both native forms survive under `<noscript>`.

Four template obligations are unreachable under that boundary and ship as **recorded gaps, never dead controls**: (a) active/inactive on create — `productValues` and `ProductService.create` accept no state field (`products/route.ts:7`, `product.ts:213`); (b) inline edit of an **inactive** category — the store matches `active: true` (`product-category.ts:180`) and the spec makes inactive targets opaque conflicts; (c) Nautt **replace/reset for an ACTIVE credential** — replacement is blocked outside `UNREGISTERED` and the local reset exists only for a stuck `REGISTERING`/`INDETERMINATE`, so Validate becomes a fresh `readStatus` round-trip and the "last validated" line renders the projected `updatedAt` as a credential update, never a fabricated validation instant; (d) enrolled-since — `getStatus` projects only `none|pending|active`. One divergence is decided here: `/storefront` keeps **one form and one Save** for identity/store/payments/currency, because per-section saves would need the route to read absent core fields as unchanged, which breaks the unchecked-checkbox disable path; the confirm-gated store switch and the currency Clear submit that same form. The merchant `SegmentedControl` moves from `catalog-fields.tsx` to a merchant-local `merchant-controls.tsx` (the template's own `pages/catalog/fields.tsx` is already the shared merchant module) instead of entering `src/components/ui/`, whose `owners` set is frozen and whose `localAdditions` needs an insufficiency finding that does not exist here.

## Riscos e condições de aborto

- **Risco:** the fetch bridges depend on the followed-redirect URL — mitigação: an unreadable param falls back to the native reload and the section's notice bridge; codes stay in component state only, never in storage.
- **Risco:** a front concludes a criterion needs `src/auth/**`, a `route.ts`, `src/components/ui/**` or `src/data-directory/**` — mitigação: it stops and reports `BLOCKED`; the gap is recorded, never widened into a service change.
- **Risco:** existing suites assert the current markup — mitigação: no test is written or run here; the realignment accumulates for [[14.5.4-phase-verification]].
- **Risco:** `globals.css` is also touched by 14.5.1/14.5.2 — mitigação: only F04 writes it, deleting exactly the named merchant blocks; `.settings-surface*`, `.storefront-logo` and every public `.storefront-*` rule stay for 14.6/14.7.
- **Abortar se:** a delivered mutation cannot keep the merchant on its own page without a route change — sinalizar `blocked: true` com arquivo e linha como evidência.
