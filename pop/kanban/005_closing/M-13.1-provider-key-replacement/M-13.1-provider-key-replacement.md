# M-13.1 — Provider API key replacement

## Approved plan

1. Add a strict candidate-key adapter read for
   `GET /client-webhooks/{providerWebhookId}`, validated against the supplied
   OpenAPI evidence: a `200` response must carry the expected webhook UUID,
   canonical callback URL, exactly the required events, and `is_active: true`.
   Validate the candidate key with the existing main-wallet read as well.
   Every validation failure performs no persistence.
2. Add a separate owner-bound replacement operation and origin-guarded
   merchant `USER` route. Its CAS requires owner, ACTIVE state, expected
   credential revision, and expected webhook id; it writes only a newly
   encrypted API key and fresh revision. Webhook identity, encrypted secret,
   state, and registration timestamp remain unchanged. It never registers,
   resets, or sends a provider POST.
3. Preserve in-flight provider calls and reconciliation behavior. No automatic
   retry or provider-side webhook creation is introduced. No schema change.
4. Add a compact bilingual merchant settings section. The single approved
   provider-brand exception is “Conexão com a Nautt Finance” / “Connection to
   Nautt Finance”. Replacing the key opens an empty password field with
   cancel/save, localized pending and safe feedback, then refreshes balance and
   context. Existing onboarding and reset states remain intact.
5. Update the integration spec, local DOX stale-GET note, focused unit, route,
   concurrency, redaction, and i18n/UI tests.
