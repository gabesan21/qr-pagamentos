# Plano — 12.3.2-remodel-authentication-and-recovery-pages

## Objetivo

Remodelar as páginas de autenticação e recuperação em `src/app/login/**` e `src/app/reset-password/**` para a nova composição do design system (shell 12.3.1), cobrindo estados de login, MFA challenge, password reset, unavailable, pending, validation e success, sem alterar regras de credenciais, sessão, MFA, redirecionamentos ou contratos de autorização.

## Áreas de mudança

- `src/app/login/page.tsx` — layout de autenticação com painel de marca responsivo.
- `src/app/login/login-submit.tsx` — estado de pending nativo com `useFormStatus`.
- `src/app/login/totp-challenge-form.tsx` — modos TOTP e recovery code, estado de erro, alternância.
- `src/app/reset-password/page.tsx` — estados de token invalid/unavailable, form, success.
- `src/app/reset-password/reset-password-submit.tsx` — pending state.
- `src/i18n/dictionaries/shared/{en,pt-BR}.ts` e `password-reset/{en,pt-BR}.ts` — copy para pending, validation, success, unavailable.
- `src/app/login/page.test.tsx`, `src/app/reset-password/page.test.tsx` — asserts de layout, estados e inventário.
- `DESIGN.md` — nenhuma direção nova; apenas consolida o contrato de autenticação já documentado se houver gap sobre estados pending/success.

## Estratégia

1. Reutilizar primitivos de `src/components/ui/` e composições entregues em 12.2.3/12.3.1; não criar componente visual local.
2. Implementar layout com painel de marca de `300px` à direita em `≥900px` e card centrado de até `720px`; form capado em `420px`; nenhum overflow horizontal em `320px`.
3. Preservar rotas POST existentes byte-a-byte; alterar apenas apresentação e estados de client boundary.
4. Cobrir os estados obrigatórios do `DESIGN.md`: default, loading/pending, empty onde aplicável, error com recovery, hover/focus, disabled; adicionar pending, validation e success específicos dos journeys.

## Frentes

| # | Frente | Entrega observável |
|---|--------|-------------------|
| 1 | Layout auth unificado | `login-page` e `reset-password-page` usam a mesma estrutura de card + painel de marca; testes de render estático verificam `data-brand-identity` e ausência de overflow em `320px`. |
| 2 | Login states | Estados: vazio, validação, submit pending, invalid credentials genérico, password changed success, MFA required, MFA failed, recovery code mode. |
| 3 | MFA challenge | `totp-challenge-form.tsx` alterna entre TOTP (`[0-9]{6}`) e recovery code (`[0-9a-f]{64}`) com label dinâmico, foco no input, botão de submit em pending. |
| 4 | Reset-password states | Estados: token loading/validating, token invalid/unavailable, form válido, submit pending, validation error (senhas divergentes/comprimento), request error, success. |
| 5 | Copy e locale | Adicionar chaves faltantes em `pt-BR` e `en`; manter equivalência sem mudar capacidade ou revelar causa. |
| 6 | Testes e qualidade | Atualizar page tests para refletir novos estados e layout; `pnpm check` e `pnpm test` passam; Playwright evidence para `/login` e `/reset-password` é registrada no card. |

## Dependências

- `12.3.1-rebuild-role-specific-application-shells` concluída (entregue).
- Primitivos de `src/components/ui/` e tokens em `design-system/tokens/themes.tokens.json` estáveis.
- Rotas `POST /login/submit`, `/login/totp-challenge`, `/reset-password/submit` e serviços de `src/auth/**` inalterados.

## Riscos

| Risco | Mitigação |
|-------|-----------|
| Quebrar contrato de inventário de UI | Reutilizar apenas owners listados em `inventory.json`; rodar `scripts/check-shared-ui-inventory.mjs`. |
| Vazar causa de erro ou token validity | Manter mensagens opacas; não adicionar novos parâmetros de query além dos já contratados. |
| Perder foco/acessibilidade nos estados dinâmicos | Usar `autoFocus` gerenciado, `aria-live` para alertas, e targets ≥44×44px. |
| Quebrar testes de rotas existentes | Não alterar `route.ts`; se refatorar helpers, manter assinatura e cobertura. |
