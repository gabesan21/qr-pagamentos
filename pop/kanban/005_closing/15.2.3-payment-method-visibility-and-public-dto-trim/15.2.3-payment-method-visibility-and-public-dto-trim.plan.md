# Plan — [[15.2.3-payment-method-visibility-and-public-dto-trim]]

- **Stage:** 002_planning · **Role:** `pop-planner` (separate from execution)

## Objective and expected result

- **Objective:** provider failures become diagnosable through a redacted documented `code`; the merchant sees the provider payment method behind an order; `pixQrCodeUrl` leaves every public payment DTO and client parser.
- **Observable result:** an adapter failure emits one structured log record carrying only operation, HTTP status and an allowlisted documented code; the merchant order detail shows a payment-method row; the V2 link and standalone checkout/status responses carry only `{ payment: { state, pixCopyPaste? } }`.

## Strategy

Three disjoint write sets, no file shared between fronts. Logging is one server-only writer placed next to `src/observability/server-request-log.ts` and reusing its discipline (single JSON line, console sink, swallow-on-failure, never alters the response or the thrown error); the four adapter operations call it and never format a record of their own. A documented `code` is logged verbatim only when it belongs to the closed set already ingested in the Nautt research; anything else logs a fixed unknown marker, so a provider-controlled string never enters the log. In `createOnrampOrder` the documented-code classification seam belongs to 15.2.2: F01 consumes it and never adds a second body read.

Payment method is an additive owner-detail exposure: the persisted `ProviderOrder.paymentMethod` joins the detail select and the detail view type only — the summary select shared with the order directory and every public projection stay byte-identical. The `pixQrCodeUrl` removal is split at the server/browser boundary: producers plus the durable contract in F02, browser parsers and payment types in F03, because `src/app/pay/**` and `src/app/store/**` are 15.3.1's write set. The presentational `checkout-payment-views.tsx` is not touched here: its `pixQrCodeUrl` prop is already dead (declared, never read) and falls with 15.3.1's rewrite of that file. No test is written or run in this task; every test obligation accumulates in the 15.2.4 checklist. `src/integrations/nautt/config.ts` and `NAUTT_API_BASE_URL` are out of scope for all fronts (2026-09-22 decisions).

## Affected areas

- `src/observability/**` and `src/integrations/nautt/**` — new server-only failure log writer, adapter call sites and the subtree contract.
- `src/orders/**`, `src/app/orders/**`, `src/i18n/dictionaries/orders-directory/**`, `src/checkout/**` — owner detail projection with its label, and the public payment DTO producers.
- `src/app/pay/[identifier]/**`, `src/app/store/[slug]/pay/**`, `pop/specs/**` — browser payment types/parsers and the two durable contracts.

## Order and parallelism

1. **Wave 1:** F02 and F03 in parallel (disjoint write sets, no logical dependency: the field is optional on both sides during the window).
2. **Wave 2:** F01, after 15.2.2 is integrated — it owns the `createOnrampOrder` error path in the same file; F01 joins wave 1 only if 15.2.2 already closed. **Scheduling constraint:** F03 never runs in the same wave as 15.3.1 (same three files).
3. **Integration:** the main agent validates ownership per front, integrates and checks the `agent` criteria.

## Risks and abort conditions

- **Risk:** 15.2.2 owns the same `createOnrampOrder` failure path — mitigation: F01 runs after it and consumes its classification seam instead of re-reading the body.
- **Risk:** 15.3.1 owns `src/app/pay/**` and `src/app/store/**` — mitigation: F03 edits only the `pixQrCodeUrl` lines in three files and never the presentational view.
- **Risk:** a provider-controlled `code` logged verbatim is a leak/injection surface — mitigation: closed documented allowlist, fixed marker otherwise.
- **Risk:** 15.1.3 rewrote the checkout lifecycle spec, so the pinned DTO statement moved — mitigation: F02 re-reads the current spec and amends the current statement, never restoring V1 wording. **Handoff:** the dead prop declaration in `checkout-payment-views.tsx` is deliberately left to 15.3.1.
- **Abort if:** the 15.2.2 documented-code seam is absent (F01) or the spec no longer carries a public payment DTO statement (F02) — report `BLOCKED` with the file evidence.
