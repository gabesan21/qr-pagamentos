# Plan — [[8.3.1-build-owner-order-query]]

- **Stage:** 002_planning · **Responsible:** planner agent (separate from executor)

## Objective and expected result

- **Objective:** Deliver the owner-scoped Commerce V2 order directory server contract on the data-directory foundation (6.3.1): canonical bounded query parsing, authenticated keyset pagination, `q` search over local/provider IDs and payer data, and exact source, USD/FIAT, date-range, and link facts filters, with page sizes 10/20/50/100 and default 20.
- **Observable result:** A re-authorized merchant principal can query `/orders`-bound directory URLs and receives a bounded redacted page plus opaque next/previous cursors; noncanonical valid URLs `307`-reset and invalid URLs resolve to the foundation's zero-I/O invalid outcome. No mutation, no rendered UI.

## Strategy

First consumer of the `src/data-directory/server` foundation, so the one genuine foundation gap is closed first: the foundation pins page sizes 25/50/100 with a global default 25 (`query-contract.ts`, the cursor envelope check in `cursor.ts`, and the administrative-foundation spec), while this task's approved contract requires 10/20/50/100 with default 20 per directory. F01 makes the closed page-size set and its default a per-directory registered value (extending the global closed set to include 10 and 20) without weakening any bounded/canonical guarantee. F02 then builds the owner order directory module in `src/orders/`: registered filter definitions, the registered order `(createdAt desc, id desc)` ending in `UNIQUE_IMMUTABLE_ID`, a Prisma adapter fetching only `pageSize + 1`, and a single server entry that resolves the cookie principal, runs `canonicalizeDirectoryRequest`, and delegates to `queryMerchantDirectory`.

Filter contract (≤ the foundation's eight-filter cap): `source` enum `LINK|AD_HOC`; `money` enum `USD|FIAT` resolved server-side by mapping the order's `exchange_currency_uuid` through the registered currency-pair data (never accepting UUIDs or codes from the URL); `from`/`to` text dates validated to an exact calendar-day grammar and applied as `created_at` bounds; `link` text fact matched against the V2 link identifier. `q` search: a value parsing as a UUID matches `order_v2.id` or the related `provider_order.provider_order_uuid` by equality; any other bounded text matches payer name/email/cpf. All predicates stay owner-scoped and compose over the 8.1.3 indexes `(owner_id, created_at, id)` and `(owner_id, source, created_at, id)` exactly as the spec's index strategy prescribes — no new index, migration, or schema change is expected.

The row DTO reuses the `order-v2-view.ts` summary shape (source, link identifier, amount, currency pair UUIDs, bilingual description, `state`, current local outcome, policy, timestamps) and stays redacted: no owner identity, verifiers, provider internals, or lifecycle fencing fields. Search and filter inputs never echo back in any outcome. Admin global directory, mutations (8.3.2), and rendering (8.3.3) are out of scope by design.

## Risks and abort conditions

- **Risk:** The page-size change ripples into cursor compatibility and the administrative-foundation spec — mitigation: keep the global closed set a superset (10/20/25/50/100), change only registration/default, and sync the spec line in the same delivery.
- **Risk:** Payer-text search degenerating into unbounded scans — mitigation: owner-scoped bounded predicates only, exactly the spec's "compose over owner-scoped keyset indexes without new design"; no `LIKE '%…%'` leading-wildcard scan without an owner bound.
- **Abort if:** any filter genuinely requires a new index, migration, or schema change — signal `blocked: true` with the query plan evidence (8.1.3's index strategy is the approved design; changing it is a separate task).
- **Abort if:** no server-side durable exchange-currency pair→code resolution exists and the spec cannot be coherently extended — signal `blocked: true` with the RECON evidence.
