# Plan — [[7.1.1-model-supported-exchange-currencies]]

- **Stage:** 002_planning · **Responsible:** planning agent

## Objective and expected result

- **Objective:** establish a dynamic, administrator-registered registry of supported exchange currencies — ISO 4217 alphabetic code as the application identity, Nautt `currency_uuid`/`exchange_currency_uuid` as runtime-registered provider mapping — with transactional single-active semantics, immutable history, and a shared resolution/gating service that treats missing configuration as a normal operational state.
- **Observable result:** an active `ADMIN` can register, deactivate, and replace mappings through a re-authorized mutation surface; active `USER` callers read only active, redacted choices; dependent features (7.1.2 store default, 7.2.2 product currency, later links/checkout) receive a deterministic available/unavailable signal and typed backend errors when no active mapping exists; existing links and orders keep their recorded UUID meaning; no public/sessionless discovery surface appears.

## Strategy and fixed contract

The ISO 4217 alphabetic code (uppercase `[A-Z]{3}`, format-validated; no closed code list anywhere in code or schema) is the only application currency identity. Each registry row binds one code to the administrator-registered Nautt `currency_uuid` (fiat identifier) and `exchange_currency_uuid` (exchange/payment-rail identifier) — the exact two provider identifiers the existing pricing adapter requires at call time (`src/integrations/nautt/owner-pricing-orders.ts` quote input: `{ currencyUuid, exchangeCurrencyUuid, amount }`); a display label is the only additional metadata. No other provider semantics (direction, limits, `deposit_fields`) are modeled or inferred — they remain open provider questions per [[specs/nautt-finance-integration]]. UUIDs are canonical lowercase, validated at the server boundary, sourced only from the admin mutation, and never from environment variables, headers, or owner browser fields.

Persistence evolves the existing `CatalogCurrencyPair` (already the restrictive reference of `PaymentLink`; orders snapshot both UUIDs) and adds one single-active pointer table, `supported_exchange_currency`: `code` (`VarChar(3)`, database bounds check `code >= 'AAA' AND code <= 'ZZZ'` — the safe check language has no regex/length operator, so exact `[A-Z]{3}` format is enforced at the service boundary with this check as defense-in-depth) as `PRIMARY KEY`, plus `pair_id` (`Uuid NOT NULL UNIQUE`, `FOREIGN KEY → catalog_currency_pair(id) ON DELETE RESTRICT`). All three constructs (`createTable`, inline constraints, `foreignKey` with referential actions) are verified expressible in `pop/scripts/migration-policy.mjs`; `createIndex` supports only plain column lists, so no partial/expression index is cited anywhere. One pointer row per code names the currently active mapping; the pointer table is the sole authority for code-based new-selection eligibility, and the legacy `active` flag keeps governing legacy code-less rows (Epoch 3 catalog) — the spec records this boundary.

Registration inserts a new `CatalogCurrencyPair` row and upserts the pointer in one serializing transaction; replacement inserts the new row (or re-points to a retained historical row) and moves the pointer atomically; deactivation removes only the pointer row. The pointer table holds no history — history lives in retained `catalog_currency_pair` rows, whose UUID columns stay immutable after insert and which are never physically deleted or remapped in place (runtime keeps no `DELETE` on `catalog_currency_pair`; pointer-table `DELETE` is legitimate configuration mutation). Re-registering a `(currencyUuid, exchangeCurrencyUuid)` pair already present (existing `@@unique([currencyUuid, exchangeCurrencyUuid])`, `catalog_currency_pair_uuids_key`, `prisma/schema.prisma:148`) is never inserted again: the service looks up the pair inside the transaction and either returns one typed duplicate-pair conflict (when the caller asked for a new mapping) or re-points the pointer to that retained row (the sanctioned restore/reactivate path after mistaken deactivation) — the constraint is preserved unchanged, never replaced. Deactivation removes only new-selection eligibility: existing links, order snapshots, and read projections keep their recorded meaning (roadmap fork). `GlobalPaymentSettings.currencies`, the Epoch 3 catalog UI, and the public payment-link DTO are untouched by this task.

Default selection (replaces "BRL-or-none" under the dynamic model): the resolver returns the active `BRL` mapping when one exists, otherwise an explicit no-default/unavailable result. It never falls back to another code, insertion order, label order, or an inactive row. Tasks 7.1.2 and 7.2.2 own persistence of store/product choices and require an active mapping only at new-assignment time.

Role boundary: only an active `ADMIN` mutates mappings; owner (`USER`) reads return only active codes with labels (no provider UUIDs, no inactive rows, no timestamps); no public/sessionless route or projection field is added; the admin mutation route follows the `src/app/admin/` contract — origin-guard first, cookie principal re-authorization, empty `401`/`403`, opaque outcomes.

Admin registration UI: this task ships only the re-authorized mutation route and service, no management screen — the administrator configuration UI belongs to Epoch 10 (`10.4.1-build-admin-settings-hub`), and retrofitting the Epoch 3 catalog UI would couple two registry models.

## Risks and abort conditions

- **Risk:** the safe check language has no regex/length operator, so exact `[A-Z]{3}` code format cannot be database-enforced — mitigation: service-boundary validation plus the expressible `code >= 'AAA' AND code <= 'ZZZ'` bounds check; no stronger claim is made in specs or AC2.
- **Risk:** administrator-registered UUIDs may not correspond to a usable provider pair (no build-time validation possible by directive) — mitigation: treated as normal operational misconfiguration; registration stores values as given, dependent features gate only on active-mapping existence, and live provider validation stays optional per the catalog spec. This is accepted residual risk, not a recon.
- **Risk:** duplicate-pair re-registration collides with `catalog_currency_pair_uuids_key` — mitigation: in-transaction existence lookup maps it to one typed conflict or the re-point restore path; the constraint is never replaced or bypassed.
- **Risk:** replacement/deactivation changes historical meaning — mitigation: immutable UUID columns, restrictive FKs retained (including pointer `ON DELETE RESTRICT`), active-only checks only at new assignment, no delete/remap paths on `catalog_currency_pair`.
- **Risk:** the pointer table interacts with the Epoch 3 admin catalog UI that still manages pairs without codes — mitigation: the legacy UI is untouched; code-bearing mappings are managed only through the new route; the spec records the transition boundary and the pointer table's authority over code-based eligibility.
- **Abort if:** the verified `createTable`/`foreignKey` constructs cannot express the pointer-table contract as designed, or any required step would need raw SQL, backfill, destructive constraint replacement (including `catalog_currency_pair_uuids_key`), or historical rewrite; return to 002. There is no application-only-enforcement fallback: single-active-per-code is database-enforced by the pointer table's primary key or the task aborts.
