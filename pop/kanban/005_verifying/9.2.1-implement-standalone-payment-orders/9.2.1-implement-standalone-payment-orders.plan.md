# Plan — [[9.2.1-implement-standalone-payment-orders]]

- **Stage:** 002_planning · **Responsible:** planner agent

## Objective and expected result

- **Objective:** deliver the sessionless standalone-payment backend: a buyer on an enabled storefront submits an amount (plus the owner-policy customer snapshot) and opens a direct Commerce V2 order — no payment link — with server-derived owner/currency/pricing, one provider quote + one onramp dispatch, V1-grade replay/timeout fencing, opaque capability polling, and webhook-driven settlement, under the epoch's zero-trust sessionless posture.
- **Observable result:** `POST /api/store/[slug]/checkout` and `POST /api/store/[slug]/checkout/status` behave exactly like the V1 checkout/status pair (same status codes, same redacted bodies, same no-store/limiter posture) keyed by store slug instead of link identifier; confirmed provider payments move the standalone order through the settlement map V1; the owner sees the orders in the existing directory/analytics; `pnpm check` and `pnpm db:test` are green. Buyer UI is 9.2.2's, not here.

## Strategy

Server-side only; no UI, no presentation read (9.2.2 owns the experience and will amend inventories then). Pinned decisions the executor must not revisit (the behavior-shaping ones are explicit spec amendments reviewed at the critical 003 gate):

1. **Third source value `STANDALONE`.** `order_v2.source` is service-fenced `TEXT`; the vocabulary extends to `LINK | AD_HOC | STANDALONE`. This settles the question 8.1.1 explicitly deferred to 9.2.1: an `AD_HOC` variant was rejected because AD_HOC's pinned invariant is "no state, owner-only, no dispatch" and the analytics local/provider dichotomy depends on it. Owner `createAdHoc`, its route, and every V1/V2-link behavior stay byte-unchanged. Standalone orders carry the V1 state vocabulary, hold no link (`payment_link_v2_id` null), have no order lines, and snapshot a fixed server-side bilingual description constant pair — never browser text.
2. **New additive table `standalone_checkout_attempt`.** Reusing `checkout_attempt_v2` is impossible (non-null `payment_link_v2_id` FK; dropping NOT NULL is outside the safe migration language). The new table mirrors its attempt columns, binds `order_v2_id` (unique, composite restrictive FK with `owner_id`), and keys replay uniqueness by `(owner_id, retry_key_verifier)` — the store owner is the retry namespace, since no link exists. Index `(owner_id, capability_expires_at)` mirrors V2; runtime grants `SELECT/INSERT/UPDATE` only. One canonical `migration.safe.json` migration per `prisma/AGENTS.md`.
3. **Sessionless trust posture (the epoch's Pause-if line).** The browser supplies only the slug (path), an opaque retry key, the amount string, and the customer snapshot — nothing else is accepted: no owner, currency, total, status, provider UUID, credential, or order identity. The amount is the card's "sessionless amount validation": validated against the canonical product-price grammar (exact positive ASCII decimal, never `Number`) and snapshot-locked server-side. Owner, policy, currency pair, description, and expiry are derived from locked persisted state inside the reservation transaction (owner row `FOR UPDATE`; registry pair `FOR SHARE`).
4. **Store-default-currency resolution and failure mode.** Slug resolves to an owner with `storefront_enabled AND storefront_standalone_payments_enabled`; the stored `storefront_default_currency_code` must resolve through the registry's existing `requireActivePair(code)` seam to the active pair's two provider UUIDs. Every failure — unknown/disabled slug, standalone toggle off, null stored code, deactivated mapping, inactive pair — is the one indistinguishable empty no-store `404`. Never fall back to `BRL`/another code; "stored code survives deactivation" is a reads-only rule and never applies to dispatch.
5. **Retry fencing / idempotency.** Unique `(owner_id, retry_key_verifier)` reservation; a keyed request verifier over the canonical accepted request (owner identity, retry key, contract version, policy snapshot, validated amount, normalized `CustomerSnapshotV1`). An identical replay re-derives and returns the existing capability only while unexpired, unrevoked, and the storefront+standalone toggles are still enabled (the link-active gate's analog); a reused key with any changed payload is the opaque `404`. Replays perform zero quote/attach/dispatch/recovery. Capability TTL = reservation + 24h (no link expiry exists).
6. **Dispatch and capability polling contract.** Mirrors V1 verbatim: short reservation transaction (order `CREATED` + attempt `RESERVED` with nonce/key-version/expiry/verifier), `markCreating` CAS, one quote, one `POST /orders/onramp` attached to the V2 order, `markPending`; every post-dispatch ambiguity is durably `INDETERMINATE`, never retried, no transaction across provider I/O. Responses: `201`/`202` `{ payment: { state, pixCopyPaste?, pixQrCodeUrl? }, statusCapability }`; status route accepts only `{ statusCapability }` and returns `200 { payment: { state, pixCopyPaste?, pixQrCodeUrl? } }` with the closed V1 state vocabulary, same empty `400`/`404`/`429` outcomes — never a status oracle. The raw capability is never persisted/logged.
7. **Provider attach and settlement wiring (recon finding).** Today neither the V1 nor the V2 settle CAS has any production caller — webhook reconciliation only updates `provider_order`. This task wires **only the V2 path**: `ProviderOrderStore.claimForCreation` gains an additive optional `orderV2Id` (never reusing `paymentLinkOrderId`); after the authoritative owner-bound GET reconciliation persists status/version, a provider order attached to `order_v2_id` invokes `orderV2Service.settle` with exact observed identities/versions (status comes from the persisted authoritative read — notification payloads stay non-evidence). `settle` gains a standalone branch: no link join, no single-use claim when the order holds no link, same versioned CAS and transition eligibility. V1 wiring stays untouched; the V1 gap is recorded as an open question for a separate modification, not fixed here. Poll/recover wiring is deferred (no consumer).
8. **Read-side coherence (deliberate amendment, 003-reviewed).** Directory `source` filter enum gains `STANDALONE`; merchant analytics provider-confirmed sales become (`LINK` ∪ `STANDALONE`) `CONFIRMED` in-period (locally finalized stays AD_HOC-only; the two members are still never merged); the funnel reads both attempt tables; best-sellers and per-link metrics are untouched (standalone has no products/link); recent activity renders the new source through the existing summary projection.
9. **Closed inventories — this task owns them this wave** (9.1.2 edits neither; 9.1.3 amends later). Rate limiter gains exactly `standalone-checkout-submit` (burst/refill mirroring checkout) and `standalone-payment-status-poll` (mirroring status); server-request-log gains exactly the two literal templates `/api/store/[slug]/checkout` and `/api/store/[slug]/checkout/status`. Routes are unlocalized, dynamic, no-store; limiter decides before parsing; origin-guard never applies (sessionless).
10. **Prisma migration required** — only for decision 2's table. Canonical `migration.safe.json` → byte-exact generated SQL; no baseline edits, no bootstrap change expected (attempts are not append-only, so no relation-guarded re-pin — mirror `checkout_attempt_v2`).

## Risks and abort conditions

- **Risk:** sessionless trust regression (browser-derived owner/currency/total/status leaks in) — mitigation: closed body-shape validation, whitelist DTOs, absence assertions; 005 re-reads against the Pause-if line.
- **Risk:** the settlement-wiring finding (decision 7) tempts V1 fixes — mitigation: V1 wiring is explicitly out of scope and recorded as an open question; any V1 behavior change is a task-stopping divergence.
- **Risk:** analytics amendment (decision 8) rejected at the critical 003 gate — replan dropping F04 to enum-only and recording the dashboard divergence in the spec's Open section.
- **Risk:** opaque-outcome confusion between "disabled storefront" and "no active currency mapping" — mitigation: decision 4 pins one shared `404`; tests assert indistinguishability.
- **Abort if:** the 003 critic rejects decision 1 (third source value) or 2 (new table) — signal `blocked: true` with the objection and replan.
- **Abort if:** the safe migration language cannot express the table/grants — signal `blocked: true`; never hand-write SQL.
- **Abort if:** V2-only settle wiring proves impossible without mutating V1 behavior — signal `blocked: true` with evidence.
