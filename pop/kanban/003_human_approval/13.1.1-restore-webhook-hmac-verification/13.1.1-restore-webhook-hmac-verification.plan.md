# Plan — [[13.1.1-restore-webhook-hmac-verification]]

- **Stage:** 002_planning · **Role:** `pop-planner` (separate from execution)

## Objective and expected result

- **Objective:** reverse the `BETA(M-5.1)` seam so every Nautt webhook delivery is authenticated by HMAC over the raw bytes before anything is parsed, and emit a redacted rejection record that makes a production signature mismatch diagnosable.
- **Observable result:** a missing, malformed or unmatched `X-Nautt-Signature` receives an empty no-store `401` and one redacted JSON log line; an authenticated delivery keeps the `204/400/503` decisions unchanged; no code path attributes an owner from `provider_order.providerOrderUuid` any more.

## Strategy

Literal reversal of the instructions in [[pop/notes/decisions/2026-07-25-beta-unverified-webhook-intake|the M-5.1 decision]] and [[pop/open_questions/2026-07-25-pre-production-gate-restore-webhook-hmac|the reversal gate]], against the documented 2026-07-17 dispatcher contract (decision 1 of [[pop/notes/decisions/2026-09-23-epoch-13-decisions|2026-09-23]]). Order inside `intake`: signature gate → owner from verification → parse → evidence → reconcile. `loadCandidates` and `verifyOwner` become required dependencies again (`verifyWebhookOwner` as the default, so `webhook-runtime.ts` keeps wiring only `loadActiveWebhookSecrets`), `resolveOwner` disappears from the intake type, the intake body and the runtime, and `WebhookIntakeResult` regains `401`. The payload digest and the envelope parse move after authentication. `webhook-signature.ts`, `webhook-secret-candidates.ts`, `webhook-envelope.ts`, `bounded-webhook-body.ts`, the delivery store and delivery recovery are the intact reversal target and are not edited.

Two decisions constrain the gate. First, a `null` or syntactically invalid signature is `401` **before** candidates are loaded — no secret participates in that decision, so unauthenticated input never spends decryption; a syntactically valid `sha256=<64 hex>` loads every active candidate and runs the existing no-early-exit constant-time comparison, where zero and multiple matches remain one indistinguishable `401`. Second, a failure to load or decrypt secrets is `503`, never `401`, and produces no rejection record: it is unavailability, not authentication.

The rejection writer is a new server-only module mirroring `src/observability/provider-failure-log.ts` (one JSON line, console sink, swallow-on-failure, never alters a response). Its record membership is closed: event, reason, status `401`, the delivery UUID only when it satisfies `isUuid`, and the event type only when it belongs to `NAUTT_WEBHOOK_EVENTS` — both headers are attacker-controlled before authentication, so anything else logs a fixed marker. Raw body, signature value, secret, encryption key, API key and owner id are not reachable members. The reason vocabulary is closed to `missing | malformed | unmatched`; `unmatched` deliberately covers wrong-secret and multi-owner ambiguity together, because separating them would widen `verifyWebhookOwner`'s single-match return contract, which this task keeps intact (that would be its own modification).

Tests are written, never run here (phase gate 13.1.3): `webhook-intake-beta.test.ts` is deleted, the `describe("BETA(M-5.1) …")` block becomes `401` rejections asserting zero claim/finalize/reconcile work, the second describe stops relying on beta acceptance (`signature: null` cases get a signature valid for their own body), and the 1,000-owner budget test returns to the pre-beta assertions — 1,000 decryptions, 1,000 comparisons, `elapsedMs` 12,600, still under `WEBHOOK_ACCEPTED_PROCESSING_BUDGET_MS`. Nothing else moves: spec, DOX, `PROJECT.md` and the open question belong to [[13.1.2-clear-beta-caveats-and-close-reversal-gate]]; the registration surface, `NAUTT_API_BASE_URL` and any local webhook delivery test stay out. Orphan webhooks left by a reset become inert again as a consequence of the restored gate — recorded in the task's memory, not resolved here.

## Risks and abort conditions

- **Risk:** the production dispatcher signs differently from the documented contract, so live deliveries fail `401` — mitigation: the rejection record (reason + delivery UUID) identifies it in one production delivery; per decision 1 the answer is a modification, never a silent re-suspension.
- **Risk:** `loadActiveWebhookSecrets` yields no candidate when a credential is not `ACTIVE` or carries no secret, making every delivery `unmatched` — mitigation: the reason vocabulary distinguishes it from a malformed header, and criterion 8 puts it in front of the human on the first production delivery. No fallback attribution is added: that would rebuild the beta seam.
- **Risk:** multi-owner secret collision is reported as `unmatched` — accepted; the single-match rule and its disclosure-free behaviour are the untouched reversal target.
- **Abort if:** the reversal would require changing `webhook-signature.ts` semantics, inventing a signature detail Nautt never documented, or touching the registration surface — set `blocked: true` citing the epoch's pause condition in [[pop/roadmap/13-pre-production-hardening|Epoch 13]].
