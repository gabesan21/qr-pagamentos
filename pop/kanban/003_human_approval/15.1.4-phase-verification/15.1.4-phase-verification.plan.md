# Plano — [[15.1.4-phase-verification]]

- **Etapa:** 002_planning · **Papel:** `pop-planner` (separado da execução)

## Objetivo e resultado esperado

- **Objetivo:** run the accumulated Phase 15.1 checklist on the integrated V2-only base, repair only what the V1 removal falsified, and hand the human the Docker-bound checklist.
- **Resultado observável:** every `agent` criterion below exits 0 on `develop`, with no V1 reference in the sources, the suites or the gate output.

## Estratégia

The criteria table below **is** the consolidated Phase 15.1 checklist: every `verify: phase` criterion left by [[15.1.1-remove-v1-application-surfaces]], [[15.1.2-remove-v1-persistence-and-rebase-migrations]], [[15.1.3-rewrite-contracts-and-parity-without-v1]] and [[15.1.5-create-missing-parity-current-route-records]] becomes an `agent` criterion here (this is the only task where running a suite is `agent`), and every `verify: user` criterion becomes a line of the human checklist. Order: run the gates first (C1–C5), repair second, re-run the affected gate last.

Everything runs through **direct pnpm, never a container**. If `pnpm` aborts on the engine pin (local Node 26.9.0 vs the 26.4.0 pin, finding A12 of [[pop/researches/pix-checkout-review/2026-09-22-review-findings|review findings]]), the sanctioned fallback is the same commands through `./node_modules/.bin/*` and `node <script>.mjs` — the fallback is not one of the two attempts.

**Environment policy.** At most two attempts to make an `agent` criterion pass when the failure is environmental (sandbox, permission, flakiness — see [[pop/notes/references/limites-de-verificacao|verification limits]]). On the second, record `ambiente` in the telemetry, reclassify the criterion as `verify: user` with a Log line, add it to the human checklist and move on. An environment failure never returns the task and never justifies building new infrastructure. C9–C11, plus anything reclassified this way, form the **Verificação humana** section of this task's PR, each with its manual step and expected pass.

**Repair reach.** Only defects born inside Phase 15.1: suites, asserts and inventories the V1 removal falsified, dead prose comments and dead dictionary keys named in [[pop/memory/2026-09-22/15.1.1-remove-v1-application-surfaces.04-deferred-findings|deferred findings]], `sourceInventory` entries pointing at deleted modules, a stale `src/i18n/dictionaries.test.ts`. A defect **above** the reach — a durable contract that is wrong, a structural request of an earlier task that was not met, drift already owned by Phase 15.4 — is never fixed here: it becomes a proposal of modification or new task recorded in this task's memory.

## Ordem e paralelismo

1. **Onda 1:** C1–C5 gates, in order, recording each output.
2. **Onda 2:** in-phase repair (C6) plus the review pass (C8), then re-run only the affected gates.
3. **Integração:** the main agent validates ownership, confirms the `agent` criteria and carries the human checklist into the PR.

## Riscos e condições de aborto

- **Risco:** `frontend-parity:check` may still carry pre-existing violations outside the V1 scope (the 15.1.3 ledger records the retirement as clean, and 15.1.5 recorded the accepted anomaly `current-route:86a91d7b9224e135`) — mitigation: **pass for this phase is zero violation class attributable to the V1 removal or to the three routes registered by 15.1.5**; any other class is a follow-up proposal in memory, never a repair here, and the accepted anomaly stays intact.
- **Risco:** a gate fails for a durable-contract defect — mitigation: report it as a follow-up and let the human decide; never rewrite a spec from here.
- **Abortar se:** a gate can only pass by changing a spec, a DOX contract or the migration baseline — sinalizar `blocked: true` with the failing output.
