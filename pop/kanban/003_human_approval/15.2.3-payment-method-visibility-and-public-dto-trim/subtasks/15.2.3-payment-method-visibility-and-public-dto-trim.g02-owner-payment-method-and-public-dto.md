## Execution contract

- **Payment method is detail-only.** The persisted provider payment method joins the owner/admin *detail* projection and its view type; the summary projection shared with the order directory stays byte-identical, and no public projection, log or URL ever receives it. The detail's provider-order read selects that one field — never the PIX payload, the provider UUID or credential material — and keeps the existing owner-bound authorization untouched.
- The detail card renders it as one labelled row next to the existing payment-state block, with a new key in **both** `pt-BR` and `en` dictionaries and an explicit absent label when no provider order or no method exists. No hardcoded or single-locale string, no dead key. The merchant and admin detail pages are expected to need no edit: they compose the shared card. If one does, stop and return to the main agent.
- **`pixQrCodeUrl` leaves the public surface.** The four producers stop selecting, mapping and emitting it; the public accepted and status payloads become exactly `{ payment: { state, pixCopyPaste? } }`. Persistence keeps its column — this front never touches `prisma/**` or the provider order store — and `pixCopyPaste`, the state vocabulary, the capability discipline, the opaque `404`/`503` outcomes and the no-store headers are unchanged.
- Amend `pop/specs/checkout-and-order-lifecycle.md` in place: the public DTO statements lose `pixQrCodeUrl`, and the owner-detail exposure statement gains the payment method as an additive server-only exposure. Do not restore V1 wording removed by 15.1.3 and do not duplicate the statement in a new section.
- Write and run no test: the assertions belong to [[15.2.4-phase-verification]] (criterion C9).
