# Plan — [[15.2.2-fail-closed-on-documented-creation-errors]]

- **Stage:** 002_planning · **Role:** `pop-planner` (separate from execution)

## Objective and expected result

- **Objective:** classify the seven documented `POST /orders/onramp` refusal codes as a deterministic, terminal local outcome instead of `INDETERMINATE`, on the V2 link checkout and the standalone checkout, still with exactly one POST per attempt.
- **Observable result:** a refused creation (expired quote, unconfigured exchange, unavailable method, missing/invalid deposit fields) stops answering "confirming with your bank" forever: the public answer is the existing redacted pre-dispatch outcome (empty `503`, `no-store`) and the merchant reads a terminal order (`REJECTED`) whose attempt is `FAILED`, distinguishable from an ambiguous one.

## Strategy

Taxonomy lives at the adapter. A response with status `400` or `422`, a parseable body and a `code` in the closed allowlist (`order.quote_not_found`, `order.quote_expired`, `order.exchange_not_configured`, `order.payment_method_not_available`, `orders.deposit_bank_account_not_found`, `order.deposit_fields_required`, `order.deposit_fields_validation_failed`) becomes a new typed refusal error carrying that code. Everything else — network failure, timeout, any 5xx, unparseable/invalid `201`, `400`/`422` without a documented code, unreadable body — keeps `NauttOrderCreationIndeterminateError` unchanged. Classification reads only the response already received: no second dispatch anywhere.

Closed-vocabulary choice (one line, approved at 003): the order reuses the already admitted `REJECTED` because the migration-safe language may only add constraints and never widen an existing CHECK (`order_v2_state_closed`), and decision 2's destructive authorization is scoped to 15.1.2 — while the attempt takes a new service-fenced `FAILED` (attempt `state` carries no database check and fits `VARCHAR(13)`), which keeps the eight-member `OrderV2State` analytics vocabulary intact and still separates a creation refusal from a settled provider rejection.

A refusal is post-dispatch, so the attempt is not released pre-dispatch: the provider-order row is discarded and the quote claim is **kept**, making that quote permanently unclaimable — fail closed without a `provider_order` creation state the closed CHECK cannot express. The same conditional write revokes the attempt capability, so no status channel is ever opened for a failed attempt. The public surface is unchanged: refusal on first submit and on idempotent replay answers `provider-unavailable`; no provider body, code or message crosses the HTTP boundary, and the public payment-view vocabulary stays `RESERVED|CREATING|PENDING|INDETERMINATE`. Quote-phase failures, `markCreating` contention and every current indeterminate path keep today's behavior; no schema, migration or route change belongs to this task.

## Risks and abort conditions

- **Risk:** discarding the provider-order row while keeping the quote claimed could look like a leak — mitigation: the refusal proves no provider order exists; the claim is the fence that forbids a second POST on a dead quote, asserted by a test.
- **Risk:** a refusal re-submitted with the same idempotency key replaying into `accepted` would leak a `FAILED` state and a capability — mitigation: the replay path answers the same redacted outcome and the capability is revoked at failure time.
- **Risk:** 15.1.1 relocates V1 helpers (state/customer types) these modules import — mitigation: F01 follows the post-15.1.1 module layout it reads, never restores a V1 path.
- **Abort if:** the closed order vocabulary cannot carry the refusal without widening a CHECK constraint, or a front needs `prisma/**` — flag `blocked: true` citing the migration-safe language in [`prisma/AGENTS.md`](../../../../prisma/AGENTS.md).
