# Plan — [[10.3.3-build-admin-user-profile-editor]]

- **Stage:** 002_planning · **Responsible:** planner agent
- **Temporal gate:** 004 starts only after 10.3.2 merges to `develop` (detail route + `getAdminUserDetail` are the extension point; `src/auth/admin-user-directory.ts` and `/admin/accounts/` are 10.3.2's write set until then).

## Objective and expected result

- **Objective:** turn 10.3.2's read-only `/admin/accounts/[id]` detail into the administrator user profile editor: sectioned native-POST forms over an approved field set (identity, role, status, password reset, locale, checkout policy, storefront) plus a safe public-store link, re-housing the legacy mutations retired from the accounts page by 10.3.2 — without opening any credential, provider, or cross-owner commerce backdoor.
- **Observable result:** an active `ADMIN` edits a target's username/email (CAS), role, status, password, locale, checkout data policy, and storefront fields from one bilingual page; every mutation re-authorizes, origin-guards first, and lands on opaque redirects; deleted targets stay read-only and reject every mutation with the same opaque outcome; contract tests and the extended run-bound `admin-users` evidence pair prove authorization, redaction, and accessibility.

Stage skills on the card are correct for a UI task (clean-code + ui-change/ui-review + sync-specs across 002/004/005); nothing missing.

## Strategy

Admin-scoped writes in one new service module; delivered owner-scoped services and frozen routes stay untouched. Pinned decisions the executor must not revisit:

1. **Exact admin-editable field set (spec amendment candidate).** Identity: `username`, `email` (nullable). Role/status/password: via the frozen legacy routes (decision 4). Locale: `preferredLocale` (closed `pt-BR`/`en`, clearable to null). Checkout: `checkoutDataPolicy` (closed five-value `CHECKOUT_DATA_POLICIES`). Storefront: `storefrontSlug`, `storefrontDisplayNamePtBr`, `storefrontDisplayNameEn`, `storefrontAccentColor`, `storefrontEnabled`, `storefrontThemeId`, `storefrontLayout`, `storefrontStandalonePaymentsEnabled`, `storefrontDefaultCurrencyCode`. **Forbidden:** `storefrontLogoMediaIdentifier` and all media lifecycle (owner-fenced `activateOwned`/`orphanOwned` — an admin is never the media owner), Nautt credentials (denial-only route stays), provider data, sessions, audit rows, `deletedAt`, password hashes (write-only reset, never read), and any product/link/order mutation.
2. **New mutation service, delivered services byte-frozen.** A new server-only `src/auth/admin-user-profile.ts` owns admin-over-user identity, locale, checkout-policy, and storefront writes against the target id, reusing the exported `CHECKOUT_DATA_POLICIES` constant and the storefront validation grammar via an **additive export** from `src/auth/storefront-settings.ts` (export the existing private validators composed as an admin patch validator; zero behavior change to the merchant service). `administration.ts`, `identity.ts`, `profile.ts`, `checkout-policy.ts`, `locale-preference.ts` stay byte-frozen; nothing calls owner-scoped services with a forged principal.
3. **CAS and locking semantics.** Identity edit uses the `profileVersion` expected-version CAS (merchant-profile precedent: one conflict outcome for stale version or username/email unique collision, sessions retained). Locale, checkout policy, and storefront writes are single-writer admin corrections: no CAS, one advisory/user-locked transaction reusing the delivered locking helpers; slug unique collision maps to the one opaque conflict outcome; storefront currency assignment gates on the registry `requireActivePair` at genuine new assignment while a stored code survives later deactivation (same rule as merchant).
4. **Role/status/password stay on the frozen legacy routes.** The editor's role, status, and password-reset forms POST to the delivered `POST /admin/users/[id]/{role,status,password}` byte-frozen (final-admin guard, session revocation, `/admin?success=…`/`/admin?error=change-failed` redirects already rendered by `/admin`). Landing on `/admin` after these three mutations is the accepted trade-off already recorded by 10.3.2 for delete; no route contract changes.
5. **Session revocation only where already delivered.** Role, status, and password mutations revoke sessions inside the frozen routes. Identity, locale, checkout-policy, and storefront edits revoke nothing (none touch credentials or authorization) — do not add revocation.
6. **Terminality fences honored.** Every new mutation resolves the target and applies the 10.3.1 fence: a `deletedAt`-marked target is indistinguishable from an unknown one and shares the one opaque failure outcome; the editor page renders deleted users read-only with the badge (10.3.2 behavior) and no forms.
7. **Four new mutation routes + four literal request-log entries.** `POST /admin/users/[id]/{identity,locale,checkout-policy,storefront}` — origin-guard first, `requireAdminFromCookie`, empty `401`/`403`, opaque relative redirects to `/admin/accounts/[id]?editor=changed|failed|conflict` (single closed notice set rendered by the detail page), each wrapped in `withServerRequestLog` with a new literal template appended to `serverRequestRoutes`. Coordination: 9.1.3 owns in-flight appends to `src/observability/server-request-log.ts` for its surfaces — our entries are distinct keys appended after that merge; rebase-level, no logic coupling. Rate-limit surface unchanged (cookie-authenticated admin routes are not limiter surfaces).
8. **Detail read extension on 10.3.2's pinned contract.** `getAdminUserDetail` in `src/auth/admin-user-directory.ts` gains an additive editor projection: current `profileVersion`, `preferredLocale`, `checkoutDataPolicy`, and the full storefront field set (excluding nothing already stored — but never password hashes, sessions, credential/provider data, or audit rows). The editor page consumes only this read; the directory row DTO is unchanged.
9. **Safe storefront link.** When the target has `storefrontEnabled && storefrontSlug`, the editor renders a plain link to the sessionless public `/store/[slug]` (never a merchant route); otherwise an explicit localized unavailable state. Pure read-only anchor, no capability.
10. **No schema or infrastructure change.** Every edited field already exists on `user`; validation, CAS, and gating are service-fenced. If recon finds a missing column, that is an abort, not a migration.

## Risks and abort conditions

- **Risk:** admin storefront write becomes a media-lifecycle backdoor — mitigation: logo field excluded from the editable set and from every form; 005 diffs the editable set against the amended boundary.
- **Risk:** redaction regression (hashes, sessions, provider data, audit rows in the editor projection) — mitigation: whitelist DTO typing + absence assertions.
- **Risk:** identity edit frees or collides with a deleted user's retained username/email — mitigation: uniqueness mapping to the one conflict outcome; 10.3.1 retention rules unchanged (deleted identifiers stay reserved).
- **Risk:** request-log inventory collision with unmerged 9.1.3 — mitigation: append-only distinct keys; if 9.1.3 is still open at 004, land this task after its merge rather than racing the file.
- **Risk:** legacy-route redirect to `/admin` confuses editor flow — accepted trade-off (frozen contract), recorded in the spec amendment.
- **Abort if:** any editable field is absent from the delivered schema (would force a migration) — signal `blocked: true` with schema evidence.
- **Abort if:** 10.3.2's merged detail contract differs from the pinned extension point (route moved, `getAdminUserDetail` absent) — signal `blocked: true` instead of re-plumbing.
