# Plano — [[8.4.1-build-merchant-analytics-projection]]

- **Etapa:** 002_planning · **Responsável:** agent planejador

## Objetivo e resultado esperado

- **Objetivo:** Close the 8.4.1 card — define reporting timezone and periods, then implement the read-only, owner-scoped merchant analytics projection over Commerce V2: exact sales volume, completion/abandonment, conversion, product, payment-link, best-seller, and recent-activity metrics, with no cross-owner or payer-data leakage. This is the backend contract 8.4.2's dashboard consumes; no UI, no administrator analytics (10.1.1 owns it).
- **Resultado observável:** a new server-only module exposes one re-authorized `USER`-principal analytics read returning the pinned period-parameterized aggregate DTO; `pnpm check` and `pnpm db:test` are green with seeded multi-owner V2 data proving owner isolation, per-currency exact-decimal sums, and the pinned funnel definitions; `pop/specs/checkout-and-order-lifecycle.md` carries the durable merchant-analytics definitions section and root `AGENTS.md` one new application-contract line.

## Estratégia

Recon on `develop` (8.1.1 spec + 8.1.2 links + 8.1.3 orders merged) confirms all source data exists: `order_v2` (owner, source, nullable `state`, canonical decimal `amount`, currency-pair UUIDs, `created_at`/`settled_at`), `order_v2_line` (product, quantity, unit price), `checkout_attempt_v2` (owner, link, order, `state`, `created_at`, `capability_expires_at`), `order_local_outcome_v2` (append-only, latest-is-current), `payment_link_v2`, and `product` (bilingual titles, active/archived). Owner-scoped keyset indexes from 8.1.3 (`(owner_id, created_at, id)`, `(owner_id, state, created_at, id)`, `(owner_id, source, created_at, id)`, attempt `(owner_id, capability_expires_at)`) cover the aggregation access paths; no new index is expected — a preflight check confirms.

Decisions that bind execution (pinned normatively in the spec section by F01, so 10.1.1 can later reuse the vocabulary):

- **Module placement:** `src/orders/merchant-analytics.ts`, mirroring the `order-v2-view.ts` server-only projection pattern (store interface + Prisma store + `get…Service()`), governed by one new root `AGENTS.md` contract line. It does **not** fit `src/data-directory/` — that contract explicitly excludes concrete analytics projections and serves cursor directories, not aggregates. No HTTP route, no rate-limit or request-log inventory change: 8.4.2's server component (`src/app/(merchant)/page.tsx`) calls the service directly, as current pages do.
- **Reporting timezone and periods:** one fixed reporting timezone, `America/Sao_Paulo` (merchant-facing, DST-free since 2019, deterministic — never owner-configurable or derived from browser data), and a closed period set (calendar-day aligned: today-so-far, last 7 days, last 30 days) with exact half-open UTC bounds computed server-side.
- **Sales volume:** sums of canonical decimal amounts computed in BigInt micro-units (never JS `Number`), grouped by the snapshotted `(currency_uuid, exchange_currency_uuid)` pair — never summed across currency groups. Two separate, never-merged members: provider-confirmed sales (`LINK` orders reaching `CONFIRMED` with `settled_at` in period) and locally finalized `AD_HOC` sales (current local outcome `LOCAL_FINALIZED`), preserving the fence that a local outcome never masks authoritative `state`.
- **Funnel (conversion/abandonment):** defined over `checkout_attempt_v2` created in period, reproducible from persisted fields only (no provider calls): converted = attempts whose linked order reached `CONFIRMED`; abandoned = attempts past their capability-expiry horizon whose order never reached `CONFIRMED`; in-progress = the remainder (excluded from both rates' denominators exactly as the spec pins).
- **Products/best sellers:** bounded top-N by confirmed quantity from `order_v2_line` snapshots of in-period `CONFIRMED` orders, with per-currency revenue; deterministic tie-break; bilingual titles from current `product` rows; archived/deactivated products still appear (snapshot preservation). Per-link metrics: attempts/confirmed/volume over V2 links only, plus active-link count.
- **Redaction and scoping:** every read re-authorizes the active `USER` principal (`requireUserPrincipal`) and filters `owner_id` server-side; the DTO carries aggregates, bilingual labels, and the public-safe 24-char link identifiers only — never customer snapshot members, internal UUIDs, attempt/verifier/capability/provider data, or administrator/global entry points. V1 tables are untouched and excluded from aggregation by definition (V1 remains frozen); recent activity composes the bounded owner recent-orders feed (reuse `order-v2-view` semantics rather than duplicating queries).

## Riscos e condições de aborto

- **Risco:** soma cross-currency ou `Number` em agregados monetários corrompe exatidão — mitigação: definição F01 proíbe ambos; db:test prova somas BigInt por grupo de moeda.
- **Risco:** definição de abandono/conversão diverge da semântica V1 de capability/expiry — mitigação: funnel derivado só de `created_at`, `capability_expires_at` e `state` persistidos; 005 (critical, full) verifica contra o objetivo do card.
- **Risco:** agregação de best sellers exige índice novo — mitigação: preflight; somente migration aditiva de índice via `migration.safe.json` é permitida.
- **Abortar se:** qualquer definição exigir mutar semântica V1, tocar dados do provider, expor payer data, ou exigir DDL não aditivo — sinalizar `blocked: true` com a definição impossível e a evidência.
