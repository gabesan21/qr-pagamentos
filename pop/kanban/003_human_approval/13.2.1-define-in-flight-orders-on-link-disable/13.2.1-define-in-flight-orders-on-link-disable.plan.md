# Plano — [[13.2.1-define-in-flight-orders-on-link-disable]]

- **Etapa:** 002_planning · **Papel:** `pop-planner` (separado da execução)

## Objetivo e resultado esperado

- **Objetivo:** pin the undefined money-state transition — what happens to in-flight V2 checkout attempts and their `order_v2` rows when an owner deactivates a link — in [[specs/checkout-and-order-lifecycle|Checkout and order lifecycle]], and implement exactly that rule.
- **Resultado observável:** deactivating a link can no longer leave a reservation able to dispatch money; the spec's `## Open` release blocker is closed; the owner's deactivate copy stops claiming that existing orders are unaffected.

## Estratégia

**The pinned contract (decided here; the executor implements it, it does not re-decide it).** Deactivation is the only owner action that touches attempts, and it touches exactly one attempt state. In **one transaction**, `setActive(..., false)` keeps its version CAS on `payment_link_v2` (that `UPDATE` takes the link row lock, serializing with the reservation's `FOR UPDATE` in `src/checkout/public-checkout-v2.ts:165-171`) and then conditionally sweeps every `checkout_attempt_v2` of that link in state **`RESERVED`** to the service-fenced terminal `FAILED` with `capability_revoked_at` set, moving each paired order `CREATED → REJECTED` — byte-for-byte the delivered 15.2.2 refusal shape (`public-checkout-v2.ts:212-217`), a second producer of the same terminal pair: no new state, no new vocabulary, no migration. The rule applies to any V2 link deactivation, `REUSABLE` and `SINGLE_USE` alike.

**`CREATING` is never swept — this is the load-bearing justification.** The row cannot tell whether the single `POST /orders/onramp` already reached Nautt; failing it would persist `REJECTED` (terminal, immutable) while provider money exists, and the later authoritative `CONFIRMED` would be fenced into a no-op. So `CREATING`, `PENDING` and `INDETERMINATE` attempts are left untouched and keep reconciling to their authoritative outcome under the **unchanged** settlement map and versioned CAS. No dispatch survives deactivation anyway: the existing `markCreating` CAS requires `state = RESERVED` (`public-checkout-v2.ts:192-195`), so if the sweep won, dispatch never happens and checkout answers the existing redacted `provider-unavailable`; if the CAS won, the attempt is already `CREATING` and completes. Exactly one outcome per attempt, no new race.

**Buyer surface: zero client, route or DTO change** — confirmed by reading, not assumed. A swept buyer gets the `503` and the already-named *submit-failure* state with start-over as the only action (`src/app/pay/[identifier]/checkout-experience.tsx:186-205`, 15.3.1 no-retry rule); start-over re-posts to an inactive link and collapses to the one opaque unavailable view — no new state and no retry. A buyer whose payment was already dispatched keeps polling: `payment-status-v2.ts` has no link-active gate and keeps serving the authoritative order state while the capability lives, which is deliberate (the money exists at the provider and the buyer must reach its outcome); a swept attempt's revoked capability yields the opaque `404`. Capability **reissue** already stops on deactivation (`public-checkout-v2.ts:98`).

**Owner surface: no new projection, route, filter or field.** Swept orders surface as `REJECTED` in `/orders` (existing `state` filter) and in `/links/v2/[id]/orders`; in-flight `PENDING`/`INDETERMINATE` orders stay listed with their states. The only UI change is truthfulness: `paymentLinkDeactivateDescription` currently says "existing orders are unaffected" (`src/i18n/dictionaries/payment-links-directory/{en,pt-BR}.ts:74`), which this rule makes false — rewrite both locale values, no new key.

**Boundaries.** No migration: `checkout_attempt_v2.state` is `VarChar(13)` with no database check and the `(payment_link_v2_id, retry_key_verifier)` unique index already serves the sweep predicate. No V1, no webhook change, no background sweeper — link **expiry** stays passive and is out of scope (there is no mutation point to hang a conditional write on, and the capability TTL is already bounded by expiry); the spec records this as a named non-promise, not a future task. The financial-edit gate is unchanged: a swept `FAILED` attempt still locks the composition. Reactivating a link never revives a swept attempt.

## Riscos e condições de aborto

- **Risco:** deactivate × settlement race — mitigation: the sweep writes only orders still in `CREATED` (never dispatched, never reconcilable), so it can never collide with a settlement CAS; settlement never reads attempt state.
- **Risco:** deadlock with the reservation — mitigation: the deactivate transaction takes the link row lock first (the CAS `UPDATE`), then the attempts, the same order the reservation uses.
- **Risco:** leaking link state into the public DTO — mitigation: no public projection, route or DTO is in the write set; the boundary stays closed.
- **Abortar se:** the rule cannot be implemented without a migration or a new attempt/order state — sinalizar `blocked: true` with the failing constraint named.
