# 7.1.2-extend-merchant-store-settings — Plan

- **Task:** [[7.1.2-extend-merchant-store-settings]] · **Size:** L · **Critical:** yes · **Yolo:** yes
- **Planned:** 2026-07-24 · **Planner:** 002_planning agent

## Objective

Extend the persisted merchant store contract (`app.user` storefront columns +
`src/auth/storefront-settings.ts` + `POST /storefront`) so one save durably
records: theme id (closed six-theme set), logo media reference, boxed/table
layout, the standalone-payments toggle alongside the existing storefront
toggle, slug, bilingual display names, accent color, and one active default
exchange currency — with deterministic fallbacks, canonical media lifecycle
semantics for the logo, and registry-gated currency assignment. No UI: 7.1.3
owns the settings screens and logo upload.

## Strategy

One cohesive executor, four sequential sub-fronts in one delivery:

1. **Database (Prisma lane).** One additive migration
   `20260724210000_store_settings_extension` (sorts after
   `20260724120000_supported_exchange_currencies`; 7.2.2 waits for this lane).
   New columns on `app.user`, all additive, no rewrites:
   - `storefront_theme_id` `VARCHAR(24)` NULL, `CHECK (IN the six ids)`;
   - `storefront_layout` `VARCHAR(8)` NULL, `CHECK (IN ('boxed','table'))`;
   - `storefront_logo_media_identifier` `VARCHAR(43)` NULL — stores the opaque
     media identifier only, **no FK** to `media_object` (media rows are
     physically purged after grace; the identifier is the public-safe handle);
   - `storefront_standalone_payments_enabled` `BOOLEAN NOT NULL DEFAULT true`
     (typed constant default preserves today's behavior: payment links keep
     working for every existing merchant);
   - `storefront_default_currency_code` `VARCHAR(3)` NULL,
     `CHECK (~ '^[A-Z]{3}$')`.
   No `bootstrap.sql` ACL change: runtime grants on `app.user` are
   table-level (verify in `db:test`). Generate via
   `node pop/scripts/migration-policy.mjs generate`, never hand SQL.
2. **Media boundary (minimal addition).** `src/media/media-service.ts` gains
   two narrow owner-fenced, purpose-bound operations that resolve the public
   identifier to the record internally and reuse the existing revision-fenced
   `store.transition`: `activateOwned(actor, identifier, purpose)`
   (`STAGED|ORPHANED`→`ACTIVE`) and `orphanOwned(actor, identifier, purpose)`
   (`STAGED|ACTIVE`→`ORPHANED`, grace set). Rationale: the settings save knows
   only the opaque identifier, and revision fencing must stay inside the media
   subtree. No other media change; quotas, reconciliation, and read contract
   untouched.
3. **Settings service + route.** `src/auth/storefront-settings.ts` extends
   `StorefrontSettingsData` and validation:
   - Theme id must be one of the closed six themes sourced from the design
     system (single source: add a minimal read-only export of the theme-id set
     in `src/design-system` derived from `tokens/resolver.json`; a contract
     test asserts equality with the resolver keys — never duplicate literals
     without the test). Layout must be `boxed` or `table`.
   - **Absent-vs-clear:** every new field uses *absent = unchanged* merge
     semantics (service reads the current row, merges, writes). Explicit empty
     input clears theme/layout/logo/currency to NULL. This protects the
     current dashboard card (`src/app/storefront-settings-management.tsx`),
     which submits only legacy fields until 7.1.3. Legacy fields keep their
     existing semantics unchanged.
   - **Currency:** a non-null code on save is gated through the existing
     `getSupportedExchangeCurrencyService().requireActivePair(code)`;
     `NoActiveExchangeCurrencyMappingError` maps to the same opaque
     `?storefront=failed` outcome. Validation of format lives in
     storefront-settings; mapping eligibility stays owned by the registry
     service. Reads return the stored code as-is.
   - **Logo orchestration (replace):** `activateOwned` new logo → update user
     row → `orphanOwned` previous logo. On row-update failure, best-effort
     `orphanOwned` of the just-activated logo (compensation; worst case is a
     quota-counted `ACTIVE` object the owner can re-attach or let be
     re-orphaned — never a broken reference). Clear = save NULL then orphan
     the old logo. Logo state/purpose (`STOREFRONT_LOGO`) and ownership are
     enforced inside the media operations, never re-checked ad hoc.
   - `POST /storefront` accepts the new form fields and keeps exactly the
     current outcome set: empty `401`/`403`, opaque
     `?storefront=changed|failed|conflict`. Origin guard and request-log
     inventory unchanged (same route, no new entries).
4. **Public projection.** `src/storefront/public-storefront.ts` may surface
   only: resolved `themeId`, resolved `layout`, and the stored
   `logoMediaIdentifier` (the `/media/[identifier]` route already 404s
   opaquely for non-`ACTIVE` media — no media join in the projection). Never
   surface: default currency code, either toggle's raw value beyond the
   existing enabled gate, owner identity, provider data, checkout policy.

### Deterministic fallback chain (service-level, never stored)

- Theme: stored id → design-system default theme (`pix-paper`, first resolver
  theme) — resolution happens at read/projection time; NULL stays NULL.
- Layout: stored → `boxed`.
- Default currency: stored code → registry default (active `BRL` mapping) →
  explicit unavailable signal (`NoActiveExchangeCurrencyMapping` for backends,
  the 7.1.1 discriminated UI-prohibition signal for 7.1.3).
- Standalone-vs-store behavior: the toggles are independent. A disabled
  storefront keeps `/store/[slug]` unavailable (existing gate) while payment
  links/checkout stay reachable — this task persists and documents that
  contract and adds no checkout enforcement; consuming the standalone toggle
  in checkout/link flows is a later task's decision, recorded in the spec.

### Currency deactivation fork (roadmap)

Deactivating a mapping that a store references preserves historical reads:
the stored code remains and keeps rendering; only *new assignments* gate on
`requireActivePair`. Tests must prove save-with-inactive-code fails and
read-after-deactivation still returns the stored code.

## Risks

- **Cross-service atomicity:** media transitions and the user-row update cannot
  share one transaction. Mitigated by the ordered activate→save→orphan +
  compensation above; document it in the media spec as the attachment pattern.
- **Silent clearing regression:** wrong absent-handling would wipe new fields
  whenever the legacy dashboard card saves. Merge semantics + a regression
  test simulating a legacy-only form POST are mandatory.
- **Theme-set drift:** mitigated by the resolver-equality contract test.
- **Quota leak window:** a save failure after activation leaves an `ACTIVE`
  unreferenced logo; bounded by compensation + existing reconciliation paths
  once orphaned. Accept, document.
- **Baseline suite noise:** M-4.1's pre-existing failures (per 7.1.1 memory)
  must be reproduced at merge-base before being attributed.
