# Plan — [[7.1.1-model-supported-exchange-currencies]]

- **Stage:** 002_planning · **Responsible:** planning agent

## Objective and expected result

- **Objective:** establish a dynamic, administrator-registered registry of supported exchange currencies — ISO 4217 alphabetic code as the application identity, Nautt `currency_uuid`/`exchange_currency_uuid` as runtime-registered provider mapping — with transactional single-active semantics, immutable history, and a shared resolution/gating service that treats missing configuration as a normal operational state.
- **Observable result:** an active `ADMIN` can register, deactivate, and replace mappings through a re-authorized mutation surface; active `USER` callers read only active, redacted choices; dependent features (7.1.2 store default, 7.2.2 product currency, later links/checkout) receive a deterministic available/unavailable signal and typed backend errors when no active mapping exists; existing links and orders keep their recorded UUID meaning; no public/sessionless discovery surface appears.

## Strategy and fixed contract

The ISO 4217 alphabetic code (uppercase `[A-Z]{3}`, format-validated; no closed code list anywhere in code or schema) is the only application currency identity. Each registry row binds one code to the administrator-registered Nautt `currency_uuid` (fiat identifier) and `exchange_currency_uuid` (exchange/payment-rail identifier) — the exact two provider identifiers the existing pricing adapter requires at call time (`src/integrations/nautt/owner-pricing-orders.ts` quote input: `{ currencyUuid, exchangeCurrencyUuid, amount }`); a display label is the only additional metadata. No other provider semantics (direction, limits, `deposit_fields`) are modeled or inferred — they remain open provider questions per [[specs/nautt-finance-integration]]. UUIDs are canonical lowercase, validated at the server boundary, sourced only from the admin mutation, and never from environment variables, headers, or owner browser fields.

Persistence evolves the existing `CatalogCurrencyPair` (already the restrictive reference of `PaymentLink`; orders snapshot both UUIDs): add a nullable-format-checked ISO code column and enforce at most one ACTIVE mapping per code in the database plus one serializing transaction. Registration creates a new row; replacement inserts the new active row and deactivates the previous one atomically; UUID columns are immutable after insert; referenced or historical rows are never physically deleted or remapped in place. Deactivation removes only new-selection eligibility — existing links, order snapshots, and read projections keep their recorded meaning (roadmap fork). `GlobalPaymentSettings.currencies`, the Epoch 3 catalog UI, and the public payment-link DTO are untouched by this task.

Default selection (replaces "BRL-or-none" under the dynamic model): the resolver returns the active `BRL` mapping when one exists, otherwise an explicit no-default/unavailable result. It never falls back to another code, insertion order, label order, or an inactive row. Tasks 7.1.2 and 7.2.2 own persistence of store/product choices and require an active mapping only at new-assignment time.

Role boundary: only an active `ADMIN` mutates mappings; owner (`USER`) reads return only active codes with labels (no provider UUIDs, no inactive rows, no timestamps); no public/sessionless route or projection field is added; the admin mutation route follows the `src/app/admin/` contract — origin-guard first, cookie principal re-authorization, empty `401`/`403`, opaque outcomes.

Admin registration UI: this task ships only the re-authorized mutation route and service, no management screen — the administrator configuration UI belongs to Epoch 10 (`10.4.1-build-admin-settings-hub`), and retrofitting the Epoch 3 catalog UI would couple two registry models.

## Risks and abort conditions

- **Risk:** the closed `migration.safe.json` language may not express the single-active-per-code database guarantee (e.g. partial unique index) — mitigation: executor checks the generator's index/constraint vocabulary first; if inexpressible, abort to 002 rather than weakening the invariant to application-only enforcement silently (application-only enforcement with the serializing transaction is an acceptable fallback only if recorded explicitly in the spec).
- **Risk:** administrator-registered UUIDs may not correspond to a usable provider pair (no build-time validation possible by directive) — mitigation: treated as normal operational misconfiguration; registration stores values as given, dependent features gate only on active-mapping existence, and live provider validation stays optional per the catalog spec. This is accepted residual risk, not a recon.
- **Risk:** replacement/deactivation changes historical meaning — mitigation: immutable UUID columns, restrictive FKs retained, active-only checks only at new assignment, no delete/remap paths.
- **Risk:** evolving `CatalogCurrencyPair` interacts with the Epoch 3 admin catalog UI that still manages pairs without codes — mitigation: the legacy UI is untouched; code-bearing rows are managed only through the new route; the spec records the transition boundary.
- **Abort if:** the safe migration language cannot express any additive form of the contract without raw SQL, backfill, destructive constraint replacement, or historical rewrite; return to 002.
