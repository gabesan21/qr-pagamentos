# Plan — [[8.1.3-implement-generalized-order-records]]

- **Stage:** 002_planning · **Responsible:** planner agent

## Objective and expected result

- **Objective:** Implement the Commerce V2 generalized order record foundation per the approved additive contract in [[specs/checkout-and-order-lifecycle]] (V2 sections): the `order_v2`/`order_v2_line`, `order_comment_v2`, `order_local_outcome_v2`, `checkout_attempt_v2`, and `payment_link_v2_single_use_settlement` tables plus the nullable `provider_order.order_v2_id` column; owner-scoped server services for `LINK`/`AD_HOC` orders with immutable monetary/customer snapshots, append/edit comments, and append-only local outcomes (`LOCAL_FINALIZED`/`LOCAL_CANCELLED`); owner mutation routes; additive owner/admin V2 order projections.
- **Observable result:** an authenticated owner can create an ad-hoc order, comment on it, and set local finalize/cancel outcomes through owner POST routes; V2 order data reads through new re-authorized owner/admin projections exposing `state` and current local outcome as separate fields; `pnpm check`, `pnpm db:test`, and `pnpm db:contract-check` pass; no V1 row, route, projection, or fence changes behavior.

## Strategy

The binding contract is the two V2 sections of [[specs/checkout-and-order-lifecycle]] (order sources, snapshots, comments, outcomes, persistence shape, indexes, fences) read against the V2 link contract in [[specs/catalog-and-payment-links]] (8.1.2 delivers `payment_link_v2`/`payment_link_v2_line` first). The migration is the spec's fixed inventory — no design freedom — generated only through `migration.safe.json` under the Prisma subtree contract. The four service-fenced invariants (identifier grammar, canonical decimal grammar, active-dependency enforcement, source vocabulary with link/state coherence) live in service code, never in the database. `AD_HOC` creation is owner-only with no attempt, capability, provider dispatch, or `state`; `LINK` order creation and the V2 state-CAS/single-use-claim primitives are delivered as server-only services for 9.3.1's public checkout and the reconciliation seam to consume — this task adds no public/sessionless route and no rate-limit change. Customer snapshots reuse the exact `CustomerSnapshotV1` members, tuples, and normalization; local outcomes never write or shadow `state`. Everything is additive: no V1 table gains behavior, no V1 row is touched, and `src/orders/order-view.ts` keeps reading only V1 data.

- `prisma/schema.prisma`, `prisma/migrations/<new>/`, `prisma/bootstrap.sql` (grant/revoke normalization if the subtree pattern requires it), `prisma/migration-policy-baseline.json` untouched.

- `pop/specs/checkout-and-order-lifecycle.md`, `pop/specs/catalog-and-payment-links.md` — status sync only (implemented-slice notes), no contract rewrite.

## Risks and abort conditions

- **Risk:** 8.1.2 not yet merged on develop → schema/migration collision. Mitigation: preflight above; executor branches only after the `payment_link_v2` migration is present.
- **Risk:** the safe migration language cannot express an inventory item (e.g., composite FK or check shape) → forced contract deviation. Mitigation: regenerate against `migration.safe.json` first; any inexpressible item is `RECON NEEDED`, never raw SQL.
- **Risk:** local-outcome code paths accidentally writing `state` or touching provider order attachment. Mitigation: services expose no state parameter on outcome APIs; 005 full-mode review against the precedence clause.
- **Abort if:** the `payment_link_v2` tables are absent from the base branch, or the inventory requires an operation outside `migration.safe.json` — signal `blocked: true` with the missing-table grep output or the rejected manifest as evidence.
