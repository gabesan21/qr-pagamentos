## Objective

Bilingual merchant store-settings UI over 7.1.2's persistence: one sectioned Storefront workspace in `/settings` — identity (slug + display names), appearance (six-theme choice with live preview, boxed/table layout, accent, logo upload/replace/remove with official fallback), payments (storefront + standalone toggles), default currency with disabled-when-unmapped state. Posts only to the existing `POST /storefront` opaque contract plus one new logo-upload route; no new mutation semantics; never touches 7.1.2's service/route logic, media internals, or schema.

## Strategy

One cohesive executor, four sub-fronts. **Recon first:** 7.1.2 is integrated on `develop` (merge `b1dcaec`) — read its delivered code for exact form-field names and the theme-id export before writing any control: `src/auth/storefront-settings.ts`, `src/app/storefront/`, media `activateOwned`/`orphanOwned` in `src/media/media-service.ts`.

1. **Page structure (existing route, no shell change).** `/settings` (`src/app/(merchant)/settings/page.tsx`) keeps its five-entry shell place; `src/app/storefront-settings-management.tsx` grows into sectioned `Card`s:
   - **Identity** — slug + both display names, byte-identical names/semantics.
   - **Appearance** — theme `NativeSelect` sourced from the design-system theme-id export (never duplicate the six literals), layout `NativeSelect`, accent `Input` (existing), logo block, and the live preview (front 3).
   - **Payments** — existing `storefrontEnabled` `Checkbox` + new `storefrontStandalonePaymentsEnabled` `Checkbox` (default checked, matches persisted `DEFAULT true`), help lines stating the toggles are independent.
   - **Default currency** — `NativeSelect` of the registry's active redacted `{ code, label }` choices + a "no default" clear option; the server page consumes `getSupportedExchangeCurrencyService()` read-only.
   - One primary `Button` submits the whole workspace to `POST /storefront`; outcomes stay exactly the opaque `?storefront=changed|failed|conflict` alert the page already renders.
2. **Logo UX (upload → STAGED → ACTIVE on save).** New `POST /storefront/logo`: origin-guard first, re-authorize cookie merchant, one `multipart/form-data` file → `getMediaService().create(actor, "STOREFRONT_LOGO", bytes)`; returns only empty `401`/`403` or opaque redirects — success `/settings?storefront-logo=staged&logo=<identifier>` (the identifier is the public-safe handle 7.1.2 persists; no leak), failure `?storefront-logo=failed` with no cause. The page feeds the staged identifier to a hidden `storefrontLogoMediaIdentifier` input and previews via `GET /media/[identifier]` (owner may read `STAGED`); save then activates/orphans (7.1.2's job). **Remove/clear** is client-only: a secondary `Button` empties the hidden input (explicit empty clears on save) and the preview reverts to the official `BrandIdentity` `merchant-fallback` lockup — never a page-local mark. The hidden input always submits. Client hints mirror, never replace, server validation: `accept="image/jpeg,image/png,image/webp"` + bilingual help with the ≤5 MiB / ≤4096×4096 bounds from `src/media/AGENTS.md`. Abandoned STAGED logos stay quota-counted until reconciliation — accepted, documented (same posture as 7.1.2).
3. **Live preview (no page-local marks, no per-theme assets).** Tokens today scope to `:root[data-theme="…"]` only, so `scripts/generate-design-tokens.mjs` additionally emits each theme block under `[data-theme-preview="<id>"]` (mechanical, from the same theme block; `pnpm tokens:check` + the resolver-equality test keep honest). The preview is a miniature storefront mock inside a `data-theme-preview` container — header rail with logo (or official fallback) + store name, one sample product card, one primary action — semantic token classes and existing primitives only; sample copy is dictionary fixture text labelled as preview; layout choice swaps boxed/table arrangement. Accent preview: extend the exact-pattern allowlist in `scripts/check-design-tokens.mjs` to also accept `style={{ "--storefront-accent": … }}` in the new preview component (same shape as the `/store/[slug]` exception; no other inline style). One focused client boundary (extending the existing pattern) observes native `input`/`change`/`submit` to drive the preview, announces busy, and disables both forms after payload formation; it never intercepts the POST.
4. **Dictionaries, states, evidence** — below.

### Disabled-currency decision

When the registry signals no active mapping (7.1.1's discriminated UI-prohibition signal), the currency `NativeSelect` renders **disabled** with a bilingual explanatory `FieldDescription`/`Alert` ("no exchange currency is configured yet; an administrator must register one") — a normal, explained empty state, never an error and never a hidden control.

### Mandatory states (ui-change §3)

- **Default/populated:** fields prefilled from `getForOwner`; selects resolve stored values with the service fallback chain (NULL theme → `pix-paper`, NULL layout → `boxed`).
- **Loading:** owned `Skeleton` page composition (`loading.tsx` if absent) + `Spinner` in busy save/upload buttons.
- **Empty:** no logo → official fallback lockup in preview and logo block; no active mappings → the disabled-currency state above.
- **Error:** opaque destructive `Alert` from `?storefront=failed|conflict` / `?storefront-logo=failed`; no detail, no rejected-file echo (failure shows the last persisted logo).
- **Success:** existing `?storefront=changed` status `Alert`; upload success is the visible staged preview + polite status line, not a second alert.
- **Hover/focus/disabled:** owned primitives only, ≥2px visible focus; pending scope disables every control in both forms.

### Dictionary key plan (both locales, `storefront` domain)

Section headings/descriptions (`storefrontIdentityHeading`, `storefrontAppearanceHeading`, `storefrontPaymentsHeading`, `storefrontCurrencyHeading` + `…Description`); `storefrontThemeLabel`/`…Help` + per-theme bilingual descriptors keyed by theme id; `storefrontLayoutLabel` + `storefrontLayoutBoxed`/`…Table`; logo `storefrontLogoLabel`, `…Help` (types + bounds), `…Upload`, `…Remove`, `…Staged`, `…UploadFailed`, `…FallbackAlt`; currency `storefrontCurrencyLabel`, `…Help`, `…None`, `…Unavailable`; `storefrontStandalonePaymentsLabel`/`…Help`; `storefrontPreviewSample*` fixture keys. All in `src/i18n/dictionaries/storefront/{en,pt-BR}.ts`; parity enforced by existing dictionary tests.

### Accessibility and evidence

- WCAG 2.2 AA by construction: labels above inputs, one primary action per section, ≥44×44 targets, token-evidence contrast, reduced motion, 320px fit, keyboard traversal, color never the only cue; logo/fallback carries a localized accessible name that never exposes the identifier.
- Evidence: `tests/store-settings.evidence.spec.ts` + `scripts/run-store-settings-evidence.mjs` / `scripts/verify-store-settings-evidence.mjs` + `store-settings:evidence[:verify]` scripts + `artifacts/store-settings/`, cloned from the profile evidence contract: run-bound manifest, six themes × two locales × 375/768/1440 captures, plus interaction captures for staged-logo preview, remove→fallback, currency disabled-when-unmapped (the disposable runtime's natural state), keyboard traversal, and click/Enter single native POST with immediate busy/disabled; axe serious/critical, overflow, 44px, external-request, console gates; manifest-hash-bound review. If the runtime can seed an active mapping via existing admin mutations, capture the enabled currency state too; otherwise component tests cover it and the gap is declared.
